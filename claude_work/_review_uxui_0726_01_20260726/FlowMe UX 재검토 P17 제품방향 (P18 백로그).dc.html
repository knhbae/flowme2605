SECTION 1

Executive Summary — 제품 문장은 읽힌다, 실행 화면은 아직이다

제품 문장은 화면에서 전달된다

홈 h1이 "콘텐츠를 일정과 할 일로 저장", 서브가 "블로그·유튜브·공식 안내에서 따라 할 부분만 골라 일정과 체크리스트로 저장"(s01). "콘텐츠 → 일정/할 일"이라는 절반은 한 문장으로 읽힙니다. 4탭 / → /flows → /my → /calendar도 사용자 피드백대로 이해됩니다. hit·candidate 상태어, 저장 confirmation("내 Flow에 저장됨"), 티어 분리, 정상·wide 버킷 0은 P16까지 유지.

그런데 문장의 나머지 절반이 화면에서 약하다

문장의 뒷부분 "→ My Flow/Calendar로 이어주는 실행 도구"는 화면에서 덜 전달됩니다. 캘린더는 날짜 점·아이콘을 "일정 vs 루틴" 타입으로만 구분하고 어느 Flow인지는 구별하지 못합니다(pd-multi). 내 Flow는 오늘 할 일을 확인·체크하기까지 "오늘 실행/오늘 상태" 중복 프레이밍과 열기→펼치기→완료 depth가 남습니다(pd-today). 두 화면 모두 "일정 흐름·저장한 일정" 같은 일반 라벨을 씁니다. 즉 실행의 두 종착지가 아직 실행 도구가 아니라 보관함처럼 읽힙니다.

개인 실행 도구 vs creator/studio

개인 실행 도구로 간다. creator/studio는 P16에서 이미 콘텐츠 5·75, 실행 41·202,466, 복사 13·47,686으로 채워졌고 noindex도 분리됐다(s39·41). 잘 만들어졌다 — 그래서 지금 더 키울 이유가 아니라 보조 표면으로 둘 근거다. 이건 공급(supply)이지 매일의 실행 loop가 아니다.

P16이 닫은 것(확인)

P15가 "빈 방"으로 남겼던 것들이 닫혔다 — creator-profile 4 route 전부 채워짐(empty 0), my-flow-studio noindex true · flow-curation-team noindex false로 색인 정책 분리, 스튜디오 진입 정책이 /my·/calendar를 명시 허용으로 정리. 이번 리뷰는 그 위에서 다음 축을 정한다.

그래서 P18의 축

공급 창고를 채운 다음 걸음은 매일 들어가는 부엌을 마감하는 것. ① 캘린더가 Flow를 구별하게(색·라벨·같은 날짜 그룹) → ② 내 Flow 오늘 depth 축소(중복 프레이밍 통합 + 1탭 체크) → ③ 공개 /f 저장 vs 내보내기 단위 정리. 전부 4탭·스키마·공유 shell을 건드리지 않는다.

한 줄 판정 — FlowMe는 개인 실행 도구다. 방향을 바꿀 필요는 없다. 다만 P16이 공급(creator/studio)을 먼저 마감하는 동안 실행의 두 종착지(캘린더·내 Flow)가 뒤처졌다. P18은 새 표면을 늘리는 대신 이 두 화면을 "보관함"에서 "실행 도구"로 승격한다 — 그 첫 단추는 캘린더가 어느 Flow인지 말하게 하는 것이다. 창고는 채웠다. 이제 매일 쓰는 부엌 차례다.

SECTION 2

Scenario Findings — 7개 시나리오

시나리오별로 문제 · 사용자 영향 · 화면/route/screenshot 근거를 붙였습니다. 판정 chip: 양호 · 부분 문제 · 핵심 문제. 각 문제는 §3 백로그 ID로 연결됩니다.

시나리오 1

처음 온 사용자 — 제품 문장이 한 줄로 읽히는가

부분 문제

양호 · 홈이 "콘텐츠 → 일정·체크리스트로 저장"을 h1+서브+대표 추천 2장으로 5초 안에 전달한다. 카드가 "이사일만 넣으면 D-30 일정·할 일 5개", "입력 없이 8개 단원 진도표"로 저장하면 뭐가 생기는지를 결과어로 약속한다. wide(s32)도 진짜 2열로 reflow.

문제 · 제품 가설의 핵심인 "URL/메모 → 실행 가능한 Flow"의 URL 입력이 홈의 첫 행동이 아니다. 홈 primary는 "콘텐츠 고르러 가기"(큐레이션 카탈로그)이고, URL-first 붙여넣기는 /flows 안쪽에 있다. 홈만 보면 FlowMe가 "URL을 바꿔주는 도구"가 아니라 "추천 콘텐츠 카탈로그"로 읽힐 수 있다.

사용자 영향 · 자기 URL/메모를 가진 사용자가 어디에 붙여넣는지를 홈에서 못 찾는다. 제품 문장의 뒷부분("My Flow/Calendar로 이어짐")은 저장을 해봐야 보이므로, 첫 화면 한 줄에서는 "저장" 앞의 입력 경로가 비어 있다. → 근거: s01 primary CTA가 카탈로그행. §3 P18-06(라벨) 관련, 방향 §4-1.

시나리오 2

URL-first hit — 준비된 Flow를 찾아 시작하는 가치가 보이는가

부분 문제

양호 · URL을 붙여넣으면 "이미 만든 준비가 있는지 먼저 찾아봤어요" → 매칭 Flow를 실제 실행 시작으로 연다. "그대로 시작 / 조금 고쳐 시작" 토글, 시작일 입력, 내보내기 방식(캘린더/메모 문서/체크리스트) 3모드가 한 카드에 정리(urlFirstExportModesCaptured 3). AI 데모가 아니라 "찾아서 시작"으로 읽힌다.

문제 · 사용자 피드백대로 수정 자유도가 "조금 고쳐 시작"(항목 제외) 수준에 머문다. 개별 항목의 날짜·내용을 캘린더 이벤트처럼 편집하는 경로가 없다. 시작일 하나로 전체가 D-계산되므로, "이 항목만 하루 미루기/이 항목 문구 고치기"가 안 된다.

사용자 영향 · 준비된 Flow가 거의 맞을 때 사용자가 마지막 1~2개를 자기 상황에 못 맞춰, "그대로 쓰거나 버리거나"의 이분법이 된다. 장기적으로 재사용률을 누른다. → 근거: s27 편집 컨트롤이 시작일+제외뿐. §3 P18-05(항목 편집 spec), 방향 §4-4.

시나리오 3

URL-first miss/candidate — 요청 저장만으로 충분한가

부분 문제 · AI draft 보류

양호 · miss일 때 원문 URL + 내가 쓴 제목·메모를 요청으로 보관하고, 나중에 매칭 Flow가 생기면 카드가 "이미 준비된 Flow가 있어요 · 이제 실행 가능"으로 승격된다(s30). 상태어가 사용자어로 닫혀 있고(legacyStatus 0) "요청 정리본 복사"로 밖으로 들고 나갈 수도 있다.

문제 · 현재 miss의 종착은 "보관"이다 — 사용자가 얻는 건 실행 가능한 초안이 아니라 "기다리는 요청"이다. 피드백대로 AI가 초안을 만들고 사용자가 손보는 흐름은 아직 없다. 또 miss 카드 본문에 "아직 Flow화되지 않은/저장 대기/요청 대기" 같은 운영어 잔존 가능성(s29, 톤 스캔 미편입).

사용자 영향 · miss 사용자는 "저장했으니 이제 뭐?"에서 멈춘다. 다만 이건 지금 당장 열 기능이 아니다 — 초안 편집은 시나리오 2의 항목 편집 모델(P18-05)이 있어야 손볼 수 있으므로, AI draft는 실행 화면 마감 이후로 게이트한다. → 근거: s30 "보관" 종착 · s29 miss 문구. 방향 §4-4, §3 P18-08.

시나리오 4

공개 /f 공유 진입 — 저장과 내보내기 단위가 혼동되지 않는가

부분 문제

양호 · 하단 sticky 주 행동이 "내 Flow에 저장"(Flow 단위)으로 고정되고(stickyFirstActionSaveOrSetup 9/9), "콘텐츠 더 보기"는 2차 순서(beforePrimary 0). 공유 shell·출처("by 차근차근 모빌리티", "원문과 근거 TS한국교통안전공단")·주의 문구가 신뢰 위계로 정리됨.

문제 · 한 화면에 세 가지 단위가 섞여 책임이 흐리다 — (a) 하단 Flow 단위 저장, (b) 본문 중간 "진행 상황은 이 브라우저에 자동 저장 · 시트 파일을 받아두세요"(Flow 단위 백업/내보내기), (c) 항목마다 체크박스·"자세히"(항목 단위처럼 읽힘). 저장하기 전인데 항목 체크가 가능해 보여, "이 항목만 따로 받는/저장하는" 것으로 오해할 여지가 있다.

사용자 영향 · 공유로 처음 온 사용자가 "통째로 저장"과 "낱개로 가져가기"를 구분 못 한다. 주 행동(저장)과 보조 행동(가져가기)의 단위가 같은 화면에서 경쟁한다. → 근거: pd-vehicle-export(자동 저장/시트 안내) + 항목 체크. §3 P18-03, 방향 §4-3.

시나리오 5

My Flow 반복 사용자 — 오늘 할 일 확인·체크까지 depth가 적절한가

핵심 문제

양호 · "전체" 탭의 저장 목록은 실서비스급이다(s18) — Flow별 진척(0/24 완료) + 상태 chip(오늘 3·다음 3·지난 할 일 4) + 카드마다 다음 실행 항목 노출. 저장 직후 "먼저 열기"도 좋은 1차 행동(s13).

문제 ① 오늘 프레이밍 중복 · "오늘" 탭이 "오늘 실행(1개 남음)"과 "오늘 상태 · 오늘 할 일 · 오늘 2개 남았어요"를 동시에 보여준다(s16). 두 블록이 같은 "오늘"을 다르게 세어(1 vs 2) 사용자가 무엇이 진짜 남은 개수인지 헷갈린다.

문제 ② 체크 depth · 오늘 할 일을 체크하려면 카드 → "열기"/펼치기 → "실행할 일"의 "완료" 체크박스까지 내려가야 한다(pd-today). 하루에 반복하는 핵심 행동(체크)이 1탭이 아니다.

문제 ③ 밀도 · 카드마다 "기준 D-30 · 범위 쪼개기 · 일정 흐름 · 0/9 완료"가 붙어 제목이 메타에 눌린다. "일정 흐름"은 모든 카드에 반복되는 일반 라벨.

사용자 영향 · 실행 허브인데 "오늘 뭐 하지 → 체크"가 여러 프레이밍과 2탭을 거친다. 반복 사용자에게 매일 마찰. → 근거: s16(중복) · pd-today(체크 depth·밀도). §3 P18-02, 방향 §4-2.

시나리오 6

Calendar-heavy — 여러 Flow / 같은 날짜가 구별되는가

핵심 문제 · 이번 리뷰 1순위

양호 · 선택일 agenda가 타입 그룹(일정/루틴)으로 묶이고 "보기 범위 전체 Flow ▼" 필터와 카테고리 칩(운동/러닝/공부/식단)이 있다. 날짜별 "전체 11 · 일정 9 · 루틴 2" 카운트도 명시.

문제 ① Flow 구별 = 타입뿐 · 월 그리드가 "일정은 점으로, 루틴은 아이콘으로 표시" — 즉 콘텐츠 종류(일정/루틴)로만 구분하고, 어느 Flow인지는 시각적으로 구별하지 못한다. 서로 다른 Flow가 전부 같은 파란 점이 된다. 사용자 피드백("같은 색·비슷한 라벨")의 직접 근거.

문제 ② 일반 라벨 · 선택일 카드 라벨이 "일정" / "저장한 일정" / "루틴" 같은 종류어다. Flow 이름("컴퓨터활용능력 학습")은 둘째 줄로 밀려, 월 그리드 셀은 아예 "● 일정"만 뜬다.

문제 ③ 같은 날짜 여러 항목 · 다른 타입(일정+루틴)이 같은 날 있을 때는 그룹으로 쌓이지만, 같은 타입의 서로 다른 Flow가 같은 날 있을 때 어떻게 구별되는지는 현재 캡처에 없다(§5 증거 공백).

문제 ④ 역할 겹침 · 캘린더 페이지가 "내 Flow 월간 일정"이라는 제목을 달아(wide) My Flow와 이름·역할이 겹친다.

사용자 영향 · 캘린더를 "콘텐츠 종류별 핵심 실행 화면"으로 쓰려는 사용자가 "오늘 이 점이 어느 Flow의 무슨 할 일인지"를 한눈에 못 본다. 이게 이번 리뷰에서 가장 자주·가장 직접적으로 실행을 막는 지점. → 근거: pd-multi mobile·wide, s14. §3 P18-01·P18-04·P18-06, 방향 §4-1.

시나리오 7

1

캘린더를 핵심 실행 화면으로 강화할지 → YES, 가장 먼저.

캘린더는 가장 자주 열리는 실행 화면인데 핵심 작업(어느 Flow인지 구별)에서 가장 약하다. Flow별 색/마커·Flow 기준 라벨·같은 날짜 그룹(P18-01·04·06)이 P18의 첫 slice. 단 4탭·agenda 그룹 헤더 1회는 유지.

내 Flow 오늘 할 일 depth를 줄일지 → YES, 두 번째.

"오늘 실행 / 오늘 상태" 중복 프레이밍을 하나로, 오늘 카드에서 펼치지 않고 1탭 체크(P18-02). 캘린더 다음으로 매일 마찰이 큰 지점. post-save 문구·continuation 5·접힘 구조는 유지.

3

공개 /f Flow 단위 vs 항목 단위 저장/내보내기를 어떻게 나눌지 → Flow 단위로 통일.

저장 = Flow 단위 1차(sticky), 내보내기 = Flow 단위 단일 2차(캘린더/시트/메모 문서는 그 안의 형식), 항목 체크 = 저장 후 진행 표시 전용. 항목 단위 개별 내보내기/저장은 만들지 않는다 — 단위를 하나로 모아야 혼동이 사라진다(P18-03).

4

URL-first miss AI draft를 언제 열지 → 보류. 실행 화면 마감 + 항목 편집 모델 이후.

초안은 사용자가 손볼 수 있어야 가치가 있는데, 그 편집 모델(P18-05)이 아직 spec 단계다. 순서: ① 캘린더·내 Flow 마감(P18-01/02) → ② hit 항목 편집 모델 확정(P18-05) → ③ 그 위에서 miss AI draft 개방(P18-08). 지금은 "요청 정리본 복사"로 밖에서 초안화하는 현 경로 유지.

5

Studio/creator를 지금 키울지 보류할지 → 보류. 보조 공급 표면으로 유지.

P16이 이미 잘 채웠다(콘텐츠 5·75, 실행 41·20만, noindex 분리). 잘 됐다는 게 곧 "더 키우자"가 아니다 — 이건 공급이지 daily loop가 아니다. 5번째 탭 승격·publishing/monetization 축 확대는 하지 않는다. 4탭 밖 보조 표면으로 유지하고, 초점은 실행 화면에.

SECTION 5

Evidence Gaps — 더 찍어야 판단이 닫히는 것

아래는 UI 결함과 구분되는 "증거만 부족한" 항목입니다. 다음 캡처에 이 viewport/state/fixture를 추가해야 P18 판단이 확정됩니다.

  1. 같은 날짜 · 같은 타입 · 서로 다른 Flow — 현재 다중 Flow 캡처(pd-multi)는 다른 타입(일정+루틴)의 공존만 보여준다. 같은 타입의 두 Flow가 같은 날 있을 때 그리드 점·agenda가 어떻게 구별되는지 fixture·캡처 없음. P18-01의 핵심 검증 대상.
  2. 저장 Flow 3개 이상 캘린더 — 색/마커가 3~5개 Flow에서 서로 구별되는지(색약 대비 포함) 캡처 없음. "전체 Flow" 필터 적용 후 상태도 미캡처.
  3. 내 Flow "오늘" 카운트 불일치의 실제 규칙 — s16의 "1개 남음" vs "오늘 2개 남았어요"가 버그인지 서로 다른 스코프인지 evidence로 미확정. 개수 소스 정의 필요(P18-02).
  4. 모바일 햄버거 열린 상태 — 헤더 "☰" 안 항목(스튜디오·설정 등) 미캡처. wide pill+햄버거 판단(P18-07)이 닫힌 헤더 픽셀에만 의존(과거 루프부터 이월).
  5. public /f 저장 후 화면 — 저장 전(pd-vehicle-export)만 있고, 저장 후 항목 체크가 "진행 표시 전용"으로 바뀌는지 미캡처. P18-03 단위 분리 검증에 필요.
  6. URL-first custom-start·miss의 wide — wideViewportUrlFirstStatesCaptured ["hit","candidate"]뿐. custom-start·miss + 캘린더·내 Flow 롱리스트 wide 미캡처(폭 reflow spot check).
  7. post-save confirmation 지속성 — "내 Flow에 저장됨"이 영구 배지인지 소멸 토스트인지 시간축 evidence 없음(소멸형이면 캡처 타이밍 의존).
  8. 실기기 미검토 — 스크린샷·marker 근거. 실제 터치 타깃·스크롤·키보드·햄버거 상호작용은 별도.
SECTION 6

P17/P18 Recommendation

가장 먼저 할 1개 slice

P18-01 · 캘린더가 어느 Flow인지 말하게. Flow별 색/마커 + Flow 기준 선택일 라벨 + 같은 날짜 그룹. 이번 리뷰에서 가장 자주·가장 직접적으로 실행을 막는 지점이고, "콘텐츠 종류별 핵심 실행 화면"의 전제다. 한 slice로 눈에 보이는 변화가 크다.

그다음 2~4개 후속 slice

  1. P18-02 내 Flow 오늘 통합 + 1탭 체크
  2. P18-04 · P18-06 캘린더↔내 Flow 역할 분리 + 일반 라벨 → Flow 라벨(P18-01과 같은 화면군, 함께)
  3. P18-03 공개 /f 저장 vs 내보내기 단위 통일
  4. P18-05 URL-first 항목 편집 모델 spec(구현 아님, spike)

당장 하지 말아야 할 것

  • Studio/creator를 5번째 탭·publishing 축으로 확대(잘 됐어도 지금은 공급, daily loop 아님)
  • URL-first miss AI draft 개방(편집 모델 전에 열면 신뢰 하락)
  • 항목 단위 개별 내보내기/저장 신설(단위를 늘리면 P18-03과 충돌)
  • 4탭 IA·공유 shell·저장/실행/내보내기 스키마·티어 분리 변경

순서의 논리 — 공급 창고(creator)는 P16이 채웠다. 이제 사용자가 매일 들어가는 두 방을 실행 도구로 마감한다: 캘린더(P18-01) → 내 Flow(P18-02) → 두 화면 역할·라벨 정리(P18-04·06) → 공유 진입 단위 정리(P18-03). 그 위에서만 항목 편집(P18-05)과 miss AI draft(P18-08)를 연다. 방향은 그대로 개인 실행 도구 — 다만 실행의 종착지부터 실행답게.

/goal 초안 — 복사해서 그대로 실행

P18에서 먼저 처리할 순서. ① P18-01 캘린더 Flow 구별 → ② P18-02 내 Flow 오늘 통합·1탭 체크 → ③ P18-04·06 역할·라벨 정리 → ④ P18-03 공개 /f 단위 → ⑤ P18-05 편집 모델 spec. Studio 확대와 miss AI draft는 지금 열지 않는다.

/goal P18-01: 캘린더가 "어느 Flow인지"를 말하게 해줘. 지금 /calendar 월 그리드는 "일정은 점으로, 루틴은 아이콘으로" 콘텐츠 종류로만 구분하고, 서로 다른 Flow가 전부 같은 파란 점에 셀 라벨도 "일정"으로 동일해서 어느 Flow인지 구별이 안 된다(pd-calendar-multi-flow). 저장된 Flow마다 안정적인 per-Flow 색/마커를 부여해서 그리드 점과 선택일 agenda 카드(좌측 띠)에 같은 색을 쓰고, 선택일 그룹 헤더를 타입("일정/루틴")이 아니라 Flow 이름 기준으로 바꾸고, 같은 날짜에 같은 타입의 서로 다른 Flow가 있을 때 Flow별로 분리되어 쌓이게 해줘. 색은 색약 대비를 확보하고, 캡처 스크립트에 "같은 날짜 같은 타입 2 Flow" 픽스처를 추가해. 4탭 IA와 agenda 공통 메타 헤더 1회(repeatedTimingMetaRow 0)는 그대로. 완료 기준: 서로 다른 Flow가 그리드·agenda에서 색/마커로 구별, 선택일 그룹이 Flow 기준, 같은 날짜 2 Flow 캡처 존재, 버킷 0·overflow 0.
/goal P18-02: 내 Flow "오늘"을 한 프레이밍 + 1탭 체크로 줄여줘. 지금 /my 오늘 탭이 "오늘 실행(1개 남음)"과 "오늘 상태(오늘 2개 남았어요)"를 동시에 보여줘서 같은 오늘을 다르게 세고(s16), 오늘 할 일을 체크하려면 카드→열기/펼치기→"실행할 일"의 완료 체크박스까지 내려가야 한다(pd-my-today-detail). 오늘 프레이밍을 하나로 통합하고 남은 개수를 단일 소스로 만들고, 오늘 카드에서 펼치지 않고 바로 완료를 체크할 수 있는 인라인 컨트롤을 넣고, 카드 메타 chip("기준 D-30·범위 쪼개기·일정 흐름")을 1~2개로 줄이고 "일정 흐름" 같은 반복 일반 라벨은 제거해줘. post-save "내 Flow에 저장됨"과 첫 할 일 반복 0, continuation actionable 5, detail/memo/source/export 접힘(접근 삭제 금지)은 그대로. 완료 기준: 오늘 프레이밍 1개·카운트 1소스, 오늘 카드에서 1탭 체크, 밀도 marker 통과.
