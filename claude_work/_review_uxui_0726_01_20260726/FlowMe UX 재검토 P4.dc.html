/my?savedMap=moving-d30 /calendar 증거 불일치 07·08
문제두 route의 상태는 "moving-d30을 2026-07-22로 저장한 뒤"인데, 스크린샷은 둘 다 빈 상태다 — 07은 "저장할 콘텐츠를 먼저 고르세요", 08은 "일정이 생길 콘텐츠를 먼저 고르세요". route-evidence.json도 두 화면 H1을 "내 Flow"/"캘린더"로만 기록해 실제 실행 항목을 캡처하지 못했다. 혼란사용자 관점에서 이게 실제 동작이라면: 방금 저장했는데 저장 후 허브가 "아직 없다"고 답하는 최악의 신뢰 붕괴. P0-02가 고치려던 바로 그 문제의 재현이다. 판정소스(postSaveContinuationRows, fallback 큐)는 존재하므로 코드 회귀보다 스크린샷 하네스가 저장 상태를 렌더에 못 실었을 가능성이 높다. 그러나 screenshots-only 검토 기준에서는 저장 후 실행 허브가 증명되지 않았다. P4에서 채워진 상태 evidence를 만들어 확정해야 한다.

SECTION 2

Blocking / High / Medium / Low

Blocking — 사용 흐름을 막음

BL-1저장 후 실행 허브가 evidence로 증명되지 않음 (07·08)

저장 직후 /my?savedMap=와 /calendar가 빈 상태로 캡처됐다. 실제 회귀라면 최악의 신뢰 붕괴, 하네스 문제라도 "실행 앱" 주장의 증거가 없다. → 채워진 상태 재현 + 첫 페인트에서 빈 CTA가 절대 먼저 나오지 않도록 가드. (P4-01)

High — 첫 행동·저장 후 실행·이해를 크게 방해

HI-1공개 /f/ 상세: 제목 "…Flow" 접미 + 이중 입력 동선 (05)

공유 링크로 처음 온 사용자가 만나는 첫 화면인데 내부어가 새고, 시작 지점이 hero 버튼/아래 input으로 갈린다. 제목에서 "Flow" 제거, date input 하나로 통합(hero 버튼은 그 input으로 스크롤·포커스). (P4-02)

HI-2공개 /f/ 상세의 app shell 정책 미결 (05)

하단 4탭이 없는 상태가 "공유 전용 shell"인지 "누락"인지 결정되지 않음. → 공유 shell로 유지하되, 단일 목적(저장)을 명확히: 하단에 persistent "내 Flow에 저장" sticky, 저장 후 4탭 앱 shell(/my)로 진입. (P4-03 · §7 결정)

HI-3홈이 아직 설명형으로 끝남 (01)

"시작 경로" 4단계 설명 카드 + 추천 카드 3분할 그리드가 CTA 아래를 채운다. 4단계 카드 제거, 추천은 결과 한 줄로 압축해 홈을 "입구"로. (P4-04)

Medium — 밀도·문구·카드 위계

ME-1특수 workbench 톤 통일 — slate/gray/blue-700 유틸 → FlowMe 토큰(#3654FF·#FAFAF8·#E7E4DD·16/12px radius). (P4-05)

ME-2지도 원문 제목의 "AJD" 접두 제거 — 사용자 표면에 무의미 토큰. 콘텐츠명만 노출 (03). (P4-06)

ME-3지도 결과 약속 한 줄 길이 — "+ … + …" 나열이 2줄 넘음. 핵심 결과 1개 + "외 N" 형태로 (03·04). (P4-06)

ME-4/flows "12개 콘텐츠" pill 강등 — 헤더 우측 배지 → 목록 위 12px 캡션 (02). (P4-04 묶음)

Low — polish · spacing · tone

LO-1공개 /f/ 신뢰 칩 2개("출처 확인됨" + "확인하며 진행")를 1줄로 정돈, 위계 낮춤 (05).

LO-2지도 본문 문단 3~4줄 → 2줄 클램프 + 접힘 (03).

LO-3로고 "FLOW" vs 서비스명 FlowMe vs 탭 "내 Flow" 표기 기준 1개 확정.

LO-4.premium-dark 오버라이드가 아직 slate 팔레트 기반 — 정식 다크가 필요 없으면 정리 검토.

바로 개발 가능한 P4 백로그

위→아래가 권장 착수 순서. 줄번호는 commit c4ba63d 근사치. 새 기능 없음 — 전부 위계·언어·톤·증거 정리.

P4-01 Blocking

저장 후 실행 허브 증거 확정 + 첫 페인트 가드

목표저장 직후 /my?savedMap=·/calendar가 항상 "다음 할 일/일정"부터 보이고, 빈 상태 CTA가 첫 페인트에 먼저 뜨지 않는다. 화면MyFlows post-save/today, calendar surface · route-evidence 생성 스크립트 지시① 저장 상태를 실제 localStorage에 심은 뒤 07·08을 재캡처(채워진 Today + agenda). ② 첫 페인트 가드: 저장 레코드가 존재(또는 savedMap 파라미터 존재)하는데 hydration 전이면 빈 CTA 대신 스켈레톤/로딩을 렌더. ③ postSaveContinuationRows가 비면 fallback 큐(오늘→밀림→다음→날짜없는 첫 항목)로 최소 1개를 보장. 완료07은 방금 저장한 콘텐츠의 먼저 할 일 카드, 08은 2026-07-22 일정 + agenda가 첫 뷰포트에. 빈 상태 문구 미노출. 검증저장 후 route evidence 재생성 + Playwright: 저장→/my 진입 시 실행 카드 존재, "먼저 고르세요" 부재 단언.
P4-02 High

공개 /f/ 제목 "Flow" 접미 제거 + 입력 동선 단일화

목표공유 링크 첫 화면에서 내부어를 없애고, 시작 지점을 하나로. 화면/f/[slug] hero (PublicFlow) · seed 제목 데이터 지시① 제목 "자동차검사 D-14 준비 Flow" → "자동차검사 D-14 준비". 사용자 표면 렌더에서 "~Flow" 접미 스트립(데이터 원본 보존, 표시만 정리). ② date input 1개만: hero "검사일 입력으로 시작"은 그 input으로 스크롤+포커스+하이라이트(지도 sticky와 동일 패턴), 아래 "1. 검사일 입력하기"의 중복 input 제거 또는 동일 input 참조. 완료제목에 "Flow" 없음, date input 1개, hero 버튼이 그 input을 포커스. 검증사용자 라우트 금지어 스캔에 "~ Flow$" 패턴 추가, /f/ 입력 포커스 e2e.
P4-03 High

공개 /f/ 를 "공유 shell"로 확정 + 단일 저장 CTA

목표4탭 없는 상태를 의도된 공유 화면으로 확정하고, 목적을 저장 하나로 좁힌다. (정책 결정은 §7) 화면/f/[slug] shell · 상단 우측 "내 Flow" 버튼 지시① 하단에 persistent sticky "내 Flow에 저장" 1개(4탭 대신). ② 우상단 "내 Flow"는 저장 이력이 있을 때만 노출하는 보조 링크로 강등(첫 방문자에겐 저장 CTA만). ③ 저장 완료 → /my?savedMap=(4탭 앱 shell)로 이동. ④ 상단에 얇은 "FlowMe" 워드마크로 출처만 표기. 완료공유 화면의 주행동이 저장 1개로 명확, 저장 후 앱 shell로 연속. 검증/f/ 진입 시 sticky 저장 CTA 존재, 저장 후 4탭 shell 진입 e2e.
P4-04 High

홈을 설명서에서 입구로

목표CTA 아래를 "행동을 돕는 것"만 남긴다. 화면HomeLanding (≈L1607~) 지시① "시작 경로 · 고르고 저장하고 이어가기" 4단계 설명 카드 제거. ② 추천 콘텐츠 카드의 입력/저장/결과 3분할 그리드 → 결과 한 줄("이사일만 넣으면 D-30 일정 · 할 일 5개")로. ③ 추천은 1~2장까지만, 나머지는 /flows로. ④ (묶음) /flows "12개 콘텐츠" pill을 목록 위 캡션으로 강등(ME-4). 완료홈 스크롤이 CTA→추천 1~2장에서 끝, 4단계 설명 없음. 검증홈 첫 2뷰포트 스크린샷, "시작 경로" 텍스트 부재 단언.

SECTION 4

가장 먼저 — P4-01

P4-01 · 저장 후 실행 허브 증거 확정 + 첫 페인트 가드

FlowMe의 제품 약속은 "저장 = 실행의 시작"입니다. 그런데 그 약속을 증명해야 할 두 화면(07·08)이 지금 빈 상태로 찍혀 있습니다. 이건 단순 버그 여부를 떠나, 상용 앱이라고 말하려면 반드시 닫아야 하는 증거 공백입니다. 다른 P4 항목(공개 /f/ 톤, 홈 압축)은 모두 "저장 전" 개선인데, 저장 전이 아무리 좋아도 저장 후가 빈 화면이면 재사용률이 무너집니다.

그래서 P4-01은 두 가지를 동시에 합니다 — (1) 채워진 상태의 07·08을 재현해 저장 후 허브가 실제로 동작함을 evidence로 고정하고, (2) 첫 페인트 가드를 넣어 저장 레코드가 있는데 hydration 전이라도 빈 CTA가 먼저 뜨지 않게 합니다. 이 하나로 Blocking이 닫히고, 나머지 P4는 안심하고 "저장 전" 품질에 집중할 수 있습니다.

착수 근거: BL-1 · route 07·08 · postSaveContinuationRows 존재 확인

7.1 공개 /f/ 상세 — "공유 shell"로 확정 (감사 open question 답)

결정 — 4탭에 맞추지 말고, 공유 shell로 유지한다

근거: /f/는 공유 링크로 앱 밖에서 처음 진입하는 화면이다. 여기에 4탭을 붙이면 "아직 내 것도 없는데 내비게이션부터" 주는 꼴이라 저장 전환을 흐린다. 공개 문서 뷰(노션·구글닥 공유)와 같은 패턴 — 탐색이 아니라 단일 행동(저장)에 집중시키는 게 맞다.

대신 지켜야 할 3가지

  • 하단 persistent "내 Flow에 저장" sticky 1개(4탭 대체) — 주행동 1개
  • 저장 완료 → /my?savedMap=로 이동해 거기서부터 4탭 앱 shell
  • 상단은 얇은 "FlowMe" 워드마크로 출처만. 우상단 "내 Flow"는 저장 이력 있을 때만

SECTION 8

최종 판단

설명형 vs 실행형

저장 전은 실행형. 홈·Flow 찾기·지도는 이제 행동/결과 중심으로 읽힌다. 저장 후는 미확정 — 07·08이 빈 상태라 실행 허브를 증명하지 못했다. 공개 /f/만 아직 설명형 잔재.

처음 온 사용자, 5초

홈에선 이해한다 — "콘텐츠를 일정·할 일로 저장" + 단일 CTA. 다만 스크롤 시 설명 카드가 동력을 깎는다(P4-04). 공유 /f/로 처음 온 경우엔 시작점이 갈려 5초 통과가 약하다(P4-02·03).

저장 후 다음 행동

코드 경로(postSaveContinuationRows·fallback 큐)는 설계됐으나 evidence로는 보이지 않는다. 반복 사용자에게 빠른 실행 허브인지는 채워진 07·08 없이 단언 불가 — P4-01의 존재 이유.

상용 앱 대비 아직 가장 약한 화면 3

  1. 저장 후 My Flow / 캘린더 (07·08) — 실행 허브 증거 공백. 최우선.
  2. 공개 Flow 상세 /f/ (05) — 내부어 접미 + 이중 입력 + 옛 톤 + shell 미정. 밀도 최고.
  3. 홈 하단 (01) — CTA 아래가 설명서로 끝남.

다음 루프 착수 순서

P4-01(저장 후 증거·가드) → P4-02·03(공개 /f/ 접미·동선·shell) → P4-04(홈 압축) → P4-05·06(workbench 톤·지도 문구) → P4-07(브랜드·다크 정리). 앞 4개까지가 "실행형 앱"이라고 자신 있게 말할 수 있는 선입니다.
