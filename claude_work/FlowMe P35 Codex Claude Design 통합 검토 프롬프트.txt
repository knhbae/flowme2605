======================================================================
1. 검토 목적
======================================================================

이번 검토는 P35를 승인하기 위한 형식적 확인이 아니다.

P35에서 구현한 다음 방향이 실제로 옳은지 평가한다.

- Flow 찾기 / 캘린더 / 내 Flow 3탭 구조
- 설명보다 실제 결과를 먼저 보여 주는 public Flow
- 한 번에 한 종류만 여는 Flow 조정
- 저장 목록과 한 Flow workspace를 분리한 내 Flow
- 날짜가 있는 항목에 집중하는 Calendar
- whole/selected/current 범위를 먼저 고르는 가져가기

잘못된 방향이면 structural_reopen을 제안해도 된다.

FlowMe는 무거운 planner가 아니다.

원문·메모
→ 실행 가능한 전체 결과
→ 최소 개인화
→ FlowMe 저장 또는 외부 도구로 가져가기
→ 실행·완료·다시 열기
→ 수정·기록·재사용

을 연결하는 portable execution layer여야 한다.

======================================================================
2. 사용자 피드백
======================================================================

1. Flow 조정에서 항목 제목, 상세 내용, 개별 날짜까지 수정할 수 있어야 하지 않는지
검토한다. 현재 UI에 contextual Item edit를 연결하는 방법과 full editor의 차이를
비교한다.

2. 저장 완료 후 곧바로 오늘 할 일이나 다음 행동으로 보내는 것이 필요한지 검토한다.
사용자가 저장된 전체 Flow를 먼저 확인해야 하는지도 비교한다.

3. 날짜형 Flow의 다음 할 일은 한 항목이 아니라 같은 날짜의 미완료 항목을 묶어
보여 주는 것이 적절한지 검토한다. 날짜 없는 Checklist, routine, sheet에는 각
형태에 맞는 실행 단위를 제안한다.

4. Flow 찾기/public preview에서 Calendar, Checklist/Todo, Sheet, Memo, Routine 중
자연스러운 결과를 먼저 확인한 뒤 FlowMe에 저장 또는 본인 캘린더·할 일·표·메모로
가져가기를 선택할 수 있어야 하는지 검토한다.

모든 결과를 고정된 5개 탭으로 노출하지 않는다. Primary artifact 1개와 의미 있는
secondary artifact 최대 2개만 제안한다.

5. 완료한 항목이 현재 화면에서 사라질 때만 즉시 되돌리기를 제공하고, 행이 남아
있으면 체크박스로 다시 여는 정책이 적절한지 검토한다. 완료, 제외, 삭제, 날짜 이동,
Flow 보관의 복구 문법을 구분한다.

6. 내 Flow의 다음 행동 탭이 모호한지 검토한다. 다가오는 일정, 남은 할 일,
이번 회차, 현재 단원 같은 형태별 라벨 또는 탭 제거 대안을 비교한다.

7. 기록 탭도 검토한다. 완료 history, 단계 메모, 회고, 보류, 다시 쓰기가 섞여
있다면 진행 기록으로 축소하거나 각 문맥으로 분리한다.

각 피드백을 다음 중 하나로 판정한다.

- supported
- partly_supported
- rejected
- needs_observation

3. 필수 시뮬레이션
======================================================================

다음 Flow를 모바일 390x844와 wide 1024x768에서 직접 조작한다.

- 이사 D-30: /f/moving-d30-basic
- 날짜 없는 차량 점검: /f/vehicle-inspection-prep
- 반복 홈트: /f/curated-allblanc-morning-workout
- 학습 Sheet: /f/source-backed-middle-school-math-1
- Memo/Guide: /f/overseas-safety-register
- Flow 찾기: /flows
- 저장 후 실행: /my
- 날짜별 실행: /calendar

각 Flow에서 다음 세 session을 이어서 본다.

Session A:
발견 → 전체 결과 → 조정 → artifact 확인 → FlowMe 저장 또는 외부 가져가기

Session B:
저장 receipt → 전체 저장 결과 → 다음 실행 묶음 → 완료 → 다시 열기 → 항목 수정

Session C:
진행 기록 → 단계 메모·회고 → 전체·선택·현재 가져가기 → 새 실행으로 다시 쓰기

자동화와 agent simulation을 실제 사용자 검증이라고 표현하지 않는다.
현재 observed-user count는 0이다.

4. 비교할 구조
======================================================================

A. 현재 P35

Public result
→ 최소 조정
→ FlowMe 저장
→ receipt
→ 다음 행동 / 전체 계획 / 기록
→ 가져가기

B. 저장 전 full editor

Public result
→ 구조·일정 전체 편집
→ 저장 또는 export

C. Artifact preflight + contextual personalization

Public result
→ 필요한 항목만 수정
→ artifact·개수 확인
→ FlowMe 저장 또는 외부 가져가기
→ 짧은 receipt
→ 형태별 개인 Flow workspace

세 구조를 5개 Flow 형태와 모바일 화면에서 비교하고 다음 중 하나를 선택한다.

- retain
- revise
- structural_reopen

======================================================================
5. 레퍼런스 비교
======================================================================

Todoist, Things, Google Calendar Tasks, Notion, Wanderlog, Strava,
Nike Training의 공식 UX를 확인한다.

화면을 복제하지 말고 다음만 비교한다.

- Today와 전체 project의 관계
- contextual Item detail
- 같은 날짜 묶음
- 완료 후 undo와 persistent recovery
- plan, current occurrence, history의 분리
- 동일 데이터의 Calendar/List/Sheet projection
- 저장 전 결과 확인과 외부 가져가기

각 패턴을 adopt / adapt / reject로 판정한다.

evidenceKind를 포함한다.

======================================================================
7. 제한
======================================================================

- 앱 코드를 먼저 수정하지 않는다.
- source, personal overlay, execution run, recurrence occurrence,
  export identity를 합치거나 다시 작성하지 않는다.
- 모든 artifact를 고정 탭으로 늘어놓지 않는다.
- 가짜 사용자 수, 평점, 리뷰를 실제 정보처럼 사용하지 않는다.
- 긴 설명 문구로 구조 문제를 덮지 않는다.
- AI API, crawler, DB, cloud sync, OAuth로 UX 문제를 우회하지 않는다.
- 자동화나 screenshot을 실제 사용자 검증으로 표현하지 않는다.

Codex는 current source와 Preview를 대조하고 구현 영향, 테스트, rollback까지 제안한다.

Claude Design은 앱 코드를 수정하지 않고 current/proposed 화면을 나란히 비교한
standalone HTML 또는 동등한 시각 산출물을 작성한다.
