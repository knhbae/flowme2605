# 선별 게시부터 개발계 반영까지

[목표·권한](spec.md)을 따른다. 승인 대기 중에는 단계0~1의 준비만 진행한다.

| 단계 | 작업 | 다음 단계 진입 조건 |
| --- | --- | --- |
| 0 현재 상태 | 직전 후보·feedback SHA·최신 main·PR210·현재 DEV/자동 시작 기준을 읽기 전용 대조 | 소유 목록과 기준선 기록 |
| 1 게시/운영 설계 | allowlist·공개 경계·hook·CI·정확 QA·새/기존 두 대상 전환/복귀 절차 준비 | 문서 검사 통과, 실행 범위 승인 |
| 2 선별 게시 | 승인된 경로만 stage, 새 branch/commit, 정상 pre-commit/pre-push, Draft PR 생성 및 연결 | 실제 게시 SHA·hook/build·PR 근거 |
| 3 CI·정확 후보 | 해당 commit의 필수 CI, 게시 build 합성 브라우저 QA, 전후 소스/정적 자산 일치 | 새 commit CI 성공 및 정확 후보 QA 통과 |
| 4 운영 인수/DEV | 운영 소유자와 단일 실행 책임 확인, 현재 세대 guard, 새 후보 전환·기존 CP2 복귀·후보 재진입, 자동 시작 대상 정렬 | 로컬/외부 정확 판본·복귀·보호값 근거 |
| 5 마감 | 결과·실행 수·게시/개발계 상태·NOT_RUN/잔여 기록, 목표 판정 | spec의 필수 완료 조건 충족 시 complete. 승인/상태 변화가 필요하면 미완료 인계. 같은 차단이3goal턴 반복되고 안전한 진행이 소진되면 blocked |

소유·공개 경계 감사와 현재 운영 기준선 감사는 독립 병렬 작업이다. root는 두 결과를 대조하고 승인·실행·마감 책임을 맡는다. 기존 원시 운영 파일은 덮어쓰지 않으며 새 준비 사본과 새 receipt를 사용한다.

## 검증 비례성

이전 후보 테스트를 같은 실행으로 재집계하지 않는다. 정상 hook의 `verify`는 그대로 실행하고, 같은 새 commit의 CI를 확인한다. 새 build의 좁은 메모·날짜 앱 QA32건을 재실행하되, 반영을 이유로 미결 정책·대형 백업·모든 실기기 시험을 추가하지 않는다. 다섯 화면 크기는390×844·375×812·844×390·1024×768·1440×900이다.

전환 도중 앱 중단이 필요하면 정확 대상과 일시 영향을 먼저 표시한다. 현재 DEV 소스를 빌드하면서 서비스하지 않는다. 실패하면 기존 CP2와 기존 자동 시작 대상으로 정상 복귀하며, 다른 QA 서버·Tunnel 프로세스를 종료하지 않는다.
