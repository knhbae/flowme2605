# 단계 계획

1. **기획·범위:** 두 완료 목표의 기록과 현재 diff, 최신 피드백 정정, 원격/기존 개발계 판본을 대조한다. 구현/QA/반영 상태를 분리하고 게시 allowlist를 확정한다.
2. **개발 설계·안전 준비:** 소유 input·private pack·자료·설정·기존 build·process/Tunnel의 읽기 전용 baseline을 확보한다. 기존 승인 launcher·정확한 rollback·자동 배포 미발생 경로를 점검한다.
3. **현재 검증:** 보안/출처/private 경계와 문서 검사를 먼저 한다. 변경 제품의 npm test·production build·필수 CI 및 좁은 두 묶음 browser 경로를 실행한다. 과거 전체 실행을 현재 PASS로 재사용하거나 같은 시나리오를 유일 수로 합산하지 않는다.
4. **승인된 게시:** 정확한 allowlist만 stage/commit하고 기존 개발계 PR207 head 위 stacked Draft PR로 검토한다. hook 우회·전체 dirty stage·main merge 없이 exact head의 네 CI를 확인한다.
5. **개발계 반영:** 마지막 build와 소스/HEAD/자산이 결합된 후보를 동결한다. 기존 PID/부모/생성시각/절대 경로/3105 소유를 재확인한 뒤 승인된 앱만 교체한다. 설치·build는 실행 작업본에서 하지 않는다.
6. **검증·마감:** 무인증 health·외부 경계·정확한 자산·합성 조작을 확인한다. 실제 계정 writer를 사용하지 않는다. 문제면 보존 이전 build로 복귀하고 실패/현재 판본을 기록한다. 마감 문서는 필요하면 실행 제품과 분리한 작업본에서 게시한다.

승인 대기 중에도 1–3의 안전한 독립 작업은 진행한다. 서비스 교체·외부 게시를 우회하지 않는다. 새로운 UX 정책이나 기존 운영 데이터 경계를 열어야 하면 이 목표에서 확장하지 않고 결정 사항으로 남긴다.
