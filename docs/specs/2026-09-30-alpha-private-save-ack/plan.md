# 실행 계획

1. 현재 Git·소유 범위·실행 중 호스트와 이전 실패 증거를 확인한다. 별도 담당이 독립 안전 계약 검토와 커밋/푸시 경계를 조사한다.
2. 검증된 receipt를 snapshot에 노출하고 순수 개인 저장 확인 gate를 만든다. shell → space → mounted editor 확인 포트를 연결한다.
3. 표적 회귀와 합성 Chromium 시나리오로 같은 요청 성공·실패·외부 변경·추가 입력·조합 보호를 검사한다. 기존 실패 기록은 보존한다.
4. 전체 테스트·실행 중 호스트를 보호하는 격리 빌드·문서 검사·독립 검토를 완료한다.
5. 이전 작업 이벤트로 소유 delta를 복원해 clean publication candidate를 검증한다. 보안/자동 배포/CI 게이트를 통과한 범위에서만 commit/push하고 배포는 하지 않는다. 미충족 게이트는 근거와 다음 행동을 기록한다.
6. 승인된 최소 보안·원문 확인 보완을 후보에서 구현하고 전체 테스트·빌드·합성 화면을 다시 확인한다. Render/Vercel은 Git 게시의 자동 배포 경계만 읽는다. 기존 #204 head 기반의 새 브랜치·별도 Draft PR으로 원격 CI를 실행하고 기존 비공개 검토 gate는 유지한다.
7. 첫 CI의 실제 실패 로그를 읽고 승인된 테스트 동선을 보완한다. 날짜·시간 적용, 보관 위치, 실제 관리 메뉴 열기와 월간 fixture의 고정 날짜를 사용하되 기존 자료 보호·Undo·취소·실패 검사는 유지한다. 후속 게시 후 동일 CI의 비공개 검토를 승인 범위 안에서 실행하고, 최종 판정은 PR 본문·checks에 기록한다. 개발계 runtime은 교체하지 않는다.
8. 두 번째 CI의 private catalog 실패를 같은 고정 원본으로 재현한다. 승인된 여섯 공개 출처 metadata의 정확한 delta만 허용하는 테스트와 부정 회귀를 추가하고, 고정 pack·전체 seal·본문/Item/Map/variant 보호를 유지한다. 전체 통합 검사 후 필요한 후속 commit/push와 동일 CI를 실행한다. 먼저 통과한 760개 브라우저 결과를 새 head의 통과로 이월하지 않는다.
