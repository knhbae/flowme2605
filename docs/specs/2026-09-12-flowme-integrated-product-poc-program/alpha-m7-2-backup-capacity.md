# M7-2 백업 한도 적정성 측정

판정: **용량 원인·성능 측정 완료, 용량 개선 구현은 다음 단계**다. 콘텐츠 4개 추가 후 작업본을 여는 시뮬레이션에서 계정 내용은 줄었지만 전체 이력이 늘어 백업 입력이 26.76→31.46MB가 됐다. 60MB 후보는 로컬에서 처리됐으나 비용·압축 임계값 결합을 확인했으므로 즉시 제품 기본값으로 채택하지 않았다. 사용자가 지금 용량 숫자나 요금제를 정할 필요는 없다. M7-2 전체 완료를 뜻하지 않는다.

## 이번 목표와 범위

사용자는 30MB를 지금 영구 정책으로 정하지 않고 성능·복원 검사 결과를 보고 조정하기로 했다. 2026-09-23의 계속 진행 요청에 따라 [직전 묶음](alpha-m7-2-catalog-wave2.md)의 용량 위험을 측정한다. 복잡한 저장 구조 변경이나 한도 유지/상향을 먼저 결론으로 두지 않는다.

이번 산출물은 재현 가능한 성능 측정 도구, 구간별 한도 지도, 실제 결과와 후속 판정이다. 기존 M7-2 실행 원장의 하위 검사이므로 새 spec/plan/tasks/qa 문서를 네 개로 중복 생성하지 않고 이 문서에서 계획·완료 조건·결과를 함께 관리한다.

### 계획

1. [x] 현재 Git·기존 코드와30MB 적용 구간을 읽기 전용 확인.
2. [x] 원본 백업의 메모리 복사본으로 현재/콘텐츠 추가/편집 기록 누적 시나리오 구성.
3. [x] 단계별 시간·프로세스 최대 메모리·원문/identity/hash 보존을 반복 측정.
4. [x] 브라우저의 codec/미리보기 준비 시간·지연/메모리 관찰. 실제 기기 성능으로 표현하지 않음.
5. [x] 측정 도구 테스트, 제품 source 불변 검사, 문서/관련 회귀 확인.
6. [x] 한도 적정성·단기 권고·후속 구현 조건을 기존 원장에 연결.

### 경계

- 실제001/002 계정과 `D:/FlowMe-Backups` 원본은 읽기 전용. 원본 파일 SHA를 전후 대조한다.
- 계정·서버·DB writes0, 운영계·Auth·credential 파일 접근0. 네트워크는 측정 코드에서 차단한다.
- 30MB 이상 후보는 **메모리 안에서만 상수를 바꾼 별도 실험 빌드**로 검사한다. 현재 제품 파일·DB 한도를 바꾸거나 후보를 배포하지 않는다.
- 합성 응답/서명과 실제 서버 검증을 구분한다. CPU·메모리 측정은 이 Windows PC의 로컬 프로세스/Chromium 결과이지 DB·운영 인프라나 실제 휴대폰 보장이 아니다.
- 원문·변경 기록을 지우지 않는다. 유료 전환·보존기간·전체 계정 제한 등 제품 정책을 이번에 정하지 않는다.
- 기록하는 것은 크기·시간·메모리·검사 결과·소스 hash다. 개인 원문/토큰/이메일/비밀번호는 출력이나 보고서에 넣지 않는다.

## 판정 기준

- 측정 정확성: 단계 구간을 명시하고 준비 비용과 처리 비용을 분리한다. 가능한 반복 실행 결과를 모두 보존하며 가장 빠른 수치만 제시하지 않는다.
- 메모리: Node `resourceUsage().maxRSS`는 프로세스 시작 이후 최대 RSS다. fixture 준비·제품 코드 로드도 포함한다. 단계별 `memoryUsage`와 함께 기록하며 순수 처리 증분으로 오해하지 않는다.
- 안전: 손상·허위 확장 크기·상한 초과는 부분 결과나 writer 호출 없이 거절해야 한다. 메모리 원문 roundtrip과 기존 원본 hash는 같아야 한다.
- 현재 흐름: 제품30MB를 바꾸지 않은 경로의 성공/거절을 먼저 재현한다. 더 큰 후보가 로컬에서 처리돼도 DB/동시 실행/실기기 검증 없이 즉시 적용 가능으로 판정하지 않는다.
- 성능 참고선: 로컬 단일 요청의 각 주요 단계10초, 프로세스 최대 RSS1GiB, 브라우저 단일 긴 작업200ms를 **이번 실험의 경고선**으로 본다. SLA·제품 정책·휴대폰 성능 기준으로 확정하지 않는다. 경고 초과 원인을 분리해 다음 검증/구현을 선택한다.

## 현재 조사

JS 공통 JSON·계정 payload, 압축파일/확장원문, HTTP body와 DB 백업 조회 집계가 서로 다른 대상을 검사하지만 같은30MB 수치를 쓴다. 특히 현재 계정이 작아도 전체 이전 상태를 담는 inverse 이력이 누적돼 백업 조회 한도에 먼저 도달할 수 있다. 한 구간의 숫자만 올려서는 전체 경로가 해결되지 않는다. 각 구간의 지도와 측정 결과를 아래에 보완한다.

### 구간별 한도 지도 — 로컬 구현 감사

모두 30,000,000바이트이며 30MiB가 아니다. 원격 DB에 적용된 정의를 이번에 다시 조회한 것은 아니다.

| 구간 | 제한 대상 | 코드 근거 |
| --- | --- | --- |
| JS JSON | compact UTF-8 JSON 객체 하나. 계정 외 복제·검증·백업에도 적용 | `alpha-persistence/contract.ts`, `json.ts` |
| DB JSON·계정 행 | `jsonb::text` 크기·깊이. JS compact와 공백/표현이 다름 | `20260921090702...private_commands.sql`, `20260923061216...full_catalog.sql` |
| HTTP·commit | 요청/응답 stream 또는 서명 대상 commit 문자열 각각. RPC 포장 크기는 별도 | `alpha-server/*-handler.ts`, 각 migration |
| 전체 백업 읽기 | 계정+공개 context+모든 operations+archives를 합산. 일부 이력만 반환하지 않음 | `20260921142955...preservation.sql` 40–46행 |
| 백업 생성·검증 | 계정+참조+전체 operations+archives+현재 사진 base64 | `alpha-preservation/backup.ts` |
| 파일·압축 해제 | 파일과 확장 원문 각각 제한. 작은 gzip도 원문 한도 유지 | `alpha-preservation/file-codec.ts` |
| 복원 전송 | 최종 HTTP JSON. raw가 넘으면 restore만 압축; 확장 원문 한도는 그대로 | `alpha-preservation/transport.ts` |
| 재시도 pending | 원문 문자열. IndexedDB이므로 HTTP JSON의 이중 escaping과 다름 | `alpha-preservation/pending-store.ts` |
| archive·사진 | archive 한 건과 복원 사진 binary 누적 각각 별도 제한 | preservation/private-media-restore migrations |

한도와 별개로 파일당 2MB·파일 512개·operations 100,000개·백업 archives 128개 검사도 있다. SQL archive 수는 30건이다. 이를 통일된 사용자 할당량으로 해석하면 안 된다.

최신 creator writer는 변경된 필드의 이전 **전체 값**을 inverse로 보관한다(`20260923061216...full_catalog.sql` 185–203행). 계정·commit이 유효한지 확인하지만, 저장 후 전체 백업 읽기가 가능한지까지 보장하지 않는다. 따라서 “저장은 성공했지만 다음 전체 백업은 한도 초과”가 가능한 구조다.

### 실험 방법과 한계

- 원본 백업은 디스크에서 읽고 메모리 안에서만 복제했다. 현재 내용, 앞서 연결한 콘텐츠 4개 추가, 편집 열기, 항목 이름 3회 변경을 실제 creator dispatcher로 재현했다. inverse는 SQL과 같은 필드 전체 이전 값으로 구성했다. 이것은 실계정 저장 결과가 아니라 실제 제품 함수에 기반한 로컬 시뮬레이션이다.
- 기준과 후보 모두 같은 제품 함수를 실행한다. 후보 60MB는 지정한 TS 3파일의 리터럴 4곳만 메모리상 번들에서 바꾼다. SQL·실서버·제품 파일은 바꾸지 않는다.
- 백업 생성, 파일 압축/해제, 무결성 검증, wire 준비를 구간별로 측정한다. 실제 preservation handler에도 합성 인증·RPC 응답을 주입해 백업 생성, 같은 상태 복원 미리보기, 변조 seal 거절을 검사한다. 실제 서버 seal 검증·DB 잠금/쓰기·복원 commit은 아니다.
- 원본에 포함된 현재 사진은 0개다. 이 실험 결과를 사진 다량 첨부, 낮은 압축률, 100,000건 이력, 동시 요청, DB timeout 성능으로 일반화하지 않는다. 파일 크기만으로 성공 여부를 판단하는 일반 공식도 제안하지 않는다.
- 각 Node 조건은 새 프로세스에서 3회 반복한다. heap 상한은 실험 프로세스에만 1,536MiB, 실행 제한은 회당 180초다. CPU는 Intel Core Ultra 7 256V, 논리 8코어, RAM 약 16.68GB, Node 24.17.0/Windows다. 워크스테이션의 다른 앱 부하는 통제하지 않았다.
- Node 최대 RSS에는 원본, fixture 생성, 합성 응답, 이미 만든 검증 결과가 함께 포함된다. 실제 서버 단일 요청의 메모리 요구량으로 제시하지 않는다. `maxRSS`는 KiB 단위의 프로세스 최대 resident set이며 단계 끝의 RSS와 구분한다([Node 24 문서](https://nodejs.org/docs/latest-v24.x/api/process.html#processresourceusage)). 전체 실험 시간에는 긍정/부정 검증을 함께 포함하므로 사용자가 느끼는 다운로드 시간과도 다르다.
- 브라우저는 fresh Chromium context와 네트워크 차단 페이지를 사용한다. 합성 반복 문자열의 codec/transport만 측정하고 전체 복원과 구분한다. sampled JS heap은 전체 프로세스 메모리나 보장된 peak가 아니다.

### 재현 명령

현재 worktree에서 `node scripts/alpha/m72-backup-capacity.mjs`를 실행한다(`--smoke`는 현재 백업 한 번). 지정된 원본 파일이 로컬에 있어야 하며 없으면 실패한다. 원문은 결과 파일에 저장하지 않는다. browser는 `npx tsx scripts/alpha/m72-backup-codec-browser.ts --synthetic-read-only`로 재현한다.

측정 실행은 제품 조작·기능 완료 검사가 아니다. 결과의 `success=false`와 `alpha-too-large`는 초과 거절 시나리오의 기대 결과이며, 도구 실행 실패와 분리한다.

## 재현된 원인

| 메모리 복사본 시나리오 | 현재 계정 bytes | 이력 bytes | 백업 구성 입력 bytes | 이력 수 |
| --- | ---: | ---: | ---: | ---: |
| 원본 기준 | 3,890,227 | 7,213,598 | 11,104,379 | 75 |
| 콘텐츠 4개 추가 | 6,260,973 | 20,500,025 | 26,761,552 | 79 |
| 추가 후 편집 작업본 열기 | 5,988,263 | 25,468,567 | 31,457,384 | 80 |
| 이어 항목 이름 3회 변경 | 6,130,736 | 39,354,276 | 45,485,566 | 83 |

표의 입력은 계정+참조+operations+archives+작성 시점이다. 파일 wrapper/서명/backup 메타데이터를 포함한 최종 파일 크기가 아니다. 이 실험은 현재 사진 0개다. 앞선 용량 probe와 수십 바이트 차이는 측정용 draft/request ID 차이이며 실제 원본의 차이가 아니다.

특히 작업본을 열면서 현재 계정은 272,710바이트 줄었지만 백업 입력은 4,695,832바이트 증가했다. 이어진 이름 변경마다 4.64–4.71MB가 늘었다. 디스크 백업 폴더 부족이나 사용자가 큰 파일을 더 올린 문제가 아니다. 현재 creatorWorkspace의 이전 전체 값을 누적하는 경로를 우선 다뤄야 한다.

원본 기준과 4개 추가는 현재 30MB 경로를 통과한다. 작업본 열기부터는 생성·서버 handler의 전체 읽기 단계에서 초과 거절이 재현된다. 실제 PostgreSQL은 `jsonb::text` 표현과 집계 메타데이터를 더 계산하므로 이 표로 DB의 정확한 남은 여유를 주장하지 않는다.

## Node 처리 비용 — 18회 완료

6조건 × 3회다. 정상 처리 12회, 기대한 초과 거절 6회이며 도구 실패·timeout·비정상 종료는 0회다. 정상 처리에는 exact 파일 왕복·backup 무결성·동일 상태 preview·변조 seal 거절·handler 백업 생성 검사가 포함된다. 실행 결과는 숫자·hash·boolean만 저장했다.

| 개발용 JS 한도·자료 | 백업 handler 초: 중앙 [최소–최대] | 복원 preview 초: 중앙 [최소–최대] | 측정 프로세스 최대 RSS |
| --- | --- | --- | ---: |
| 현재 30MB / 원문 11.10MB | 3.14 [3.04–3.40] | 3.62 [3.47–3.77] | 0.74GiB |
| 현재 30MB / 원문 26.76MB | 7.77 [7.66–11.75] | 7.80 [7.35–7.96] | 1.20GiB |
| 실험 60MB / 원문 31.46MB | 7.57 [7.51–8.42] | 8.44 [8.33–9.88] | 1.33GiB |
| 실험 60MB / 원문 45.49MB | 11.07 [10.76–11.10] | 11.42 [11.02–11.89] | 1.70GiB |

RSS는 fixture·원본·합성 응답·긍정/부정 검증을 함께 들고 있는 **측정 프로세스 전체 최대치**다. 이 표를 실서버 단일 요청의 메모리나 DB 성능으로 해석하지 않는다. handler도 네트워크 왕복 없이 로컬 응답을 받아 실행했다. 모든 구간의 개별 3회 수치는 원본 근거에 남아 있다.

현재 한도의 두 초과 사례(입력 31.46/45.49MB)는 백업을 만들지 않고 거절했다. fixture 생성 후 handler 거절 시간 중앙값은 각각 0.31/0.45초다. 원문을 일부 잘라 통과시키거나 실패 파일을 성공으로 표시하지 않았다.

측정 경고선과 비교하면 현재 26.76MB부터 프로세스 RSS 1GiB를 넘고, handler 백업 1회는 10초를 넘었다. 후보 45.49MB는 handler 백업·미리보기 모두 3회씩 10초를 넘었다. 큰 자료 처리의 비용을 무시하고 60MB를 바로 기본값으로 채택할 근거가 되지 않는다.

압축 임계값 결합도 실제 자료 복사본에서 확인했다. 후보의 31.46MB 원문은 4,514,903바이트 파일로 압축할 수 있지만 preview가 35,643,619바이트 raw 요청을 선택했다. 45.49MB도 압축 파일 6,499,039바이트 대신 raw 요청 51,528,761바이트를 선택했다. 반면 현 30MB에서 26.76MB 원문은 3,847,644바이트의 압축 요청을 사용한다. HTTP 한도를 높이는 것이 압축 시점까지 늦추는 현 결합은 분리 대상이다.

## 후속 구현 순서 — 용량 숫자는 사용자 결정 사항으로 넘기지 않음

이번 측정에 이어 다룰 목표는 **기록을 지우지 않고 반복 편집 후에도 백업·복원이 가능한 저장 경로**다. 60MB를 영구 한도로 채택하거나 무료 검증을 유료 운영으로 바꾸는 목표가 아니다.

1. **중복 이력 축소의 호환 설계·소규모 구현 비교**: creatorWorkspace 전체를 매번 복제하는 대신 변경된 작업본/초안 단위 이전 값을 보관하는 versioned inverse 후보를 먼저 검증한다. 기존 inverse·Undo/Redo·CAS·idempotency 의미와 과거 백업은 그대로 읽혀야 한다. 표현을 줄여도 이전 상태가 정확히 재구성되지 않으면 채택하지 않는다. 이력 삭제·기간 단축·조용한 생략은 제외한다.
2. **저장과 백업 가능성 연결**: 현재 데이터가 저장 한도 안에 있어도 전체 백업이 불가능해지는 상태를 재현 테스트로 고정한다. 작은 반복 편집 100회 이상, Undo/Redo, 응답 유실·재시도·경합 뒤에도 전체 백업을 만들 수 있어야 한다. 이력 표현 개선만으로 해결되지 않는 규모는 일관된 snapshot/manifest 기반 분할 백업을 별도 비교한다. 한도 숫자만 늘린 결과를 해결로 판정하지 않는다.
3. **한도와 처리 비용 분리**: HTTP 압축 전환 임계값, expanded bytes, JSON 객체·DB 전체 읽기·사진 한도를 목적별로 다룬다. 보안 검사와 무결성 검사를 생략하지 않으면서 중복 직렬화·복제를 줄인다. 브라우저 긴 작업은 작업 분리·진행/취소 경로로 검증한다.
4. **실제 경로 검증**: 구/신 inverse와 백업 호환, 원문/identity/hash, owner/RLS/서명·누락 chunk·순서·다른 revision 혼합·도중 실패 원자성을 검사한다. 로컬/격리 fixture 통과 후 별도 DEV 시험 자료로 DB 집계·동시성·시간을 확인하고, 그 결과로 개발용 수치를 정한다. 실제001/002의 기록을 부하 시험용으로 늘리지 않는다.

다음 단계에서도 새 서비스 가입·요금제·유료 전환·보존기간 결정을 먼저 요구하지 않는다. 비용 발생이나 보존 의미 변경이 필요한 경우에만 사용자 결정으로 올린다. 현재 30MB는 기존 구현 그대로 남아 있지만 측정으로 정당화된 영구 정책은 아니다.
