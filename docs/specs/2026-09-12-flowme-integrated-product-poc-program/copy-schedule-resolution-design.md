# 개인 시작일·계획 충돌의 명시 수용 설계

2026-09-14 · 모델·UI 연결 후 [같은 실제 작성물의 검증](copy-schedule-resolution-review.md)을 진행했다. 개인 시작 조건별 남은 브라우저 조합과 일반↔반복 전환·여섯 틀/Map/전체 개선 루프는 유지한다. [64상태의 실제 작성물](authored-update-loop-review.md)을70까지 이어 사용했다.

## 기존 요구와 연결 지점

원본의 새 일정을 읽는 것과 개인 실행을 바꾸는 것은 별개다. 현재 `series-private-start`와 `series-personal-plan`은 수용 자체를 거절한다. 기존 계획을 계속 쓰려면 ‘그대로 유지’를 사용하고 다른 설명 등은 별도로 수용할 수 있다. 새 일정을 쓰려는 사람에게는 이전 선택과 기록을 보존하는 명시 수용이 필요하다.

1. 읽기 전용 비교에서 실제 이전/새 공개 일정, 개인 시작일, 해당 사본·항목의 개인 계획을 보여준다. 개인 본문 일정이 직접 바뀌었거나 일반↔반복 종류가 바뀐 경우는 이 경로로 넘기지 않는다.
2. 사용자가 기록 보관을 확인한 경우에만 일정 한 필드를 수용한다. 개인 시작일을 새 고정/상대 원문으로 대체하면 이전 값을 남긴다. 개인 계획 owner·operations·실행 이벤트와 원래 회차 기록은 변경하지 않는다. 달라진 원문으로 기존 회차를 자동 재연결하거나 완료를 복제하지 않는다.
3. 기존 `recurrence` 아래 선택 필드 `retainedChoices.version:1`에 요청 identity, 항목, 이전/새 일정 판본, 당시 개인 시작 선택, 관련 계획 owner ID와 시각을 기록한다. 원문 규칙을 다시 복사하지 않는다. 기존 payload는 읽기만으로 이전·쓰기하지 않으며 운영 key/schema는 바꾸지 않는다. 이력 상한은 버전 상수로 둔다.
4. 비교 당시 내용과 현재 공개/개인 상태를 재대조하고 기존 Program CAS/readback/receipt/Undo를 사용한다. 취소·같은 상태·잘못된 확인·stale·quota에서 성공 변경은0이다. 새 일정은 명시 수용 뒤에만 적용한다.
5. 기존 비교 화면에 충돌이 있을 때만 보관 확인과 적용을 노출한다. 실패 안내는 적용 버튼 옆에 두고 선택을 유지한다. 이전 선택은 접힌 이력에서 원래 판본으로 열 수 있게 한다. Figma 새 산출물 없이 기존 컴포넌트/CSS를 재사용하는 Code-only 작업이다.

## 완료 판단

시작 미정 원문→개인 시작 입력→고정 원문 수용, 개인 전체/이후 계획→다른 원문 일정 수용, 이전 계획/기록 조회, 정확한 판본과 문서 복귀, 실패/재시도·Undo/reload를 각각 확인한다. 모델/저장/브라우저/실기기 증거를 구별한다. 지원이 연결되기 전까지 기존 차단은 유지한다.

일반↔반복은 다음 별도 전환이다. 기존 일반 항목의 원문·개인 메모·날짜별 진행·하위 체크·문서 참조를 보존하면서 새 실행 의미를 연결해야 하므로 위 확인 하나로 차단을 우회하지 않는다. 이 설계를 그 요구의 완료나 영구 제품 정책으로 해석하지 않는다.

정확한 옛 판본·시작으로 다시 수용하면 그 원본에 연결된 기존 개인 계획이 다시 활성화될 수 있다. 확인 화면은 이를 보관과 구별하며 자동 새 실행으로 만들지 않는다. 보존 이력의 계획 ID는 당시 연결을 가리킨다. 명시 계획 Undo로 기록 없는 owner가 제거된 뒤에도 이력은 읽되, 현재 존재하는 다른 사본/항목 owner로 연결하지 않는다. 새 반복 계약이나 종류 전환이 이 의미를 바꾸면 이력 validator와 복귀 시나리오를 함께 재검토한다.

## 수용 후 새 시작일을 정하는 연결

실제 70→73의 제안/새3판 공개→74의 미정 일정 수용 뒤, 과거 개인 계획이 존재한다는 이유만으로 새 시작일 저장을 거절하는 결함을 재현했다. 보관을 확인한 새 원문을 실행할 수 있어야 한다는 위 요구의 누락이다.

수용한 일정 판본·항목·계획 ID와 일치하는 `retainedChoices`가 있고 해당 계획의 원본 판본이 현재 수용 판본과 다른 경우에만 기존 시작일/기준일 입력을 허용한다. 옛 계획·완료·이벤트·공개 판본·문서는 그대로 둔다. 같은 수용 판본에 속한 계획은 시작 날짜가 달라도 기존 계획 범위 확인을 요구한다. 보관 확인이 없거나 다른 판본/항목/계획의 확인이면 계속 거절한다. 이 연결은 새 저장 필드나 자동 재연결·실행 초기화를 만들지 않는다.

미정·상대 시작과 전체·이후 계획의 교차 회귀, 실제 같은 공개 자료의 UI 시작 입력·완료/보존 기록·실패/취소/Undo/reload로 확인한다. 향후 같은 판본의 계획 재시작 UX를 설계할 때 이 보수적 경계는 별도로 재검토한다.
