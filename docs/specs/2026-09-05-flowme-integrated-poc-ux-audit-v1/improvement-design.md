## 1. 이번 설계가 바꾸지 않는 것

일반 텍스트 작성 → 결과 확인 → 명시적인 개인 Flow 저장 → 개인공간에서 정리·실행하는 경로를 유지한다. 강제 구조 검토 단계, 별도 틀 편집기, 새로운 첫 화면 wizard는 만들지 않는다. 개인 Flow 저장과 별도로 승인된 제작자 초안·회차·로컬 원문 비교도 삭제하지 않는다. 해당 기능은 후속 P2/P3 계약의 범위만 보존한다.

원문·개인 계획·실행의 소유자를 구분한다. 원문의 체크는 개인 실행 완료가 아니며, 날짜 보기의 기준 월은 계획 기준일이 아니다. 날짜 미정, 원본 따르기, 기간에서 숨기기, 계획에서 제외하기도 서로 대체하지 않는다.

전역 `PlatformNav`와 ink/cobalt는 그대로 둔다. exact-query 내부의 흰 본문·회색 탐색·청록 행동·평면 목록은 이미 승인된 로컬 문법이다. 새로운 전역 디자인 시스템을 선택하지 않는다.

관련 정본:

- [A0 결정 기록](../2026-09-02-flowme-integrated-poc-gap-closure-v1/a0-decision-record.md): 저장 경로, staged 편집, 한 편집기, standalone 역할.
- [Stage 3 계약](../2026-09-02-flowme-integrated-poc-gap-closure-v1/stage-3-contract.md): 필드 소유자, dirty 닫기, 저장 영수증, 날짜 3상태.
- [제품 UX 계약](../2026-09-03-flowme-integrated-poc-product-ux-pass-v1/design-contract.md): 화면 위계, 로컬 UI, 모바일, 오류·초점·Undo.
- [P3-F 결정](../2026-09-04-flowme-integrated-poc-production-candidate-v1/decision-contract.md): 전역/로컬 경계와 여덟 데이터 소유 영역. 이 문서가 개인 포함 여부의 소유 영역을 이미 정했으므로 그 결정을 다시 묻지 않는다.
- [P3-D 계약](../2026-09-04-flowme-integrated-poc-source-update-ownership-v1/spec.md): 로컬 원문 후보 비교·적용·복구. 외부 업데이트 기능이 아니다.

## 3. 먼저 고칠 편집 안전성

### 3.1 S3-P: 속성 도움의 정확한 항목 소유자

`P3K-D2-01`, 브라우저 `K-X1`에 대응한다. 행 번호 하나만으로 적용 대상을 기억하면 원문 편집 뒤 다른 항목을 가리킬 수 있다.

| 상태 | 화면과 문구 제안 | 허용 행동·초점 | 쓰기 |
|---|---|---|---|
| 선택 직후 | `첫 번째 할 일 · 장소`처럼 실제 대상 제목과 속성명을 보여 준다. 같은 제목이 여럿이면 구간명을 보조 표시한다. 내부 ref는 기본 화면에 노출하지 않는다. | 첫 값 입력에 초점. 원문은 같은 편집기에 남는다. | 0 |
| 값 입력 중 | `이 항목에 적용`을 주 행동으로 둔다. | native Tab, Shift+Tab 유지. 취소/Escape는 도움을 닫고 원래 opener 또는 유효한 원문 위치로 돌아간다. | 0 |
| 도움을 연 뒤 원문 변경 | `원문이 바뀌어 적용할 항목을 다시 확인해야 해요.` 적용을 비활성화한다. 입력한 장소는 도움의 임시 값으로 보존한다. | `항목 다시 선택`으로 돌아간다. 선택하지 않은 다른 항목에 자동 적용하지 않는다. 원문을 작성 중이면 초점을 강탈하지 않는다. | 0 |
| 재선택 | 새 대상 제목과 보존된 값을 함께 확인한다. | 사용자의 명시적 재선택 후에만 새 ticket을 발급한다. | 0 |
| 정상 적용 | 아래 저장 원자성 절차가 성공한 경우에만 원문 반영을 알린다. | 해당 원문/항목 위치로 복귀. 한 번 Undo/Redo 유지. | 승인된 draft transaction만 |

개발 설계는 도움을 여는 시점의 document/editor instance, source fingerprint, revision 또는 동등한 dispatch epoch, exact owner binding을 함께 고정한다. 적용 때 최신 source fingerprint로 과거 ticket을 다시 포장하지 않는다. source change 뒤 제목·행 번호·유사도로 대상을 추정하지 않는다. 보존할 수 없는 selection은 문서 내 안전한 현재 위치로 복귀시키고 예외를 명시한다.

소스 ticket은 UI 안전장치이며 새로운 운영 Item identity 발급 정책이 아니다. 기존 `savedCopyId + flowId + itemId`와 원문의 source binding을 바꾸지 않는다.

### 3.2 S3-F: 원문 반영과 임시 보관의 결과를 하나로 처리

`P3K-D2-03`, 브라우저 `K-X3-react`, `K-X3-standalone`, `K-X3-reload`에 대응한다. 현재 실제 문구는 “저장 성공”이 아니라 일반 원문 반영 알림이었다. 문제는 실패 안내가 이 알림에 덮이고, 화면과 durable draft bytes가 달라진 뒤 reload에서 변경이 사라진다는 것이다.

다른 틀/구조/예시 적용 경로에 이미 있는 실패 rollback 계약을 속성 적용에도 맞춘다. 임시 보관 실패를 새로운 자동 저장 정책으로 해결하지 않는다.

| 상태 | 원문·입력값 | 표시·행동 제안 |
|---|---|---|
| 준비 | exact before 원문·selection·scroll·draft bytes를 보존한다. 값 입력은 도움의 임시 상태다. | `적용` |
| 적용 중 | 계획된 원문 변경과 허용 key 저장/readback을 하나의 논리 transaction으로 처리한다. 중복 적용을 차단한다. | `반영 중…`; 닫기와 재시도 중복 차단 |
| 성공 | 화면 원문과 마지막 성공 draft가 일치한다. native Undo 한 번이 정확한 원문 변경을 되돌린다. | `항목 정보를 반영하고 이 기기에 보관했어요.` |
| 보관 실패·정상 rollback | source와 durable bytes는 직전 성공 상태로 돌아가고, 입력한 속성 값은 재시도할 수 있게 남는다. | `보관하지 못해 원문은 바꾸지 않았어요. 입력한 값은 남아 있어요.` + `다시 시도` + `취소` |
| rollback 검증도 실패 | 성공으로 간주하지 않는다. 원문·bytes의 확인된 상태만 설명하고 추가 적용을 막는다. | `복구 상태를 확인하지 못했어요.`; recovery 상태와 기존 안전한 복구 경로. 확인 없이 reload·초안 초기화를 권하지 않는다. |
| 다시 시도 | 현재 source와 exact before를 다시 검증한다. stale이면 다시 선택 단계로 간다. | 같은 사용자 intent를 한 번만 적용한다. 성공 후에만 실패 안내를 해제한다. |

오류는 한 live region이 소유한다. 보조 toast가 뒤늦게 성공 문구를 덮지 못하도록 `success | failed | recovery-required | stale | canceled | noop` 결과를 호출자까지 전달한다. draft 보관은 개인 Flow handoff가 아니므로 아직 개인공간에는 새 Flow가 생기지 않는다.

### 3.3 S7-C: dirty 닫기

`K-D1-01`을 원래 Stage 3 상태표로 복구한다. 새 확인 단계를 모든 행동에 덧붙이는 것이 아니다.

- clean: 취소·닫기·Escape·Back은 바로 닫고 정확 opener로 돌아간다. storage write 0.
- dirty: 같은 close intent에서 `변경한 내용을 버릴까요?`를 묻는다. 첫 초점은 안전한 `계속 편집`; 다른 행동은 `변경 내용 버리기`다.
- 계속 편집: 입력 값·부모 Plan draft·selection·scroll을 유지한다.
- Item 버리기: 해당 Item draft만 버리고 이전 부모 Plan draft는 보존한다. Plan 전체 버리기와 문구·범위를 구분한다.
- submitting/recovery: 닫기·배경·전역 Undo로 미완료 transaction을 우회하지 못한다. 작업 상태를 알린다.
- 실패: draft와 오류 위치를 유지하고 `다시 시도`를 제공한다. 실패를 dirty 버리기로 자동 전환하지 않는다.

dialog 위에 또 modal을 쌓는 대신 기존 overlay 안의 확인 상태를 사용한다. Escape는 최상위 상태에만 적용한다. 원래 opener가 사라진 경우에는 원래 보기의 heading으로 복귀하고 이유를 검증 기록에 남긴다.

### 3.4 IME 후보의 처리

`P3K-D2-04`는 아직 실제 실패 재현이 아니다. 양쪽 입력 폼에서 composing Enter, compositionend 직후 Enter, 일반 Enter, 취소/Escape를 별도 검사한다. 합성 composing 이벤트 검사는 자동화 증거이고, 실제 한국어 IME·Android/iOS 입력 검사는 `NOT_RUN`이다. 조합 중 Enter를 적용으로 해석하는 코드 경로가 확인되면 조합이 끝나기 전 mutation 0을 보장한다. native Tab을 속성 적용 단축키로 바꾸지 않는다.

## 4. 새로 저장한 Flow의 첫 실행

### 4.1 S4-H: source 체크와 실행 완료 분리

`P3K-BP-03`, `BP-039`, 브라우저 `K-X4-source-checked`에 대응한다.

| 값 | 명시 handoff 직전 | 새 개인 Flow 생성 직후 | 사용자가 완료한 뒤 |
|---|---|---|---|
| 원문 `[x]` / sourceChecked | 원문 사실 | 그대로 보존 | 그대로 보존 |
| 개인 실행 완료 | 아직 실행 대상 없음 | 미완료 | 완료 transition의 결과 |
| 완료 시각 | 원문 표식으로 생성하지 않음 | 생성하지 않음 | 승인된 실행 계약으로 기록 |
| Text 원문 보기 | 원문의 표식 | 원문의 표식 | 원문의 표식 |
| 개인 실행 결과 | 해당 없음 | `0/1 완료`, 미완료 행동 | `1/1 완료`, 다시 열기 행동 |

신규 handoff 경로에만 이 초기화 계약을 적용한다. 기존 payload의 `done`이 실제 사용자 완료인지 과거 source 표식에서 유래했는지 provenance 없이 알 수 없다. 기존 완료를 일괄 삭제하거나 운영 schema를 바꾸지 않는다. 기존 버전 read는 보존하고, 필요한 호환 처리에서는 명시적인 버전 판별·불변 테스트를 먼저 설계한다. fixture 기본값과 새 사용자 handoff 초기화도 같은 함수인 것처럼 섞지 않는다.

### 4.2 S4-R: 저장 영수증과 첫 화면

작성 완료 화면은 `개인 Flow로 저장했어요.` 아래 제목·생성한 항목 수·위치 `미분류`를 보여 주고 `개인공간에서 열기` 하나를 주 행동으로 둔다. 내부 lineage/hash는 기본 화면에서 숨기되 원문 보존 안내는 유지한다. 기존 CreatorDraft 저장 영수증과 혼용하지 않는다.

열기 후 Flow 제목·진행률·첫 실행 항목이 먼저 보인다. 새로 작성한 Flow를 여는 것만으로 합성 “새 원문에서 N곳 달라짐” 알림을 만들지 않는 방향을 제안한다(`P3K-BP-01`). P3-D 기능은 `사용 안내 → 로컬 원문 비교 연습`처럼 명시적인 검증 진입에서 그대로 조작할 수 있게 둔다. 이 진입의 명칭은 제안이며 구현 시 기존 도움 구조에 맞춘다. 새로운 상시 CTA나 외부 업데이트 서비스를 만들지 않는다.

실제 provenance가 있는 기존 후보와 연습용 `local-fixture` 후보의 표시를 구분한다. 기존 pending 후보를 삭제하거나 자동 해결하지 않는다. 명시 진입 이후 비교·나중에·충돌 해결·적용·Undo·reload의 기존 계약은 그대로 검증한다.

## 5. 개인공간 기간·순서·복구

### 5.1 S5-T: 같은 날짜는 어느 보기에서도 같은 목록

`P3K-V41-01,02,03`의 설계다. 원본과 React의 확인된 기간 규칙을 standalone에 맞춘다. 새로운 “오늘부터 7일” 제품 정책은 만들지 않는다.

| 영역 | 데이터 기준 | 보이는 구조 | 바꾸지 않는 값 |
|---|---|---|---|
| 오늘 | 오늘 날짜 + 지난 미완료 | `지난 미완료`와 오늘 날짜 heading을 분리 | 과거 날짜를 오늘로 자동 이동하지 않음 |
| 주간 | 기준일이 속한 월~일 | 실제 날짜별 heading과 목록 | 다음 주 항목을 현재 주로 당기지 않음 |
| 월간 | 기준일이 속한 달 | 할 일이 있는 날짜 우선, 빈 날짜 펼침/접기, 날짜별 빠른 추가 | 빈 날짜 접기가 항목 삭제/숨김이 아님 |
| 날짜 미정 | 유효 실행 날짜가 없는 항목 | `날짜 미정` 하나의 목록 | 임의 날짜를 채우지 않음 |
| 직접 순서 | `date + 실제 날짜`, `undated`, `overdue + 기준일` | 해당 목록의 `직접 정렬` + `시간순으로 되돌리기` | 개인 Plan 순서·원문 순서·다른 날짜·시간·완료·메모 |

오늘·주간·월간에서 같은 실제 날짜의 순서를 공유한다. 지난 미완료는 별도 목록 문맥이므로 특정 날짜 목록의 직접 순서와 무조건 같다고 가정하지 않는다. 날짜 heading에 날짜가 있으면 행에서는 반복 날짜만 빼고 시간·Flow·폴더 경로를 남긴다. 접근성용 이동 설명은 시각적인 장문 안내와 구분해 보존한다.

standalone의 기존 `orders.today/week/month`를 날짜 key로 조용히 덮어쓰지 않는다. 서로 충돌하는 여러 view 순서 중 어느 것이 마지막 사용자 의도인지 알 수 없을 수 있다. 기존 payload exact bytes를 유지하는 read 호환·새 버전 write·충돌 시 fail-closed의 선택지를 개발 설계에서 비교한다. 손실 없는 변환이 입증되지 않으면 해당 정렬 mutation을 막고 다른 안전한 기능은 유지한다. 이를 핑계로 전체 PoC를 초기화하지 않는다.

### 5.2 S5-M: 이동과 contextual Undo

왼쪽 `이동할 곳`은 `이 목록의 순서 / 실행 날짜 / 정리 폴더`를 구분한다. 오른쪽에는 항목 이름 일부와 48px 손잡이를 볼 수 있는 재정렬 통로를 남긴다. Flow Item에는 독립 폴더 이동을 제시하지 않고 `폴더는 Flow와 함께 이동` 안내를 유지한다.

drag·350ms 길게 누르기·짧은 누르기·`…`·키보드는 같은 목적지와 transition을 사용한다. 현재 위치는 중립 상태이며 성공 안내와 새 Undo를 만들지 않는다. Escape·pointer cancel·영역 밖 놓기·크기 변경 취소는 write 0과 합성 클릭 정리를 유지한다.

일반 이동 성공 후 상태 줄에는 예를 들어 `내일로 옮겼어요. 되돌리기`를 함께 제공한다(`P3K-V41-05`). 설정을 열어야만 복구할 수 있는 상태를 없애되, 기존 설정 Undo를 제거하지 않는다. 영수증이 이미 Undo를 소유한 맥락에는 중복 버튼이나 중복 live announcement를 만들지 않는다.

- Undo는 표시된 성공 transaction과 연결한다. 실패·같은 위치·취소 때문에 직전의 다른 변경을 가리키는 새 Undo가 생기면 안 된다.
- 이동 뒤 대상 행이 사라지면 상태 줄은 같은 viewport 안에 남고, 키보드에서 바로 접근할 수 있어야 한다. 성공 알림이 입력 중인 초점을 강탈하지 않는다.
- 짧은 가로 화면에서는 피드백과 핵심 행동이 서로 가리지 않게 본문 흐름에 배치한다. 하단 고정 overlay를 덧씌워 마지막 행이나 caret을 가리지 않는다.
- 되돌린 후 정확 ref·날짜·순서·선택/스크롤을 복원한다. 기존 Undo snapshot 수명과 저장 계약을 임의 확장하지 않는다.

## 6. Authoring 원본 UX 맞추기

### 6.1 S2-E: 한 편집기, 선택적 도움

React의 같은 source editor를 기준으로 standalone의 core 동등성을 구현하되 편집 엔진 교체를 목표로 하지 않는다. 현재 standalone의 textarea와 결과 Item 검토 경로도 보존해야 할 동작이다. 먼저 문서 소유자·selection·undo owner를 하나로 만들 수 있는 adapter를 설계한 뒤 현재 행 도움과 모드 표시를 연결한다.

| 화면 상태 | 첫 행동·주 행동 | 빈/오류/취소·초점 |
|---|---|---|
| 처음 빈 문서 | 바로 입력 가능. `작성 틀`은 선택적 보조 행동이다. | 예시는 source 밖에서 바로 보이고 입력하면 해당 힌트만 비켜난다. 빈 골격만으로 blocking issue나 canonical Item을 만들지 않는다. |
| 틀 목록 | 여섯 틀의 목적과 짧은 예시를 읽고 선택한다. | browse/cancel/Escape는 원문·selection·undo·storage 변화 0. 원래 `작성 틀`로 복귀한다. |
| 선택한 틀 미리보기 | `빈 틀 넣기`를 주 행동으로 둔다. | 원문이 비었는지 적용 직전 다시 검증. 중간에 입력했다면 차단하고 원문을 보존한다. |
| 삽입 직후 | 같은 편집기에서 미완성 TXT를 바로 수정한다. | 한 번 native Undo로 전체 삽입 제거, Redo exact 복구. 원래 틀 문법에 맞는 첫 편집 위치로 간다. |
| 완성 예시·검증 입력 | 빈 틀과 별도 표시/행동으로 제공한다. | 이미 승인된 31개 corpus·6개 compiled example·6개 scaffold의 bytes와 기능을 보존한다. 이 개수는 기존 자산 inventory이며 이번 재시험 수가 아니다. |
| 기술 정보 | 필요할 때 펼치는 `검증 정보` 안에 compiler/version을 둔다. | source 보호·임시 보관 실패 안내까지 숨기지 않는다. |

`빈칸 힌트`는 전체 Flow 편집의 presentation state다. raw text, canonical parse, clipboard, selection, scroll, undo, 명시 저장 bytes에 들어가지 않는다. 빈 문서 화면을 개선한다고 완성 예시를 자동 입력하지 않는다.

### 6.2 S3-G: 네 그룹 → 속성 → 값

React의 현재 16개 catalog를 삭제하거나 다시 미구현으로 세지 않는다. 최초 chooser를 네 그룹으로 접고, 선택한 그룹의 항목만 펼친다. standalone의 기존 group 선택 구조를 비교 기준으로 사용한다.

1. 현재 항목의 `+`: 정확 대상 제목과 네 그룹만 보여 준다.
2. 그룹 선택: 선택 그룹 이름·속성 목록·뒤로를 보여 준다.
3. 속성 선택: 해당 입력 UI로 전환한다. 장소·링크·숫자·날짜 등 기존 타입/검증을 재사용한다.
4. 적용: K1-A 안전 계약을 통과한 한 번의 명시 원문 변경.

Escape는 값 입력 → 속성 목록 → 그룹 → 원문 순으로 한 단계씩 돌아가고, 어느 취소 단계에서도 원문을 바꾸지 않는다. Tab/Shift+Tab은 native focus 이동으로 유지한다. 날짜/반복 등 종속 메뉴는 지원 계약 안에서만 연다.

원본의 `더보기`에 있던 반복/종료·안내/주의·출처가 현재 여러 그룹으로 재배치된 차이는 별도 mapping 표로 확인한다. catalog 자체의 지원과 그룹 구성 변경의 승인 여부를 분리한다. scoped 승인 근거가 없다면 원래 네 그룹 의미를 복구하고, 사용자의 영구 제품 taxonomy로 새롭게 확정하지 않는다.

모바일에서도 도움 제목·값·취소·적용이 같은 내부 스크롤 영역에서 발견되어야 한다. 844×390에서 CTA만 남고 입력값이 완전히 가려지는 배치를 허용하지 않는다. 데스크톱은 입력 약 40~44%·결과 약 56~60%라는 기존 문법을 활용하고 상시 세 번째 도구 pane은 만들지 않는다.

## 7. 개발1 선택·편집·영수증과 로컬 UI

### 7.1 S1-D: 선택 전에 무엇인지 확인

검색 행은 Flow 제목 아래 실제 출처명 또는 원문 식별에 필요한 짧은 정보와 안전한 원문 링크를 제공한다. 허용 URL이 없으면 링크를 만들어 내지 않고 `원문 링크 없음`처럼 사실대로 표시한다. 운영 key나 내부 origin enum은 출처명이 아니다.

선택 후 요약에는 `원문 보기`와 `내 사본 보기`의 owner를 명확히 표시한다. 공유 원문 preview에는 원문 값만, 내 사본 preview에는 effective 개인 제목·순서·날짜·실행 값을 사용한다. 같은 목적이면 기존 ResultPresenter와 P3-J 완료 기준 renderer를 재사용한다. 서로 다른 owner의 화면을 무조건 하나로 합치지 않는다.

검색 결과 없음은 검색어 수정과 돌아가기만 제공하며 샘플 Flow를 결과처럼 넣지 않는다. source description/criteria가 없으면 빈 상태 규칙을 적용하고 완성 기준을 창작하지 않는다. 선택·preview·보기 전환·뒤로는 storage mutation 0이며 검색어·선택 child·스크롤이 복원되어야 한다.

### 7.2 S6-P: 개인 계획 필드와 변경 영수증

기존 React의 personal-plan capability를 standalone에 맞추는 범위다(`K-D1-02,06`). 원본 필드가 있다는 이유로 모든 origin에 같은 새 편집 필드를 추정하지 않는다.

- Plan: 원본 정보 읽기 → 내 제목 → capability가 있는 개인 구간 제목·Item 순서 → 변경 영향 확인.
- Item: 원본 제목·설명·완료 기준 읽기 → 내 제목·메모 → 계획 날짜 `원본 따르기 / 직접 날짜 / 날짜 미정` → 실행 위치 읽기.
- Item `계획에 반영`은 부모 draft만 바꾼다. Plan 최종 저장 전 persistent write는 0이다.
- 실행 날짜 이동·완료/다시 열기는 기존 실행 행동에서 처리하고 Item 폼 transaction에 몰래 넣지 않는다. Item 독립 폴더 편집도 만들지 않는다.
- 저장 전에는 바뀐 값·대상 수를 보여 준다. 지원되지 않는 포함/제외를 `0개 제외` 고정으로 구현 완료처럼 표현하지 않는다. 현재 전체 반영이면 그 사실만 표시한다.

영수증은 같은 intent의 `저장 중 / 저장됨 / 같은 내용 / 취소 / 실패 / 재시도 / 되돌림`과 before→after, 정확 대상·영향 개수를 표현한다. standalone의 누적 성공 수나 작성 완료 영수증은 Plan 저장 영수증을 대신하지 못한다. 실패는 draft를 보존하고 같은 intent 재시도, 성공은 readback 후 한 번 Undo를 제공한다.

### 7.3 S-LOCAL: 해당 화면을 고칠 때 로컬 위계도 함께 맞추기

`K-D1-07,08`, `P3K-V41-03,04`, `P3K-D2-06`을 마지막 색칠 작업으로 남기지 않는다. 각 기능 묶음에서 수정하는 화면의 위계를 동시에 검증한다.

| 요소 | 로컬 적용 | 보호 대상 |
|---|---|---|
| 주 행동·선택·focus | 승인된 exact-query 청록 token을 명시 소비. disabled/danger는 별도 의미를 보존한다. | 전역 cobalt token, 기본 `/my`, PlatformNav |
| 화면 제목·주 행동 | 한 맥락에서 같은 editor를 여는 중복 entry를 정리한다. | 출처·원문/개인 경계·복구 안내 |
| 날짜·집계 | heading과 같은 날짜 반복, 효용 없는 이중 집계만 정리한다. | 실제 시간·경로·완료 상태·접근성 설명 |
| 내부 기술 정보 | compiler, source ref, hash, shadow 같은 검토 정보는 명시 disclosure/보고서로 옮긴다. | 손실 차단과 오류·보관·source 보호 안내 |

색상은 코드 변수 존재만이 아니라 실제 computed style로 확인한다. 전역과 로컬을 다른 테스트 대상으로 측정한다. 읽기 쉬워 보인다는 주관 평가만으로 대비·초점·작은 화면 통과를 대신하지 않는다.

## 8. 설계 gate: 지금 추정 구현하지 않을 것

이 표는 기존 A0/P3-F 결정을 다시 묻는 표가 아니다. 이미 정해진 소유 영역과 아직 없는 필드 계약을 구별해, 다음 단계에서 무엇을 더 확인해야 하는지 정한다. 현재 감사 목표를 막는 사용자 질문은 아니다.

| 항목 | 이미 결정된 것 | 남은 구체 계약 | 승인 없이 가능한 선행 작업 | 별도 사용자 결정이 필요한 경우 |
|---|---|---|---|---|
| Plan 기준일 | 월 탐색은 보기 상태, 원문 일정은 read-only, 개인 변경은 PoC shadow다. | source anchor capability, 상대 offset 적용 범위, 개인 anchor override, fixed/미정/실행일 보존 및 버전 호환 | month cursor / selected date / source anchor / personal anchor 4값 표, source DTO 조사, 0write 재계산 preview·경계 fixture | 원본/후속 결정을 읽어도 anchor 적용 범위나 기존 사본 처리 의미가 미정이면 대안·영향을 제시한 뒤 선택 요청 |
| Plan 포함·제외 | P3-F에서 PersonalOverlay가 개인 포함 여부를 소유한다. timeline 숨김·삭제와 다르다. | 구체 membership field, 제외된 Item의 표시·복원·개수·날짜·완료 보존, 기존 all-ref guard와 버전 계약 | `포함 / 제외 / 복원 / staged / committed` 상태표, 현재 전체 반영 문구, source·execution 불변 fixture | 원래 UX가 특정 owner/보존 의미를 정하지 않았다면 그 선택만 요청. 개인 overlay 사용 여부는 다시 묻지 않음 |
| 날짜순을 원문에도 적용 | 원문은 명시적으로 편집 가능한 WorkingSource와 immutable SourceSnapshot이 다르다. | 같은 Step 안 Item+속성+하위 체크 block 재정렬, stable binding, revision1/Undo1, selection 복귀 | D2-018 grammar와 현 compiler의 round-trip 조사, explicit preview와 순수 reorder plan 설계 | immutable 사본을 바꾸거나 새 운영 source writer가 필요해지는 안은 중단. 기존 WorkingSource 안의 명시 작업이면 그 범위에서만 진행 |
| 과거 view 순서 호환 | 기존 사용자 PoC payload를 임의 정리하지 않는다. | today/week/month 충돌 순서의 해석, 구버전 read와 새 context write 분리 | exact bytes 보존 read adapter·충돌 fixture·비파괴 fail-closed 설계 | 손실 없이 해석할 수 없는 기존 순서를 자동 선택해야 하는 경우에만 결정 요청 |
| 과거 source 체크/완료 혼합 | 신규 handoff는 source와 실행 완료를 분리한다. | 기존 `done`의 provenance가 없는 payload 해석 | 기존 완료 bytes 보존, 신규 경로만 수정, 구버전 불변 회귀 | 사용자 완료를 지우거나 일괄 변환해야 한다면 별도 승인 없이는 실행하지 않음 |

운영 Calendar writer, 공개 publish, provider sync, migration은 이 gate의 대안으로 넣지 않는다. scoped P2-B/P3-B/P3-D가 구현한 회차·제작자 초안·로컬 원문 비교를 옛 A0 제외 문구만 보고 삭제하거나 새로 중복 구현하지 않는다.

## 9. 모든 화면에 적용할 검증 규칙

각 묶음은 기획·UX/디자인·개발 설계·개발·검증을 한 바퀴 끝내고 다음 묶음으로 간다. 기능을 다 만든 뒤 UX/UI를 마지막에 한 번 확인하는 방식으로 진행하지 않는다.

1. 원본 요구 ID → 후속 대체 범위 → 현재 실패 → 변경한 상태 → 새 실행 증거를 한 행으로 연결한다. 기능·UX·UI·증거 판정은 따로 유지한다.
2. 390×844, 375×812, 844×390, 1024×768, 1440×900에서 해당 묶음의 정상·빈·긴 내용·오류 상태를 확인한다. 필요 시 320px/200% reflow는 추가 검사로 분리한다.
3. 문서 가로 넘침뿐 아니라 내부 textarea/helper/dialog 스크롤, 첫·마지막 행동, caret, 초점, safe area, 48px 이동 행동을 확인한다. 입력 가상 키보드·실제 기기 검사는 자동 viewport 결과로 대신하지 않는다.
4. 키보드 전체 경로, 비드래그 이동, Escape, 취소, 실패·재시도·Undo·reload를 화면과 데이터로 함께 확인한다.
5. `flow:*` 중 PoC prefix 밖의 key/value 전후 byte-for-byte 동일, prefix 밖 setItem/removeItem/clear 호출 0, 운영 writer 호출 0을 검사한다. 기본 `/my`와 gate 오류/corrupt fail-closed 회귀를 포함한다.
6. 현재 실행한 테스트 수·시나리오 수·viewport 수를 각각 집계한다. 옛 합격 수는 현재 테스트 수로 합산하지 않는다.
7. 실제 Android Chrome·iOS Safari·보조기술은 실행하지 않았다면 `NOT_RUN`, 관찰 사용자 수는 0명이다. 이를 다음 구현 목표의 대기·완료 조건으로 두지 않는다.

이 설계의 구체 실행 순서와 다음 목표는 [구현 계획](implementation-plan.md)에 정리했다.
