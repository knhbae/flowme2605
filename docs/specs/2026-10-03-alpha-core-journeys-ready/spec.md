# 핵심 사용 여정 UX 개선·개발계 반영·사용자 시험 준비

2026-10-03. 사용자 요청: “다시 앞에 말한거랑 종합해서 좀 큰 목표를 세워줘봐”.

상태: **P/C/N/F 구현·합성 검증·선별 게시 완료, 공통 CI 보완 중**. 사용자의 “ㄱㄱㄱㄱㄱ”·“승인이라고!”로 구현·검증·소유 후보 선별 commit/push/Draft PR/비공개 CI·개발계 교체를 승인했다. 같은 승인 내용을 다시 요청하지 않는다. 등록 당시 goal의 계획-only 문구보다 이 후속 사용자 승인과 현재 spec을 따른다. 정확 HTTP QA와 두 개발계 교체/복귀는 미완료이며 실제 사용자 관찰 시험은 시작하지 않는다.

## 목표와 제품 방향

v4.1 개인공간·개발1 공개 콘텐츠 활용·개발2 원문 작성을 통합한 알파에서, 세 목적별 대표 경로의 상태와 다음 행동을 명확히 한다. 이미 검증한 수정본의 반영, 좁은 UX 설계·구현·검증, 개선본의 개발계 반영, 1~2명 시험 시작 준비를 한 목표로 관리한다.

- 개인 문서에 계획·할 일·메모를 자유롭게 쓰고, 같은 Item을 기간 화면에서 실행한 뒤 정확한 원문으로 돌아간다. 메모를 자동으로 할 일로 바꾸거나 Flow 제작을 요구하지 않는다.
- 공개 경험·지식을 찾아 선택한 판본을 확인하고, 필요하면 개인 사본으로 실행한다. 원본·개인 사본·기록을 구분한다. 외부 출력만 하고 종료하는 경로도 유지한다.
- 원할 때만 질문·기여를 작성한다. Flow 없는 질문도 지원하고 저장된 요청과 현재 미저장 입력을 구분한다. 공개·게시를 자동 실행하지 않는다.

세 경로는 사용 목적이지 필수 순서나 계정 모드가 아니다. 전체 UX 완성·전체 요구 충족률·제품 출시를 이 목표의 이름으로 선언하지 않는다.

## 요구·피드백을 비교하는 방식

원천은 [직전 요구 대조](../2026-10-02-alpha-ux-comparison-gaps/requirements.md)·[UX 검토](../2026-10-02-alpha-ux-comparison-gaps/ux-review.md)·[Dots 정정](../2026-10-02-alpha-ux-comparison-gaps/dots-review.md)·[UX2 인수](../../content-audit/2026-10-03-flowme-ux2-static-review-followup-ko.md)다. 직전 대조의 26항목을 전체 충족률로 환산하지 않는다.

실행 시 최신 피드백 원문을 다시 읽고 중간 삽입·수정도 대조한다. 각 대상은 `원천/관찰 맥락 → 현행 화면·행동 → 충족/갭/미확인 → 변경 이유 → 후보 화면·행동 → 검증 → 반영 판본 → 잔여`로 연결한다. 사람의 직접 관찰, Dots 시뮬레이션, 정적 발견, 제품 재현, 정책 제안은 구분한다. 폴더 필터로 정정된 누락을 코드 결함으로 되돌리지 않는다.

## 보존할 계약

- 기존 `/my`, 원본 Flow·원문·운영 저장 key/schema는 이번 UX 작업으로 변경하지 않는다. 알파의 현재 승인된 경로·writer·허용 namespace를 유지한다. PoC 전용 쓰기 경계를 일반 운영 writer 호출로 바꾸지 않고 `localStorage.clear()`도 사용하지 않는다.
- 같은 Item·Flow 소속·날짜 출처·등록/기록 identity와 문서↔기간 연결을 유지한다. 폴더 표시/검색 필터를 실제 소속 변경으로 해석하지 않는다.
- actor/초안/대상/expected·CAS·live 거절 proof를 유지한다. 결과 불명은 정확한 원 ID/payload로 확인한다. 원 요청 확인 뒤 추가 입력을 자동 저장·게시하지 않는다.
- 입력·선택·키보드·Escape·취소·Undo/reload·계정 전환 경계를 유지한다. 중복 안내만 줄이고 충돌·권한·보관 위험과 서로 다른 저장 결과는 숨기지 않는다.
- 기존 백업/복원의 진행·닫기·재진입 의미를 보존한다. 발견성 개선을 새 대형 업로드·백업 job 활성화 또는 새 복원 정책으로 확대하지 않는다.
- 합성 QA의 저장 경계·sentinel/public 원본 불변을 실제 계정/DB 전수 불변이나 관찰 사용자 검증으로 확대하지 않는다.

별도 승인된 게시 선행 보안·출처 보완은 위 UX 범위와 구분한다. 공식 의존성 갱신은 기존 `/my`의 화면·행동 호환을 검증하고, 실제 원문과 맞지 않거나 확인되지 않는7개 source-backed 콘텐츠는 기존 보류 계약으로 **새 공급만** 제한한다. 정적 원문·기존 저장 사본·진행 기록·운영 key/value와 schema는 삭제·변경하지 않는다. 따라서 공급 목록의 의도된 차이를 “기존 공개 목록도 byte 동일”이라고 주장하지 않으며, 기존 개인 사본의 읽기 보호와0쓰기 근거를 별도로 남긴다. [출처 처리 근거](../../content-audit/2026-10-03-core-journeys-cp1-source-review.md)와 [소유·해시](prerequisites-manifest.md)를 따른다.

## 권한과 완료선

목표·계획 등록 뒤 사용자의 “ㄱㄱㄱㄱㄱ”로 착수했고 “승인이라고!”로 이번 목표의 소유 후보 선별 commit·push·Draft PR·비공개 CI·앱 교체/복귀 승인을 확인했다. 게시 선행의 보안·출처 검증 해결도 기존 명시 허용 범위에 포함한다. CP1/CP2마다 정확한 소유 파일·head/build·QA를 고정하며 정상 구현의 작은 수정마다 다시 승인받지 않는다. 새 DB/Auth/schema·DNS/Tunnel 설정·실제 계정 쓰기·main merge/Production은 이 승인에 포함하지 않는다.

전체 목표는 대표 연결부의 요구/설계/구현/QA, 권한이 확인된 두 반영 체크포인트, 시험 준비 산출물과 시작 가능 판정을 실제 근거로 마쳤을 때 완료한다. 승인 대기나 실행 환경 제약이 남으면 완료한 단계와 미완료 단계를 나눈다. 시험 준비 문서가 있어도 접속·권한 조건이 부족하면 “시험 시작 가능”이라고 쓰지 않는다. 실제 관찰 시험은 전체 목표 완료 조건이 아니다.

시험 준비 단계의 완료 조건은 실제 시작을 강제하는 것이 아니라 **가능/조건부/불가 판정과 그 근거·잔여 gate·재개 조건을 마련하는 것**이다. 제외된 Auth·새 계정·공개 운영 조건 때문에 조건부/불가인 경우에도 다른 필수 단계가 완료됐으면 이 목표를 닫을 수 있다. 이번 범위의 미해결 결함·QA 또는 CP1/CP2 미완료를 그 방식으로 완료 처리하지 않는다.
