# C: 질문·기여 초안 복구 설계

2026-10-03. UX-N1의 내부 화면·코드 대조다. 기준은 [목표](spec.md), [단계 계획](plan.md), [직전 6상태 범위](../2026-10-02-alpha-ux-comparison-gaps/results.md#다음-ux-개선-범위--초안-복구-화면)다. 새 브라우저·실기기·관찰 사용자 근거는 아직 없다.

현행 Community는 작성 폼 위의 오류/재시도, 폼 제목 옆 저장 상태, 실제 초안 충돌 비교를 따로 보여준다. AlphaWorkspace의 서버 상태·복구 패널·결과 메시지까지 합쳐지면 원 요청 확인과 추가 미저장 입력이 서로 다른 결과라는 점이 흐려진다. 현재 저장 정책이나 CAS를 바꿀 문제는 아니다.

| 상태 | 저장 대상·남은 입력 | 후보 표시와 주 행동 |
| --- | --- | --- |
| 확정 거절 | 해당 요청은 저장되지 않음. 현재 입력 유지 | 폼 제목 아래 한 안내와 `초안 저장 다시 시도`. 저장 상태의 같은 실패 설명은 감산 |
| 재저장 중 | 현재 입력의 저장 진행. 이전 거절 문구 제거 | 폼 제목 옆 `저장 중…`. 거절 재시도 버튼 제거 |
| 성공 | 확인한 현재 초안 전체가 저장됨 | 폼 제목 옆 계정/기기 저장 완료. 이전 오류/재시도 제거 |
| 결과 불명 | 원 요청이 저장됐을 수 있음. 현재 입력 유지 | 폼 안 `원 요청 저장 결과 확인` 의미의 한 안내와 기존 같은 요청 확인 행동. 새 요청/일반 retry를 제시하지 않음 |
| 원 요청 확인·추가 입력 미저장 | 정확한 원 receipt만 확정. 이어 쓴 내용은 미저장 | 원 요청 확인과 남은 입력을 한 안내에 함께 표시. 기존 `입력 보관 후 최신 내용 열기` 행동. 현재 입력 저장 성공으로 승격하지 않음 |
| 실제 초안 충돌 | 다른 초안 변경/삭제와 현재 입력이 다름 | 같은 오류·일반 retry 제거. 최신 초안 비교를 필요할 때 열고 확인 후 내 입력 저장하는 기존 CAS 행동 유지 |

Community는 `resolveDraftSaveRecovery(failedDraft, expected, reason)`가 반환한 표시용 상태·문구·행동만 같은 활성 초안의 실패 origin에 적용한다. 부모가 먼저 확인한 결과는 `draftSaveRecovery`와 대상 초안 ID로 전달하며 활성 초안과 ID가 같을 때만 표시한다. 그래서 자식의 오류 callback보다 먼저 전역 안내가 사라지는 순간에도 복구 행동이 남는다. AlphaWorkspace는 actor·원 명령·expected·live 거절 proof 또는 원 receipt를 검증하며 행동도 기존 controller/보관 동선으로 제공한다. 이 prop은 저장 권한이나 CAS를 만들지 않는다.

정확한 전체 초안 일치만 인정하는 `acceptConfirmedSocialDrafts`는 유지한다. 원 요청 확인 후 추가 입력의 baseline을 자동 채택하거나 새 저장·게시를 실행하지 않는다. 현재 DOM 입력과 cursor를 읽는 기존 port를 보존하고 명시 retry도 그 값을 사용한다. 사진·공개·삭제·권한·보관 실패와 다른 대상의 전역 경고는 같은 저장 결과로 취급하지 않는다.

`flow-ux-review`와 quality-rubric/quality-gate/ux-copy로 감산 검토했다. 같은 실패를 두 번 설명하는 저장 상태와 현재 오류의 일반 retry 경쟁을 제거할 대상으로 삼았다. 입력 보존·결과 불명·실제 충돌·공개 preview·비공개 보관·접근 이름·44px 조작 크기는 복구와 결과 구분에 필요해 유지한다. 낮은 평가 축은 Cognitive Load와 Execution Clarity이며 제품 전체 점수나 사용자 이해도 점수는 만들지 않는다.

표적 회귀는 실제 저장 callback의 큐/성공/오류 origin, 6상태의 실제 JSX, 원 요청 확인 행동과 현재 입력 명시 저장의 구분, 다른 초안/계정·충돌·입력/선택 유지에 둔다. 부모 담당자는 같은 후보 판본의 관련 npm·타입·빌드와 390×844·375×812·844×390·1024×768·1440×900 실제 앱 점검을 수행한다. 세로가 짧은 화면은 안내/행동의 가림과 넘침을 확인하되 긴 본문 전체의 한 화면 표시를 약속하지 않는다.

## 부모 통합과 독립 검토 후 보완

위29개는 최초 C 표적 실행이다. 이후 부모의 confirmed-unsaved proof와 경고 감산을 통합했다. 원 receipt의 정확성만으로 전역 경고를 숨기지 않고, 현재 참여 입력이 원 요청과 다르고 pending/capture가 그 한 초안에 한정되는지 확인한다. 다른 문서·제작·Discovery의 미저장 입력이 있으면 전역 보호 안내를 유지한다. 원본과 같은 참여 입력에 다른 편집기의 pending만 있는 경우도 감산하지 않는다.

unknown/confirmed 버튼은 만들어진 때의 조건을 신뢰하지 않고 클릭 때 같은 live resolver를 다시 확인한다. account owner/actor·receipt 종류/changed/revision·외부 변경·현재 입력 상태가 달라진 오래된 행동은 실행하지 않는다. Community의 독립 사진 오류는 복구 모델이 있어도 표시하며 같은 저장 origin의 반복 오류만 줄인다. 이 보완은 상태 표시의 권한을 좁힌 것으로 저장 baseline·writer·자동 retry 권한을 확장하지 않는다.

부모와 자식의 actual 컴포넌트 검사 Alpha82 + Community30 =112/112 PASS를 확인했다. 독립 읽기 검토의 actual callback/JSX18개 제한 검사에서도 위 경계를 확인했고 세 결함 범위의 치명 잔여를 발견하지 못했다. root의 최종 병합 표적230개에는 이112개가 포함되므로 별도 합산하지 않는다. 실제 HTTP5크기·키보드·IME/AT·관찰 결과는 [QA](qa.md)의 미실행/실행 판정을 따른다.
