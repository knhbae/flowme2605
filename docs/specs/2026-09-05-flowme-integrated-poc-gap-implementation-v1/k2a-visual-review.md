# K2-A 화면 직접 평가

2026-09-05, root가 새 Chromium 캡처 20개를 직접 열어 확인했다. `output/playwright/k2a-current-22/`에서 `74d07` 폴더는 standalone, `780e2` 폴더는 React다. 각각 영수증·실행 화면을 390×844, 375×812, 844×390, 1024×768, 1440×900에서 확인했다. 자동화 화면이지 실제 기기나 관찰 사용자 검증이 아니다.

## 이번 요구의 결과

| 화면 | 확인한 동작·표시 | 이번 판정 |
|---|---|---|
| 양쪽 신규 저장 영수증 / 5개 크기 | 제목·2개 Item·개인공간 열기 행동을 읽고 접근 가능 | 완료 초기값 변경으로 영수증·열기 경로가 깨지지 않음 |
| 양쪽 개인 Flow / 5개 크기 | 사용자 완료 뒤 첫 항목만 체크되고 1/2로 표시, 다른 Item 미완료 | 개인 완료의 정확 대상 유지 |
| 양쪽 원문 보기 / 5개 크기 | 보존된 원문 [x]와 [ ]를 그대로 표시 | 실행 완료와 원문 구획을 확인. 원문 exact 여부는 별도 자동 assertion 근거 |
| React 결과 표 / 5개 크기 | 데이터 상태는 맞지만 status·title이 한 글자씩 길게 감김 | 기능과 별개인 기존 가독성 결함. 전체 UI PASS 아님, K3-C에 연결 |
| standalone 완료 toast / 짧은 가로·결과 화면 | 본문·CSV 영역과 겹치는 배치가 보임. 844 영수증에서는 열기 버튼 오른쪽 테두리와 근접 | K2-C 피드백 배치에서 처리할 잔여. 모든 픽셀 경계가 가리지 않는다고 주장하지 않음 |

자동 `ratio:1`은 요소가 viewport 안에 있는지 확인하고 중심 hit-test는 실제 클릭점을 확인하지만, 모든 텍스트의 가독성이나 요소 전체의 다른 레이어 겹침을 보장하지 않는다. 이 한계를 이번 직접 평가에서 분리했다.

추가로 실제 생성된 로컬 HTML을 새 격리 context에서 844×390으로 열어 직접 작성·저장했다. 열기 버튼의 가로·세로 5%/50%/95% 조합 9점이 모두 해당 버튼에 hit했다. 생성 HTML이 실제 file 경로에서 실행된 보조 검사이며, 통합 E2E 22개나 운영 sentinel 22개 수에 더하지 않는다. 실제 기기 검사도 아니다. 캡처는 `output/poc-gap-implementation/k2a/standalone-receipt-hit-844x390.png`다.

## 후속으로 넘기는 기존 차이

- K2-C: 성공 알림과 Undo의 문맥·배치, toast와 다른 핵심 행동의 겹침.
- K3-C: React Sheet의 최소 열 너비·가로 스크롤 안의 읽기, 기술명·중복 행동·합성 원문 후보의 기본 노출. 전역 token은 변경하지 않는다.
- K3-B/C: 양쪽 영수증의 정보 구획 차이는 해당 receipt/로컬 UI 단계에서 정리한다. 이번 완료 초기값 검증을 영수증 전체 동일성 검증으로 쓰지 않는다.

K2-A의 BP-039/P3K-BP-03은 검사한 신규 handoff와 개인 결과 완료 소유 범위에서 해결했다. 세 원본의 전수 기능·UX·UI 완료로 확대하지 않는다.
