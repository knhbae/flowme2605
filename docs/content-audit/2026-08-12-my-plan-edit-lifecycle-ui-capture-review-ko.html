01 · Existing feedback

새 취향이 아니라,
기존 피드백의 마지막 연결입니다

처음에는 공개 화면의 세대 차이가 보였습니다. 이어서 내 계획을 감사하자 같은 문제는 편집기와 저장 수명주기 뒤편에도 남아 있었습니다.

편집

이동

취소와 browser Back이 서로 다른 단계·위치·초점으로 돌아갔습니다.

수명주기

02 · Representative change

같은 “수정” 버튼이
같은 편집 작업을 엽니다

Flow Map을 대표 사례로 변경 전과 로컬 변경 후를 같은 390 × 844 화면에서 비교했습니다.

Flow Map390px실제 로컬 UI

Before: 눌러도 제자리 · After: 공통 Plan 편집기

변경 전에는 수정 버튼을 눌러도 상세 화면이 그대로였습니다. 변경 후에는 저장 이름, 기준일 capability, 포함 항목과 최종 저장을 가진 공통 편집기가 열립니다.

결과
저장 출처가 UI 세대를 결정하지 않습니다. 지원하지 않는 기준일은 무반응이 아니라 잠금 상태와 이유를 보여줍니다.

04 · Save, cancel, back

항목은 계획에 반영하고,
계획 저장에서 한 번 확정합니다

어느 출처에서 들어와도 같은 단계, 같은 취소 규칙, 같은 복귀점을 사용합니다.

1계획 수정상세의 수정 버튼에서 시작
2항목 수정제목·메모·날짜 편집
3계획에 반영부모 Plan 초안만 갱신
4저장 또는 취소Plan에서 최종 결정
5열었던 곳으로위치·초점을 함께 복귀

추가 검토에서 닫은 변경 사항

초기 연결 이후 정밀 리뷰에서 조합 저장과 복구 경계를 더 확인했습니다.

Map 포함·순서제외 항목 재포함과 순서 변경이 reload 뒤에도 유지됩니다.
기준일 + 항목 변경한 번의 저장에서 날짜·메모와 기준일을 함께 바꿔도 서로 덮지 않습니다.
날짜 재설정고정 날짜 → 날짜 없음 → 원본 날짜 흐름이 이전 값으로 되돌아가지 않습니다.
무변경 저장아무것도 바꾸지 않은 저장이 오류나 불필요한 구조 생성으로 이어지지 않습니다.
원본 보존이전 저장본과 초안의 알 수 없는 필드·identity를 그대로 보존합니다.

05 · Lifecycle

보관하고, 되돌리고,
보관함에서 직접 복구합니다

상세의 “계획 관리”를 단일 진입점으로 삼고, archive 이후 history와 focus까지 끊기지 않게 맞췄습니다.

모바일 목록 Back, archive가 상세 history를 소비하는지, Undo 뒤 활성 목록과 초점으로 돌아오는지, 직접 복구와 48px 터치 영역까지 전용 브라우저 시나리오로 검증했습니다.
