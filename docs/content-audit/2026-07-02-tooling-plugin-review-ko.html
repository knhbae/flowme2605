도구를 더 붙이기보다 작업 축별로 엄격히 골라야 한다

FLOW는 일반 SaaS 제작보다 source-to-action 변환, 모바일 UX 검증, HTML 작업판, 실제 사용 증거, creator/public/My Flow 경계가 중요하다. 그래서 인기 도구를 많이 설치하는 것보다, 각 작업 축에 맞는 최소 도구 세트를 정하고 보안·토큰·문맥 비용을 관리해야 한다.

검토 방식

앞으로 skill/plugin은 인기도가 아니라 FLOW의 현재 병목과 검증 단계에 맞춰 평가한다.

fit first, install later
1

프로젝트 적합도

content → anchor → artifact → export → check → feedback 루프를 강화하는가.

2

현재 단계 적합도

Stage 0을 넓히지 않고 대표 콘텐츠·My Flow·검증을 좁혀주는가.

3

근거와 채택 신호

공식 문서, GitHub activity, 설치 기반, 커뮤니티 신호를 함께 본다.

4

위험 비용

MCP 권한, 토큰 소모, 보안, 데이터 유출, 도구 정의로 인한 context 비용을 본다.

우리 프로젝트에서의 사용 방식

도구별로 언제 켜야 하는지를 정하면 agent 작업 품질이 더 안정된다.

작업 유형 우선 도구 적용 기준 주의점
기획·백로그 HTML workboard, GitHub, FLOW local skills Now/Next/Later/Blocked/Done이 필요한 경우 Markdown만 남기지 말고 HTML 보기 제공
UX/UI 화면 설계 Figma MCP, figma-ux-ui-design, Playwright Home, Flow 찾기, My Flow, Creator 등 화면 경계가 바뀔 때 Figma는 핵심 화면에만 사용, 간단 문서에는 과함
프론트 구현 Build Web Apps, Vercel/Next, shadcn, Playwright 실제 route/component/E2E 변경 새 UI 라이브러리 도입보다 기존 AppClient 구조 존중
콘텐츠 변환 flow-content-conversion, Firecrawl 후보, eval tooling 후보 원문 row가 Step/Item/export로 바뀌는지 검토 자동 ingestion은 source/risk gate 전까지 보류
검증·관측 Playwright, PostHog 후보, Langfuse 후보 브라우저 QA와 실제 usage/eval 데이터가 필요할 때 실사용 검증과 내부 QA를 절대 섞지 않기

권장 적용 순서

바로 설치보다 운영 루프에 붙이는 순서가 중요하다.

1. 현재 도구 사용 규칙 고정

FLOW skills, Playwright, GitHub, Figma, Build Web Apps를 작업 유형별로 언제 쓰는지 AGENTS/harness에 연결한다.

2. Evidence Capture 후보 선정

PostHog 이벤트 스키마와 Langfuse/eval 기준을 먼저 문서화하고, 실제 도입은 v0.2에서 한다.

3. Source ingestion PoC 제한 실행

Firecrawl류 도구는 2~3개 공개 소스에서만 source row 추출 품질을 테스트한다. 자동 공개는 금지한다.
