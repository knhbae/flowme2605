FlowMe 사용자 피드백·제품 방향 종합본
작성 기준: 2026-07-26

이 문서는 지금까지 반복해서 제기한 사용자 피드백과 제품 방향을 한 번에 전달하기 위한 검토 요청서다.
단순 요약이나 부분적인 화면 꾸미기에 그치지 말고, 실제 서비스와 현재 소스·화면을 직접 확인한 뒤 시뮬레이션, 평가, 대안 설계, 구현 우선순위를 제안해 달라.

공개 서비스:
https://flowme2605.vercel.app

GitHub:
https://github.com/knhbae/flowme2605


[1. FlowMe가 해결해야 하는 핵심 문제]

FlowMe는 캘린더, 할 일 앱, 노션을 모두 대체하는 무거운 플래너가 아니다.

원문 URL, 콘텐츠, 메모에서 사용자가 실제로 실행할 부분을 뽑아:

발견 또는 입력
→ 쓸 만한 전체 결과 확인
→ 나에게 필요한 최소 조정
→ My Flow에 저장하거나 외부 도구로 가져가기
→ 날짜에 배치하고 실행
→ 완료·완료 취소·건너뜀·보류
→ 항목 수정·추가·삭제·복구·순서 변경
→ 단계별 메모·의견·회고
→ 전체·선택·현재 범위로 내보내기
→ 다시 쓰기

까지 자연스럽게 이어 주는 portable execution layer여야 한다.

중요한 것은 기능 수가 아니라, 여러 카테고리의 콘텐츠에서 공통 구조를 잡아 사용자가 필요한 부분만 직관적으로 보고 조정하고 실행할 수 있게 하는 것이다.


[2. 전반적인 현재 문제]

1. 긴 설명이 너무 많다.
- 실제 결과보다 “무엇을 저장한다”, “어떻게 쓴다”는 설명이 먼저 보인다.
- 설명 문장으로 구조 문제를 덮지 말고 결과 미리보기, 상태, 버튼 문구, 화면 배치로 이해시켜야 한다.
- 출처, 안전, 권리, 조건처럼 꼭 필요한 설명만 남기고 나머지는 점진적으로 열어야 한다.

2. 화면마다 같은 Flow와 같은 행동의 문법이 다르다.
- Home 카드, Flow 찾기 카드, URL 진입 결과가 서로 다른 상세와 항목 수를 보여 준 사례가 있었다.
- 운동·반복 Flow만 특별한 버튼과 상태 문법을 쓰기도 한다.
- 저장 전, 저장 직후, My Flow, Calendar가 서로 다른 제품처럼 느껴진다.

3. 전체 결과보다 카드·설정·수정 명령이 먼저 보인다.
- 사용자는 저장하기 전에 “무엇이 생기는지” 전체 그림을 먼저 확인해야 한다.
- 저장 후에도 오늘 할 일 몇 개만 보여 주는 것으로 끝나지 말고, 저장된 전체 Flow가 타임라인·체크리스트·표·루틴 등 자연스러운 형태로 확인되어야 한다.

4. 조정 UX가 단순하거나 반대로 지나치게 복잡하다.
- 빼기·더하기만으로는 부족하다.
- 제목, 기준일, 개별 날짜, 날짜 없음, 시간, 메모, 순서, 포함·제외를 자연스럽게 조정할 수 있어야 한다.
- 동시에 모든 설정을 한 화면에 펼쳐 복잡한 편집기를 만들면 안 된다.
- “지금 바꾸려는 것 한 종류”만 문맥적으로 여는 progressive editing이 필요하다.

5. My Flow는 아직 실서비스 수준의 명확한 목적과 구조가 부족하다.
- 목록, 오늘 할 일, 전체 Flow, 다음 항목, 수정, export, 회고, 재사용, 관리 기능이 긴 화면에 섞인다.
- 무엇을 먼저 봐야 하고 어디서 수정해야 하는지 모호하다.
- 저장한 Flow가 많아질수록 찾고 관리하기 어렵다.
- 부분 수정이 아니라 library → focused workspace 구조로 크게 재설계할 가능성도 열어 둬야 한다.

6. Calendar와 날짜 없는 할 일의 관계가 직관적이지 않다.
- 날짜 없는 할 일을 어디서 보고 어떻게 날짜에 배치하는지 찾기 어렵다.
- Calendar에서 날짜 없는 목록이 길게 펼쳐지거나, 특정 Flow 필터가 가로로 길어지는 문제가 있다.
- 날짜 배치, 선택 이동, 전체 이동, 되돌리기 정책을 별도 핵심 UX로 깊게 설계해야 한다.

7. export가 사용자의 실제 목적에 비해 약하고 범위가 불명확하다.
- 항목 하나씩 내보내는 기능만으로는 의미가 작다.
- 전체 Flow, 선택 항목, 현재 항목 범위를 실행 전에 명확히 보여 줘야 한다.
- 이벤트·행·항목 수, 포함 정보, 손실 정보, 결과 위치를 미리 확인하고 완료 receipt를 받아야 한다.


[3. 원하는 표준 사용자 여정]

1. 사용자가 URL, 메모 또는 준비된 Flow를 발견한다.
2. 시스템은 긴 설명 대신 실제 전체 결과를 먼저 보여 준다.
3. 콘텐츠 성격에 맞는 기본 결과 형태 하나를 우선 제안한다.
4. 필요한 경우에만 날짜·빈도·기간·포함 항목 같은 최소 입력을 받는다.
5. 사용자는 저장 전에 결과를 확인하고 필요한 부분을 조정한다.
6. 저장 또는 가져가기를 누르면 무엇이 몇 개 만들어지는지 분명하다.
7. 저장 직후에는 별도 receipt 화면에서 저장된 이름, 항목 수, 날짜 범위, 다음 행동을 확인한다.
8. My Flow에서는 전체 Flow와 다음 행동을 바로 찾을 수 있다.
9. Calendar에서는 날짜 있는 항목을 실행하고 날짜 없는 항목을 쉽게 배치한다.
10. 완료한 일은 쉽게 다시 열 수 있다.
11. 항목을 추가·수정·삭제·복구·재정렬할 수 있다.
12. 단계별 메모와 수정 요청을 남길 수 있다.
13. 전체·선택·현재 범위로 외부 도구에 가져갈 수 있다.
14. 완료된 실행 기록을 보존한 채 새 실행으로 다시 쓸 수 있다.


[4. Home과 Flow 찾기]

검토할 질문:
- Home과 Flow 찾기의 역할이 중복되는가?
- Home을 유지한다면 단순 인기 Flow 목록이 아니라 “사람들이 Flow를 어떻게 활용하는지”를 보여 주는 사용 사례·후기·재사용 장면 중심이 더 적합한가?
- 최근 Flow와 인기 Flow는 Flow 찾기에 두는 편이 나은가?
- Home을 없애거나 진입 라우터로 축소하고 3탭 IA로 가는 편이 더 명확한가?

필수 원칙:
- Home 카드와 Flow 찾기 카드가 같은 canonical Flow를 열면 같은 제목, 원문, 항목 수, 결과 형태, 저장 identity를 사용해야 한다.
- 같은 원문과 같은 사용자 목적을 entry마다 다른 Flow로 저장하면 안 된다.
- 원문 링크는 실제 링크로 동작해야 한다.
- 카드의 “1, 2, Flow 열기” 같은 구조는 더 자연스러운 “더보기” 또는 명시적 전체 보기로 바꿀 수 있다.
- “이사일”, “D-30 일정”, “생활 일정”, “할 일 5개” 같은 배지가 실제 선택에 도움이 되는지 검증한다.
- 사용자 수, 리뷰 수, 자주 쓰는 항목 같은 social proof가 유용한지 prototype에서 비교한다.
- 실제 데이터가 없다면 production에서 가짜 숫자를 사실처럼 노출하지 않는다. fixture 또는 가상 예시는 명확히 표시한다.


[5. Flow 찾기 카드와 상세]

카드에서 우선 검토할 정보:
- Flow 제목
- 신뢰 가능한 원문·제작자
- 사용 목적
- 실제 결과 형태
- 항목 수 또는 기간
- 필요 입력
- 사용자 평가·활용 신호가 실제로 존재한다면 해당 정보

상세 화면 원칙:
- 콘텐츠마다 자연스러운 결과 형태는 달라도 화면 문법은 같아야 한다.
- 결혼, 이사, 운동, 차량 점검이 서로 완전히 다른 앱처럼 보여서는 안 된다.
- 첫 화면에서 실제 전체 결과를 먼저 보여 준다.
- 설정 카드, 결과 탭, 전체 구조 카드가 같은 항목을 반복하지 않는다.
- 한 화면에서 primary action은 하나만 명확하게 보이게 한다.
- 사용자가 선택하지 못하는 비활성 결과 탭은 늘어놓지 않는다.
- 조정 전에는 행마다 수정 버튼을 반복 노출하지 않는다.
- 조정 모드에서는 제목, 날짜, 메모, 포함 여부 등 필요한 종류만 단계적으로 연다.


[6. 다섯 가지 결과 형태]

각 콘텐츠를 무조건 같은 화면으로 만들지 말고 다음 실제 결과 형태를 명확하게 보여 줘야 한다.

1. Calendar·Timeline
- 기준일 역산, 날짜별 일정, 여행·프로젝트 일정

2. Checklist·Todo
- 날짜가 없어도 실행 가능한 확인 목록과 조건형 행동

3. Sheet·Table
- 비교, 수집, 강의 계획, 행 단위 관리

4. Memo·Guide
- 참고 정보, 기록, 결정 근거, 다시 볼 링크

5. Routine·Execution Flow
- 반복 series와 개별 occurrence가 있는 운동·청소·습관

요구:
- Flow 선택 후 다섯 형태를 모두 강제 탭으로 보여 주는 것이 아니다.
- 실제 콘텐츠를 다섯 형태로 각각 변환했을 때의 의미와 손실을 비교할 수 있는 설계·prototype은 필요하다.
- production에서는 자연스러운 primary artifact 1개와 가치 있는 secondary artifact 최대 2개만 노출한다.
- 지원되지 않거나 의미 없는 형태는 숨긴다.
- 같은 콘텐츠에서 어떤 형태가 기본이어야 하는지 근거를 제공한다.


[7. 저장 전 조정]

현재 가장 부족하다고 느끼는 핵심 영역이다.

사용자가 저장 전에 확인하고 조정할 수 있어야 하는 것:
- Flow 제목
- 기준일 또는 종료일
- 전체 날짜 이동
- 선택 항목 날짜 이동
- 개별 항목 날짜 고정
- 날짜 없음 전환
- 항목 포함·제외
- 항목 제목과 상세 메모
- 개인 항목 추가
- 삭제와 즉시 되돌리기
- 순서 변경
- 반복 빈도와 종료 조건

단, 모두 한 화면에 펼치지 않는다.

권장 문법:
- 결과 먼저 보기
- “조정” 진입
- 조정할 종류 선택
- 해당 값만 편집
- 변경 결과 즉시 미리보기
- 저장 또는 취소

source-backed 원문 자체를 개인 수정으로 덮어쓰지 않는다.
원본과 개인 수정본, 실행 상태를 분리한다.


[8. 운동·반복 Flow]

현재 운동 Flow가 다른 Flow와 다른 전용 UI와 용어를 사용해 복잡하게 느껴진다.

검토할 문제:
- 반복 기간이 왜 4주로 고정되는가?
- 주 몇 회, 요일, 시간, 소요 시간, 종료일 또는 회차 수를 더 간단히 조정할 수 있는가?
- “오늘 결과 남기기”, “완료”, “강도 낮춤”, “휴식으로 변경” 같은 전용 상태가 공통 실행 문법과 충돌하는가?
- 원본 운동 영상·공식 안내가 실행 항목인지 참고 자료인지 구분되어 있는가?
- Flow 찾기와 Calendar에서 같은 routine·occurrence를 같은 UI 문법으로 보여 주는가?

권장 방향:
- 초기에는 “월·수·금 · 07:30 · 45분 · 8회” 같은 compact summary를 보여 준다.
- 상세 설정은 조정 sheet에서 필요한 필드만 연다.
- series와 오늘 occurrence를 분리한다.
- 한 회차 완료·재개·건너뜀·보류가 series 전체를 바꾸지 않는다.
- 자료 링크는 실행 항목과 시각적으로 분리한다.
- raw RRULE 같은 기술어를 사용자에게 노출하지 않는다.


[9. 저장 후 receipt와 전체 Flow]

저장 직후에는 단순히 오늘 항목만 보여 주지 않는다.

필수 정보:
- 저장된 Flow 이름
- 전체 포함 항목 수
- 날짜 범위 또는 날짜 없음 상태
- 반복 요약
- 원문
- 기본 실행 위치
- 다음 행동 하나

사용자는 저장 결과가 맞는지 전체 Flow를 바로 확인할 수 있어야 한다.
저장 전 입력과 조정 control이 receipt 화면에 남아 있으면 안 된다.


[10. My Flow]

My Flow는 대대적인 구조 변경 가능성을 열어 두고 검토해야 한다.

핵심 역할:
- 저장한 Flow를 찾는 library
- 선택한 Flow를 실행·수정·관리하는 focused workspace

목록에서 우선 보여 줄 것:
- Flow 제목
- 다음 행동 또는 진행 상태
- 가까운 날짜
- 간단한 진행률
- 명시적인 열기 행동

목록에서 숨기거나 상세로 옮길 것:
- export 전체 matrix
- 보관·삭제
- 긴 설명
- 모든 설정
- 반복되는 완료 control

focused workspace 권장 순서:
1. Flow identity와 상태
2. 다음 행동
3. 전체 계획
4. 날짜별 또는 단계별 묶음
5. 기록 요약
6. 문맥형 조정
7. 가져가기
8. Flow 관리

모바일:
- 긴 카드가 연속되는 한 화면을 피한다.
- 한 화면에서 여러 종류의 primary card가 경쟁하지 않게 한다.
- 같은 날짜의 항목은 묶인 구조로 보이게 한다.
- 완료와 다시 열기를 쉽게 찾게 한다.
- 전역 4탭 navigation과 로컬 workspace navigation이 경쟁하지 않게 한다.

와이드:
- library rail, plan canvas, inspector 역할을 명확히 분리한다.
- 모바일을 단순히 늘인 화면으로 만들지 않는다.

검색:
- Flow가 1개, 5개, 20개, 60개일 때도 쉽게 찾고 열 수 있어야 한다.
- 검색 후 열기, 수정, 완료·재개, export까지 사용자 여정을 검증한다.


[11. 완료·취소·건너뜀·보류]

상태 의미를 분리한다.

- 완료: 이번 실행을 마침
- 다시 열기: 완료를 취소하고 실행 상태로 복귀
- 건너뜀: 이번 occurrence를 실행하지 않음
- 보류: 나중에 결정하거나 실행
- Flow에서 제외: source-backed 항목을 개인 사본에서 숨김
- 항목 삭제: 개인 draft 항목을 삭제

완료 취소는 전체 목록 깊숙한 곳을 찾아 들어가지 않아도 되어야 한다.
행과 상세에 동일 완료 체크를 중복해서 보여 주지 않는다.
반복 Flow의 한 회차 완료가 series 전체 완료로 보이면 안 된다.


[12. 날짜와 이동]

날짜 변경은 개별 입력 하나로 끝나는 문제가 아니다.

반드시 정책과 UX를 함께 설계할 것:
- 전체 기준일 이동
- 상대 일정 재계산
- 사용자가 고정한 개별 날짜 유지
- 선택 항목만 이동
- 단일 항목 날짜 변경
- 날짜 제거
- 날짜 없는 항목을 Calendar에 배치
- 이동 취소와 undo
- 반복 series 전체, 이번 회차만, 이번 회차부터 변경

My Flow 요약, 전체 목록, Calendar, ICS, export가 같은 effective date를 읽어야 한다.
한국 시간 기준 Today와 기본 날짜가 정확해야 한다.


[13. Calendar]

현재 달력 자체는 일부 개선됐지만 다음을 더 검토해야 한다.

- Flow가 많아져도 scope filter가 가로로 길어지지 않게 한다.
- 선택된 Flow 요약과 전체 목록 dialog를 분리한다.
- 특정 Flow만 쉽게 선택해서 볼 수 있게 한다.
- 날짜 없는 항목은 명확한 tray 또는 bottom sheet에서 날짜에 배치한다.
- 날짜 없는 항목을 단순 긴 목록으로 펼치지 않는다.
- 선택한 날짜의 상세는 긴 하단 영역보다 bottom sheet, dialog, inspector 대안을 비교한다.
- 같은 날짜에 여러 Flow가 있으면 grid는 compact summary, agenda는 full detail 역할을 유지한다.
- Calendar와 My Flow의 완료 control 문법을 통일한다.
- 반복 occurrence가 preview, My Flow, Calendar, ICS에서 같은 수와 identity로 보여야 한다.


[14. 항목과 Flow의 CRUD]

항목:
- 추가
- 수정
- 날짜 지정·제거
- 순서 변경
- 삭제
- 즉시 undo
- 새로고침 후 복구

Flow:
- 보관
- 즉시 undo
- 보관함에서 복구
- 보관된 Flow만 영구 삭제
- 영구 삭제 전 삭제 범위, 복구 불가, 원본 보존 여부 확인
- 필요하면 먼저 개인 백업

사용자 동사를 통일한다.

- 실행: 완료 / 다시 열기
- 일정: 날짜 정하기 / 날짜 없애기
- source-backed 구성: Flow에서 제외 / 다시 포함
- 개인 draft 구조: 항목 삭제 / 항목 복구
- 자료: 자료 숨기기 / 다시 보이기
- Flow lifecycle: 보관 / 복구 / 이 기기에서 영구 삭제

개인 메모를 내부 제외 sentinel과 같은 필드에 저장하거나 삭제해서는 안 된다.


[15. export와 외부 활용]

사용자는 FlowMe 안에서만 쓰는 것이 아니라 기존 도구로 가져가야 한다.

필수 범위:
- 전체 Flow
- 선택 항목
- 현재 항목 또는 현재 회차

필수 결과:
- Calendar·ICS
- Checklist·Todo
- Sheet
- Memo
- 필요할 경우 Notion·Obsidian에서 쓸 수 있는 portable output

실행 전에 알려 줄 것:
- 결과 종류
- 범위
- 항목·행·이벤트 수
- 날짜 포함 여부
- 원문 링크 포함 여부
- 개인 메모 포함 여부
- 완료 상태 포함 여부
- 손실되는 정보

실행 후 알려 줄 것:
- 성공 여부
- 실제 생성 수
- 결과 위치
- 다시 시도

“내보내기”라는 모호한 단어만 쓰지 말고 “전체 24개 캘린더 일정 받기”, “선택 5개 체크리스트로 복사”처럼 결과를 예측할 수 있어야 한다.


[16. 단계별 메모·리뷰·수정]

회고는 Flow가 모두 끝난 뒤에만 남기는 기능일 필요가 없다.

검토할 대안:
- 각 항목에 짧은 개인 메모
- 실행 중 불편 사항 또는 수정 제안
- 한 단계 완료 후 간단한 반응
- Flow 전체 완료 후 회고
- 원본 제작자에게 보낼 수정 제안과 개인 메모 분리

화면을 복잡하게 만들지 않도록 기본 실행 화면에는 노출을 최소화하고, 항목 상세 또는 완료 직후에 문맥적으로 제공한다.


[17. 원문·자료·canonical identity]

- 같은 원문, 같은 사용자 목적, 같은 editorial variant는 Home, Flow 찾기, URL lookup, alias에서 같은 canonical Flow로 해석해야 한다.
- source URL 하나만으로 서로 다른 사용자 목적을 강제로 합치지 않는다.
- 24항목과 5항목처럼 콘텐츠 snapshot이 다른 개인 사본은 자동 병합하거나 삭제하지 않는다.
- 기존 완료, 메모, 날짜, run, occurrence, export identity를 보존한다.
- 원문 링크와 참고 자료를 실행 항목과 구분한다.
- 영상·공식 안내가 단순 자료라면 완료할 일처럼 보이지 않게 한다.
- source, personal overlay, execution run, recurrence occurrence, export receipt의 책임을 분리한다.


[18. 시각·반응형 원칙]

- 긴 설명보다 hierarchy와 interaction으로 이해시킨다.
- 카드 안에 카드를 반복하지 않는다.
- 섹션 전체를 떠 있는 카드처럼 만들지 않는다.
- 첫 viewport에서 제품 이름, 실제 결과, 다음 행동이 명확해야 한다.
- 모바일에서 CTA와 bottom navigation이 겹치지 않아야 한다.
- 같은 기능의 label, 위치, 상태 표현을 route마다 통일한다.
- 390px, 1024px, 1440px을 각각 실제로 설계한다.
- 텍스트와 control이 겹치거나 가로 overflow가 없어야 한다.
- 아이콘 버튼에는 accessible name과 tooltip을 제공한다.
- keyboard focus 순서와 dialog·sheet focus return을 검증한다.


[19. 참고할 외부 패턴]

단순 시각 복제가 아니라 아래 문제를 각 서비스가 어떻게 푸는지 비교해 달라.

- Google Calendar, Apple Calendar, Fantastical: 날짜 배치, 다중 캘린더 scope, agenda
- Todoist, Things, TickTick, Microsoft To Do, Apple Reminders: inbox, today, project, 완료 취소, 빠른 수정
- Notion: progressive disclosure, database view, property editing
- Structured, Sunsama, Motion 계열: 오늘 실행과 일정 배치
- 운동 계획 앱: series, 오늘 회차, 소요 시간, 기록
- 여행 계획 앱: 날짜별 묶음, 지도·자료와 실행 항목 분리

각 reference에 대해:
- 빌릴 패턴
- FlowMe에 맞지 않는 패턴
- FlowMe의 portable execution layer 원칙에 맞게 축소할 방법
을 구분한다.


[20. 반드시 비교 설계할 미결정 질문]

1. Home을 유지할지, 진입 라우터로 축소하거나 제거할지
2. Home과 Flow 찾기의 역할을 어떻게 분리할지
3. 저장 전 조정의 깊이와 저장 후 focused editor의 경계
4. My Flow의 Today/전체 구조를 유지할지 다른 grouping이 나은지
5. My Flow를 부분 개선할지 library → focused workspace로 재설계할지
6. Calendar item detail을 inline, bottom sheet, dialog, inspector 중 무엇으로 할지
7. 다섯 결과 형태를 언제 비교해 보여 주고 언제 primary 1개만 노출할지
8. review·사용량·자주 쓰는 항목 정보를 실제 데이터 전 단계에서 어떻게 prototype할지

한 안만 바로 구현하지 말고 최소 A/B/C 대안을 실제 화면 또는 wireframe으로 비교한 뒤 선택 근거를 제시해 달라.

[22. 검토·평가 방식]

각 문제를 다음 중 하나로 분류한다.

- supported: 기능과 도달 경로가 명확함
- hidden: 기능은 있으나 찾기 어려움
- partial: 일부 화면이나 결과에만 반영됨
- missing: 기능 또는 정책 없음
- inconsistent: route·viewport·destination마다 다르게 동작
- blocked: 데이터 또는 제품 결정이 선행되어야 함

각 finding에 포함할 것:
- severity
- route
- viewport
- persona
- 재현 단계
- 기대 결과
- 실제 결과
- 사용자 영향
- 근거 종류
- 제안 대안
- acceptance screenshot 또는 test marker

근거 종류:
- current production interaction
- current source
- current screenshot
- prior design artifact
- external reference pattern
- heuristic simulation
- observed user

자동화, 에이전트 시뮬레이션, screenshot은 실제 사용자 관찰이 아니다.
현재 observed-user count가 0이라면 그대로 표시한다.
현재는 실제 사용자 관찰을 시작하기 전에 구조와 정확성을 충분히 개선하는 단계다.

[25. 절대 피할 것]

- 긴 설명을 추가해 UX 문제를 덮기
- 화면마다 별도 임시 UI와 별도 상태 모델 만들기
- 운동이나 특정 slug만을 위한 특수 규칙
- 실제 데이터가 없는 사용자 수·평점·리뷰를 사실처럼 표시하기

- 날짜 없는 일을 임의 날짜나 월간 반복 일정으로 만들기
- 모든 artifact를 비활성 탭으로 늘어놓기
- 자동 QA를 실제 사용자 검증이라고 표현하기
- UI 문제를 데이터 계약 전면 재작성으로 우회하기
- FlowMe를 캘린더·노션·Todo를 대체하는 무거운 planner로 확장하기


[최종 요청]

위 내용을 단순히 동의하거나 요약하지 말고, 공개 서비스와 최신 소스에서 대표 여정을 직접 재현해 달라.
현재 화면의 문제를 evidence로 확인한 뒤, 필요한 경우 기존 구성을 크게 바꾸는 대안도 포함해 비교 설계해 달라.

특히 다음 세 영역은 부분적인 polish로 끝내지 말고 구조적으로 판단해 달라.

1. 저장 전 전체 결과와 조정 UX
2. My Flow의 library·focused workspace 구조
3. Calendar의 날짜 없는 항목 배치와 반복 occurrence 실행

시뮬레이션과 자동 테스트는 적극적으로 사용하되 실제 사용자 검증과 구분한다.
설계안은 모바일 390px을 우선하고 1024px·1440px까지 확장한다.
최종 결과는 다음 개발자가 단계별로 구현하고 검증할 수 있을 정도로 구체적으로 작성한다.
