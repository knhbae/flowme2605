## 3. 한 문장 목표

제작자가 사용 권한이 있는 원문이나 자신의 메모를 붙여 넣고, 문법을 몰라도 결과를 이해하며, 필요한 부분만 안전하게 고친 뒤, 초안으로 저장하고 다시 열어 관리할 수 있는 Text Authoring 경험을 정의한다. 제작 검토, 공개 미리보기, 저장된 실행, 외부 이동의 역할을 분리하고, 구현팀이 추가 해석 없이 화면·상태·acceptance test를 만들 수 있는 수준까지 구체화한다.

## 4. 현재 확정 원칙

다음 원칙은 반대 근거가 없으면 유지해.

1. 일반 평문 붙여넣기가 기본이고 문법 학습은 선택 사항이다.
2. 내부 SourceRow → Item → Step → Flow 구조는 유지하되 상시 필수 구조 단계는 두지 않는다.
3. 첫 원문 snapshot, 현재 작업 원문, canonical Item, projection, 저장된 개인 Plan, export 파일은 별도 상태다.
4. 원문에 없는 날짜, 출처, 자료, 완료 기준, 행동을 만들지 않는다.
5. 표식 없는 문장은 임의 Todo가 아니라 TXT 원문 메모로 보존한다.
6. root Item은 `- [ ]`, Item 속성은 두 칸 들여쓴 `  - 속성: 값`, 하위 확인 항목은 `  - [ ]`다.
7. Checklist는 Todo의 한 단계 하위이고, Routine은 Item의 반복 속성이다.
8. 날짜가 있는 같은 Item이 Calendar에 나타나며 날짜가 없는 Item은 Todo/TXT에 남는다.
9. Calendar는 실제 달력 UI여야 하고 Todo 카드 목록과 같은 UI를 쓰지 않는다.
10. 반복 Item은 canonical 하나를 유지하고, 각 결과는 같은 bounded occurrence를 보여 준다.
11. Calendar 표시 정렬은 원문을 자동 변경하지 않는다. 원문 정렬은 명시적 적용과 실행 취소가 필요하다.
12. 우측 수정은 안전하게 원문으로 직렬화할 수 있을 때만 한 번에 양쪽에 적용한다. 표·혼합행·주석 등 손실 가능 입력은 fail-closed로 원문 위치를 안내한다.
13. 설명은 항상 펼치지 않고 `?`, 첫 사용 안내, 인라인 오류처럼 필요한 순간에만 노출한다. 필수 오류와 비가역 확인은 숨기지 않는다.
14. AI, 원격 URL 본문 수집, 외부 Calendar/Todo/Excel 쓰기, 게시, P35 통합은 이번 P0 기획의 전제가 아니다.
15. 내부 QA와 브라우저 캡처는 사용자 검증이 아니다. 현재 관찰 사용자 세션은 0이다.

## 5. 가장 먼저 분리할 서비스 단계

현재 제작 데모의 `Calendar / Todo / Sheet / TXT` 네 결과를 서비스 전체의 단일 탭 체계로 간주하지 마. 아래 네 단계의 목적·권한·CTA를 별도 정의해.

1. 제작·검토
   - 원문이 어떻게 해석됐는지 제작자가 비교하고 수정하는 단계
   - Calendar / Todo / Sheet / TXT가 모두 필요한지, 일부가 진단용인지 판단
2. 공개·저장 전 미리보기
   - 다른 사용자가 저장할 계획을 보는 단계
   - 현재 승인 후보는 Text / Todo / Calendar
3. 저장된 내 계획
   - 사용자가 완료·일정·메모를 실제 실행하는 단계
   - 공개 source와 개인 상태를 분리
4. 저장 후 내 도구로 옮기기
   - TXT / VTODO / VEVENT / XLSX 중 하나를 선택해 복사·다운로드하는 단계
   - Excel은 FlowMe 안의 공개 결과 편집기가 아니라 저장된 계획의 표 snapshot 후보

각 단계별로 다음 표를 만들어.

- 사용자
- 사용자의 한 가지 핵심 목적
- 읽기/수정 권한
- 보이는 결과 형식
- primary CTA
- secondary CTA
- 저장되는 상태
- 이전/다음 단계
- 실패·복구
- 현재 근거
- 아직 필요한 결정

## 6. P0 핵심 여정

다음 연속 여정을 실제 서비스로 정의해.

`콘텐츠 목록 → 새 콘텐츠 또는 기존 초안 열기 → 원문 붙여넣기 → 실시간 결과 확인 → 오류·차이 수정 → 필요 시 원문 정렬 → 초안 저장 → 목록에서 재진입 → 준비 완료/등록 seam 확인`

각 단계마다 다음을 적어.

- 사용자의 목적
- 화면에서 가장 먼저 보여야 할 것
- primary action 1개
- 필요한 보조 행동
- 시스템 자동 처리
- 사용자가 판단할 내용
- 저장 데이터와 owner
- 빈 상태, 로딩, 성공, 실패
- 뒤로 가기와 재진입 위치
- 모바일 우선 행동
- acceptance criterion

`준비 완료/등록`은 자동 게시나 production 통합을 뜻하지 않아. 현재는 제작 초안의 상태명과 다음 시스템으로 넘기는 seam만 정의해.

## 7. 정보 구조와 화면

최소한 다음 화면·surface를 정의해.

### A. 콘텐츠 관리 목록

- 빈 목록과 기존 초안 목록
- 제목
- 상태
- 대표 결과 또는 콘텐츠 성격
- 마지막 수정 시각
- 열기
- 복제
- 이름 변경
- 보관 또는 삭제와 복구
- 검색·필터가 P0에 정말 필요한지

Notion이나 프로젝트 관리 도구 전체를 만들지 말고, 제작자가 다시 찾아 수정하기 위한 최소 기능만 남겨.

### B. 제작 화면 상단

- 뒤로 가기
- 콘텐츠 제목
- 자동 복구·미저장·저장 완료 상태
- 예시 불러오기
- 문법 도움말
- 명시적 저장 또는 완료
- 페이지 이탈 경고

QA 예시 총수, 그룹 count, fixture ID, 내부 stage명, 테스트 결과는 제품 화면에서 제거하거나 개발 모드로 분리해.

### C. 원문 입력

- 평문 붙여넣기가 기본임을 한 문장으로 안내
- 선택형 문법 도움말
- 오류 행과 결과 항목 연결
- 현재 선택한 결과에서 원문 위치로 이동
- 긴 문서 탐색
- 원문 정렬 적용과 undo
- source snapshot과 현재 작업본의 차이 확인
- 복구본과 외부 source update의 구분

### D. 결과 영역

- Calendar: 월간 grid, 종일/시간 일정, 같은 날 시간순, 선택일 상세, 반복 회차
- Todo: 부모 Todo, 한 단계 하위 checklist, 날짜, 반복, 완료의 읽기/쓰기 경계
- Sheet: 실제 column header와 행, 반복 회차, copy/export 판단에 필요한 구조
- TXT: 좌측 원문 복제가 아니라 읽고 복사하기 좋은 계층형 결과, 전체 선택·복사·다운로드

결과 버튼은 위치가 움직이지 않게 하고, 활성·비활성·차단의 이유를 같은 자리에서 설명해. 다만 이 네 버튼을 공개 미리보기의 최종 IA로 자동 확정하지 마.

### E. 선택형 항목 검토·수정

- 정상 입력에서는 결과 확인과 저장을 막지 않음
- unresolved 문장과 실제 사용자 조치가 필요한 issue만 정확히 표현
- `예외 처리`라는 QA 분류와 runtime `원문 수정 필요`를 분리
- 결과 행의 수정이 정확한 원문 block으로 연결
- 닫기 후 origin, scroll, focus 복원

## 8. 원문↔결과 동기화 계약

화면을 그리기 전에 아래 상태 전이와 정책을 작성해.

### 권장 기본안

- 첫 붙여넣기 원문은 immutable source snapshot으로 보존
- 현재 작업 원문이 제작 편집의 정본
- 우측 Inspector 제출 한 번이 원문과 canonical 결과를 atomic하게 갱신
- 가능한 속성만 표준 문법 block 안에서 수정
- 주석·일반 문장·알 수 없는 속성·공백·줄바꿈을 보존
- 표/CSV/TSV, 여러 줄 중복 속성, shared Step 속성, merged/generated Item, 복수 링크처럼 손실 가능하면 우측 수정 비활성 또는 원문 행으로 이동
- 변경 한 번은 undo 한 번으로 양쪽 모두 복구
- 외부 source refresh와 사용자의 textarea 타이핑을 같은 충돌 흐름으로 다루지 않음

### 반드시 설계할 상태

- 좌우 일치
- 원문 입력 후 결과 계산 중
- 우측 수정 후 원문·결과 적용 완료
- 안전하게 직렬화할 수 없음
- 결과 표시 정렬과 원문 순서가 다름
- 원문 정렬 적용 전 확인
- 실행 취소 가능
- 자동 복구 완료
- 저장되지 않은 변경
- 명시적 저장 중·성공·실패
- 외부 source 변경 감지
- 실제 충돌
- 오래된 초안 복구
- 파싱 일부 성공
- 특정 결과만 비활성
- 전체 구조 결과 차단, TXT 원문 보존

각 상태마다 사용자 문구, 버튼, disabled 조건, focus 이동, 데이터 owner, undo 가능 여부를 표로 작성해.

## 9. 오류·복구 설계

다음을 누락하지 마.

- 빈 입력
- 표식 없는 일반 문장
- 연도 없는 날짜
- 존재하지 않는 ISO 날짜
- 상대 날짜 문법 오류
- 기준일 누락
- URL 최소 형식 오류
- URL만 있고 본문이 없음
- 반복 시작일 누락
- 반복 종료 횟수·종료일 오류
- 종료 없는 반복
- 지원하지 않는 반복: 매년, n번째 요일, 공휴일 제외, 예외일
- 정의되지 않은 Item 속성
- 깊은 중첩 checklist
- CSV/TSV/Markdown 표 손실 가능성
- 너무 긴 입력
- 저장 실패
- 복구본과 현재 source 충돌
- 이탈 전 미저장 변경
- 삭제·보관 뒤 복구

오류 메시지는 `무엇이 문제인지 → 어느 줄인지 → 무엇을 입력해야 하는지 → 어떤 결과가 막혔는지`를 알려야 해. 원문을 조용히 삭제하거나 임의 날짜·행동을 만들지 마.

## 10. 콘텐츠 시나리오

현재 검증된 30개 사례를 서비스 이름별 목록이 아니라 source shape와 사용자 행동 기준으로 재분류해. 최소한 아래를 원문 → 제작 결과 → 공개 미리보기 → 저장/transfer 관점으로 시뮬레이션해.

### 현재 반드시 유지할 사례

- 일반 평문과 설명 중심 메모
- 부모 Todo와 한 단계 하위 checklist
- 날짜 없는 Todo
- 절대 날짜와 D-Day/상대 날짜
- 같은 날 종일 + 09:00/10:00/16:30 일정
- 매일 + 종료일
- 매주 + 횟수 종료
- 매월 반복
- 종료 없는 반복과 bounded 더보기
- K-MOOC 14주
- LibriVox 38장
- Allblanc 영상 목록
- CSV, TSV, Markdown 표
- 잘못된 날짜
- 잘못된 URL
- URL-only
- 정의되지 않은 속성

### 추가 검토할 사례

1. 팟캐스트·기사·자료 큐
   - 회차명, 재생시간, 수동 자료 URL, 날짜 없음
   - 책·영상과 같은 구조면 새 문법을 만들지 말고 콘텐츠 변형으로 분류
2. 혼합 레시피
   - 재료표는 사실 정보, 조리 단계는 실행 행동
   - 현재 구조가 재료 행까지 Todo로 만들 수 있는 의미 공백을 드러냄
   - 자동 추론으로 숨기지 말고 `정보 / 준비물 / 실행 단계` 역할 구분이 필요한지 결정
3. 긴 장문 문서
   - blockquote, code fence, HTML, 안내·주의와 실행 항목 혼합
4. 실제 상품 비교표
   - quoted comma, multiline cell, URL, 가격·통화는 행동이 아니라 사실값
5. 프로젝트·협업 목록
   - 담당자, dependency, 공유 완료는 현재 구조화되지 않은 P1/P2 공백으로 기록
6. 고급 반복
   - 매년, 둘째 월요일, 공휴일 제외, 개별 예외 회차, timezone 변경은 P1/P2 후보

사례를 많이 추가하는 것이 목표가 아니야. 기존 구조로 충분한 변형, 새 UX만 필요한 경우, 새 문법·데이터 모델이 필요한 실제 공백을 구분해.

## 11. 외부 서비스 패턴 조사

현재 서비스 수준의 관례는 바뀔 수 있으므로 최신 공식 문서와 실제 제품 화면을 확인하고 출처 URL과 확인 날짜를 남겨.

- Google Calendar 또는 Outlook Calendar: 날짜, 시간, 반복, 종료, 예외 회차
- Microsoft To Do 또는 Todoist: 부모 Todo, steps/subtasks, 예정일, 반복
- Notion: 일반 문서와 구조화 속성, sub-item, 편집 surface
- Obsidian 또는 Markdown editor: 평문 우선, 문법 도움말, preview
- Excel 또는 Google Sheets: paste, 행·열, 정렬, 복사, overflow
- 콘텐츠 제작 도구: draft, autosave, saved, version, reopen

서비스별 기능 목록 대신 아래 기준으로 비교해.

- FlowMe가 차용할 최소 패턴
- 그대로 가져오면 복잡해지는 패턴
- 평문 우선 원칙과 충돌하는 패턴
- 모바일에서 유용한 패턴
- 접근성에 필요한 패턴
- FlowMe가 별도로 결정해야 할 사항

외부 UI를 그대로 복제하지 마.

## 12. subtraction review와 문구

첫 wireframe을 만든 뒤 한 번 더 빼는 검토를 수행해.

- 사용자가 다음 행동을 하는 데 필요 없는 카드, 배지, 설명, 숫자 제거
- 같은 내용을 반복하는 제목·도움말 제거
- QA count와 내부 용어 제거
- 기본 상태에서는 평문 입력과 결과만 강조
- 고급 문법, 구조 검토, 원본 비교, export 상세는 progressive disclosure
- `?`는 보조 설명에만 사용
- 오류·손실·비가역 확인은 직접 노출
- 버튼은 결과가 분명한 동사로 작성

다음 문구 묶음을 실제 화면 기준으로 작성해.

- 빈 입력 안내
- 붙여넣기 완료
- 결과 계산 중
- 자동 복구됨
- 저장 중/저장됨/저장 실패
- 원문 수정 필요
- 특정 결과 비활성 이유
- 원문 순서 적용
- 실행 취소
- 우측 수정 적용
- 안전하게 자동 반영할 수 없음
- 이탈 경고
- 보관/삭제 복구

## 13. 모바일·반응형

최소 320, 360, 390, 899, 900, 1024, 1440px를 검토해.

- 모바일에서는 한 번에 가장 중요한 작업 하나만 전면에 둠
- 입력/결과 전환 시 선택 결과·scroll·focus 유지
- 결과 형태 selector 위치 고정
- 키보드 열린 상태에서 저장·결과 전환 도달
- 긴 원문과 Calendar의 중첩 scroll 방지
- sticky footer가 마지막 내용과 버튼을 가리지 않음
- safe area
- 오류 줄로 이동
- bottom sheet/drawer의 닫기·Escape·focus return
- 회전과 재진입 시 현재 단계 복원 정책

현재 `>=900px` 비교 작업대, `<900px` staged 전환을 출발점으로 삼되 900px가 실제 서비스에 맞는지는 wireframe과 작업 기준으로 검토해. Claude 시안의 breakpoint나 pane 수를 이유 없이 채택하지 마.

## 14. 접근성

다음 acceptance를 포함해.

- 키보드만으로 핵심 여정 수행
- 논리적 탭 순서
- 선택 상태를 색상 외 방식으로 표현
- icon-only button의 접근 가능한 이름
- 오류와 source line 연결
- drawer/dialog focus trap과 origin return
- 44px 터치 영역
- 본문·상태 텍스트 대비
- 200% 확대
- screen reader에서 Todo와 하위 checklist 계층 전달
- Calendar 날짜·일정 읽기 순서
- 입력마다 과도하게 알리지 않는 live region
- reduced motion

## 16. 구현 인수인계 수준의 acceptance criteria

최종 기획은 아래를 만족해야 해.

- QA 데모와 실제 제품 IA가 명확히 구분됨
- 제작자 목록 → 작성 → 검토 → 수정 → 저장 → 재진입 여정이 끊기지 않음
- 평문만으로 시작 가능하고 고급 문법은 선택형
- 화면마다 primary action이 하나로 분명함
- Claude는 구조 참고, FlowMe visual system은 유지
- Calendar와 Todo가 다른 목적과 UI를 가짐
- TXT가 좌측 작업 원문과 다른 읽기·복사 목적을 가짐
- Sheet가 제작 검토인지 공개 결과인지 저장 후 transfer인지 역할이 명확함
- 공개 Text/Todo/Calendar와 저장 후 TXT/VTODO/VEVENT/XLSX가 분리됨
- Checklist는 Todo 하위, Routine은 반복 속성
- 우측 수정이 좌측 작업 원문에 반영되는 범위·실패·undo가 정의됨
- 표시 정렬과 원문 재정렬이 구분됨
- source에 없는 정보를 생성하지 않음
- 알 수 없는 정보와 invalid 값이 조용히 사라지지 않음
- 반복의 유한/무한 window와 더보기 규칙이 정의됨
- 모바일에서 마지막 내용과 primary action에 도달 가능
- 키보드와 screen reader 기준이 있음
- recipe처럼 사실·행동이 섞인 입력의 의미 공백을 숨기지 않음
- P0가 협업·프로젝트 관리·AI 자동화·외부 integration으로 팽창하지 않음
- 구현팀이 추가 해석 없이 state와 acceptance test를 만들 수 있음
- internal QA와 observed-user validation이 분리됨

## 17. 사용자 결정 질문

아래 질문은 근거 조사 후 권장안을 붙여 제시해. 답이 없으면 임의로 확정하지 말고 candidate 상태로 남겨.

1. P0 제작자는 개인 제작자와 공식 콘텐츠 제작자 중 누구인가?
2. 콘텐츠 목록을 P0에 포함한다면 최소 관리 행동은 무엇인가?
3. 현재 작업 원문을 편집 정본으로 둘 것인가?
4. 우측에서 수정 가능한 속성은 어디까지인가?
5. 우측 수정은 즉시 원문에 적용할 것인가, 적용 전 차이를 보여줄 것인가?
6. 자동 복구와 명시적 저장을 어떻게 구분할 것인가?
7. `완료`는 제작 준비 완료인가, Flow 등록인가, 공개 게시인가?
8. 제작 검토의 Sheet와 공개/transfer의 Excel을 어떻게 구분할 것인가?
9. 기본 결과는 자동 추천, 마지막 선택 기억, 항상 TXT 중 무엇인가?
10. 상대 날짜 기준일의 범위는 문서, Step, Item 중 어디인가?
11. 혼합 레시피의 사실/행동 구분을 P0에 포함할 것인가?
12. 담당자·dependency·깊은 중첩·고급 반복을 P1/P2로 미뤄도 되는가?
13. 보관·삭제·복제·버전 복원 중 P0 최소 집합은 무엇인가?
14. 모바일에서는 동시 비교보다 빠른 입력/결과 전환을 우선해도 되는가?

## 18. 우선순위 보고 형식

- P0: 실제 제작·저장·재진입에 반드시 필요
- P1: 반복 사용·관리·더 넓은 콘텐츠에 필요
- P2: 협업, 고급 반복, AI, 외부 integration에 필요
- 보류: 문법·데이터 모델 결정이나 사용자 근거가 먼저 필요

각 항목에 `사용자 문제 / 제안 / 포함 이유 / 제외 시 영향 / 의존 결정 / 검증 방법`을 붙여.

## 19. 금지사항

- 앱 코드, parser, test, standalone HTML 수정 금지
- 현재 QA 데모를 완성 제품으로 간주 금지
- QA count와 fixture ID를 제품 UI로 가져오기 금지
- AI 자동 분류를 현재 기능처럼 전제 금지

- Sheet/Excel을 모든 단계의 같은 탭으로 처리 금지
- 협업·Notion·프로젝트 관리 도구 전체로 확장 금지
- 내부 QA를 관찰 사용자 검증으로 표현 금지
- commit, push, PR, merge, deploy, 외부 게시 금지
