ICS가 아니라 Item이
FlowMe 콘텐츠의 최소 실행 단위다

일정, 반복 루틴, 체크리스트, 표·진도, 메모, 의사결정, 근거·주의를 하나의 export 형식에 맞추지 않는다. 동일한 Item을 기준으로 달력·체크리스트·시트·메모를 다시 만들 수 있어야 URL 수집, AI 변환, My Flow, 사용자 수정이 같은 계약을 공유할 수 있다.

독립 상태를 가져야 하면 Item이다.

완료, 기록, 결정, 보류, 일정 조정 중 하나라도 독립적으로 필요하면 Item으로 둔다. Field는 값이고 Memo는 맥락이다. SourceRow는 Item을 뒷받침하는 최소 근거 단위다.

계층: Step은 묶고, Item이 실행한다

기존 source-backed bridge의 Step = FlowItem 의미를 새 backend 계약에 그대로 쓰지 않는다. 새 canonical 계약은 기존 runtime의 실제 구조와 맞춰 FlowSection → Step, FlowItem → Item으로 정리한다.

01
Bundle / Flow Map

연관된 Flow를 발견·발행 관점에서 묶는다. 실행 상태는 소유하지 않는다.

02
Flow

하나의 사용자 job, 하나의 primary source, 하나의 primary natural artifact를 가진다.

03
Step

기간, 단계, 주차, 날짜 묶음, procedure group 또는 source row group이다. schedule의 정본이 아니다.

04
Item

완료·기록·결정·보류가 독립적인 최소 실행 단위다. 안정적인 ID와 직접 SourceRef를 가진다.

05
Field / Memo

Field는 일정·정렬·기록·export에 필요한 값, Memo는 방법·링크·수량·예외·주의·사용자 prompt다.

근거 계층은 실행 계층과 분리

URL 한 줄을 곧바로 Item으로 바꾸지 않는다. 어떤 snapshot의 어떤 source row가 무엇을 뒷받침했는지 추적한다.

Review는 바깥에 둔다.

GAP 01Field가 정본에 없다

기록표·비교표·memo field가 slug별 코드로 붙는다. 새 URL 콘텐츠가 같은 표를 만들려면 데이터 저장이 아니라 코드 배포가 필요하다.

GAP 02itemType이 서로 다른 축을 섞는다

scheduled_task는 시간, log_entry는 행동, memo_evidence는 부가 맥락인데 하나의 primary type 우선순위로 고른다.

GAP 03SourceRow provenance가 없다

Flow-level URL과 detail link는 있지만 Item이 원문의 어떤 행에서 파생됐는지 안정적으로 검증할 수 없다.

GAP 04schedule 의미가 여러 위치에 있다

day_offset, duration_days, date_window, repeat_rule, 개인 date override가 서로 다른 층에 있다.

GAP 05export builder마다 입력이 다르다

전체 Flow ICS, routine ICS, My Flow 단일 Step ICS, text/XLSX가 base·overlay·run state를 같은 방식으로 합성하지 않는다.

GAP 06version 감지가 content hash가 아니다

map version, Step 수, source checked date가 같으면 내용 변경을 놓칠 수 있다. canonical content hash와 stable node diff가 필요하다.

배타적 enum 대신 orthogonal facets

Item은 동시에 일정이 있고, 반복하며, 완료 체크가 가능하고, 기록 Field와 caution Memo를 가질 수 있다. 이 조합을 primary enum 우선순위로 압축하지 않는다.

독립적인 사용자 상태와 stable identity를 가진 실행의 중심이다.

Schedule

absolute, anchor_offset, date_window. 일정이 없으면 ICS를 만들지 않는다.

Recurrence

daily·weekly·monthly, interval, weekdays, count/until, source-defined 여부를 구조화한다.

Intent

act, inspect, decide, record, use_resource.

Completion

check, decision, record. 각각 doneWhen 또는 decision/record Field를 가진다.

Field / Memo

Field는 계산·기록·export 값, Memo는 방법·링크·수량·예외·경고다.

Source / Caution

Item·Field·Memo마다 SourceRef를 붙인다. caution은 check task로 위장하지 않는다.

예: “다음 접종 일정 확인”은 intent=inspect + completion=check + schedule=date_window + 공식 SourceRef + 의료 caution Memo를 동시에 가진다. Calendar, checklist, memo에 나갈 수 있지만 canonical Item은 하나뿐이다.

저장소와 API: content·review·user state를 분리한다

처음부터 Flow/Step/Item을 UI 테이블처럼만 저장하지 않는다. immutable versioned canonical JSON을 보존하면서 stable identity와 조회에 필요한 node index를 함께 둔다.

1. Source layer

sources · source_snapshots · source_rows. 원본 identity와 immutable 추출본.

2. Canonical content

flow_contents · flow_content_versions · flow_nodes와 Flow/Step/Item/Field/Memo index.

3. Conversion / Review

conversion_requests · generation_runs · conversion_proposals · draft_overlays · review_records.

4. User copy / Run

user_flow_copies · user_item_overlays · execution_runs · execution_item_states · version_reviews.

5. Migration provenance

local_import_batches. 어떤 local key가 언제 무엇으로 import됐는지 남겨 rollback과 중복 방지를 지원한다.

상태·버전·사용자 수정 우선순위

한 개의 status로 content lifecycle, generation UX, source acquisition, execution을 섞지 않는다. merge 순서와 각 상태의 owner를 계약에 고정한다.

01ready
02generating
03Aproposal
03Bpartial
03Cfailed
04reviewed
05saved

Effective merge order

  1. pinned immutable content version
  2. reviewed version resolution
  3. UserFlowCopy overlay
  4. ExecutionRun state
  5. occurrence-specific override
  6. unsaved UI buffer · 저장 전 비정본

local

현재 localStorage read/write를 유지한다. canonical adapter와 parity 검증만 추가한다.

shadow-write

local을 authoritative로 유지하면서 server에도 idempotent write한다. import batch provenance를 기록한다.

server-primary

검증 후 server read를 우선한다. feature flag로 local path에 즉시 rollback할 수 있다.

삭제 금지: migration 완료만으로 기존 local key를 자동 삭제하지 않는다. 새 published version도 saved copy를 조용히 덮어쓰지 않는다. removed Item에 개인 상태가 있으면 사용자가 정리할 때까지 retained/orphaned로 보존한다.

Backend 착수 순서와 이번 비범위

DB나 LLM API부터 연결하지 않는다. canonical validator와 projection parity가 먼저다. 그래야 provider나 저장소를 바꿔도 Flow 의미가 유지된다.

계약 고정

TypeScript contract, JSON fixture, runtime validator, hard-fail 규칙을 확정한다.

Fixture 검증

12개 shape의 expected/forbidden projection과 negative gate를 자동 검증한다.

Compatibility adapter

canonical → 현행 FlowBundle을 만들고 count, date window, source, export parity를 비교한다.

내부 canary

July ready-for-internal-canary 5개 bundle, 49 Items부터 shadow 검증한다.

Repository / DB

provider-neutral repository와 immutable version 저장을 feature flag 뒤에 붙인다.

안전한 URL intake

canonical URL, snapshot, source rows, rights/risk를 LLM 이전에 확보한다.

LLM provider adapter

canonical proposal만 생성하고 validator 실패 시 저장·publish하지 않는다.

Review / Projection API

사용자 overlay, 검토, save, My Flow run, ICS/XLSX/text projection을 같은 effective model에 연결한다.
