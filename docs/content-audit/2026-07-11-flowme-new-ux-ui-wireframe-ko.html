1. 설계 원칙

핵심

첫 화면은 “찾기”보다 “바꾸기”

사용자는 이미 본 글, 영상, 공식 안내, 개인 메모를 가져옵니다. Home과 /flows는 catalog 설명보다 입력과 결과 preview를 먼저 보여줘야 합니다.

출력

결과는 FlowMe 안에 갇히지 않는다

캘린더, 체크리스트, Markdown, TSV, ICS처럼 기존 도구로 옮길 수 있는 산출물이 먼저 보이고, My Flow는 그 다음의 계속 실행 공간입니다.

편집

전체 편집기 대신 시작 전 4개만

시작일, 저장 이름, 포함/제외 Step, 내보내기 방식만 먼저 열어줍니다. 원본 Flow와 source는 유지하고 수정은 개인 사본에만 남깁니다.

2. 통합 기능 루프

URL과 메모는 서로 다른 시작점이지만, 사용자가 이해해야 하는 제품 루프는 같습니다: 가져오기, Flow로 정리하기, 가볍게 고치기, 실행하기, 옮기고 다시 쓰기.

1

가져오기

URL 붙여넣기 또는 메모 붙여넣기. Home은 짧은 입력, /flows는 전체 작업대.

2

정리하기

URL은 hit, needs_review, miss, resolved-hit로 나누고 메모는 초안 후보와 확인 필요 줄로 나눕니다.

3

고치기

시작 전 패널에서 시작일, 저장 이름, 포함 Step, 내보내기만 조정합니다.

4

실행하기

개인 사본은 My Flow Today에 들어오고, 날짜가 있는 Step만 Calendar agenda에 보입니다.

5

옮기기

Step detail에서 Markdown, 체크리스트, ICS, TSV를 현재 개인 사본 기준으로 다시 생성합니다.

5. 이번에 빠졌던 기능 전체 지도

기존 W01~W08은 “URL 또는 메모를 넣고 실행한다”는 가장 짧은 경로만 보여줬습니다. 실제로 논의한 제품은 그보다 넓습니다. 아래 5개 묶음이 하나의 서비스이며, 일반 사용자는 앞의 4개만 보고 공급·검수 기능은 뒤에서 조용히 받쳐주는 구조입니다.

A. 가져오기

이미 가진 것을 넣기

  • 블로그·유튜브·공식 안내 URL 붙여넣기
  • 메모장·Obsidian 계획 붙여넣기
  • 공유 링크 /f로 바로 진입
  • 추천 콘텐츠·제작자 채널에서 발견
  • 최근 입력과 최근 실행 이어서 보기
B. 찾기·정리

AI보다 먼저 재사용

  • canonical URL로 기존 Flow 조회
  • hit·복수 hit·needs_review·miss 분기
  • 관련 기존 Flow 추천
  • miss URL을 제작 요청으로 보관
  • 메모를 비공개 초안으로 구조화
  • 출처·주의·실행 가능 여부 분리
C. 내 상황 맞춤

얇게 고치고 시작

  • 그대로 시작 / 조금 고쳐 시작
  • 저장 이름·시작일·포함 항목·출력 선택
  • 기간·강도·반복 프리셋은 2차 옵션
  • 원본은 유지, My Flow에 개인 사본 저장
  • 구조 변경은 별도 fork 초안으로 승격
D. 실행·재조정

매일 돌아오는 실행 공간

  • My Flow Today와 전체 보관함 분리
  • 개인 사본 설정 다시 조정
  • 제외 항목 분리·다시 포함
  • Calendar에서 Flow별 색·라벨·같은 날 그룹
  • Step 상세의 체크·메모·근거
  • 원본 업데이트에도 개인 상태 보존
E. 옮기기·확산

FlowMe 밖에서도 쓰기

  • Markdown·체크리스트·ICS·TSV
  • 콘텐츠에 맞는 출력 순서 자동 추천
  • 공개 공유 링크와 저장 전 미리보기
  • 개인 초안 → 검수 → 공유 Flow
  • 원문 작성자·커뮤니티 adoption 루프
  • 후보 handoff·수동 등록·source QA
현재 기반 이미 앱과 문서에 있는 것

URL 조회, 후보 저장·재조회, 개인 사본, 설정 조정, My Flow, Calendar, Step export, source-backed 등록 QA.

P0 화면화 다음 구현 후보

Home 통합 입력, 상태별 결과 위계, Today 깊이 축소, Calendar Flow 구분, 목적지별 export sheet.

P1 확장 사용 패턴 확인 후

메모 초안 편집, 복수 hit 비교, 기간·강도·반복 프리셋, fork, 공개 공유 전 검수.

보류·운영 일반 화면과 분리

AI 자동 생성, 계정·서버 동기화, 직접 API 연동, 관리자 승인, 대량 등록은 지금 첫 화면에 노출하지 않습니다.

6. 상태 전이와 “누가 무엇을 소유하는가”

이 제품에서 가장 헷갈리기 쉬운 지점은 원본 콘텐츠, 재사용 가능한 Flow, 내 개인 사본, 오늘의 실행 상태가 섞이는 것입니다. 화면마다 이 다섯 층을 분리하면 “원본을 고친 건지”, “내 것만 바뀐 건지”, “파일에 무엇이 나가는지”가 명확해집니다.

입력 URL·메모·공유

사용자가 가진 자료를 넣거나 이미 공유된 계획을 엽니다.

판정 먼저 찾기

기존 결과, 검토 필요, 아직 없음, 메모 초안을 구분합니다.

확인 결과 미리보기

일정·체크·문서 결과와 첫 행동을 저장 전에 봅니다.

개인화 내 사본 만들기

이름·시작일·포함 항목·목적지만 내 사본에 저장합니다.

실행 Today·Calendar

오늘 할 일, 날짜 있는 일정, 상세 체크와 메모를 실행합니다.

재사용 내보내기·공유

내 사본 기준 파일을 받고, 필요하면 fork·공유로 확장합니다.

1 원문 Source

URL, 작성자, 원문 근거. 사용자가 고쳐 쓰지 않으며 항상 추적 가능하게 남깁니다.

2 공용 Flow

원문에서 만든 재사용 구조. canonical 조회의 hit 대상이며 품질·민감도 정책을 가집니다.

3 개인 사본

내 이름, 시작일, 포함·제외 선택, 출력 방식. 공용 Flow 업데이트가 덮어쓰지 않습니다.

4 실행 상태

완료, 미룸, 메모, 로컬 체크. 원본이나 공용 Flow와 독립적으로 누적됩니다.

5 출력 Artifact

Markdown, 체크리스트, ICS, TSV. 생성 시점의 개인 사본과 실행 문맥을 반영합니다.

내부 상태 사용자에게 보이는 말 주 행동 허용 금지·보류

9. UI 동작·반응형·측정 규칙

모바일

한 화면, 한 행동

첫 viewport에는 입력 또는 실행 항목 하나와 주 버튼 하나만 둡니다.

export와 설정은 bottom sheet 또는 접힌 영역으로 열고, 하단 4탭 위에 겹치지 않습니다.

Calendar는 월 grid보다 선택 날짜 agenda를 먼저 읽게 하며 같은 날 항목은 Flow별로 묶습니다.

데스크톱

입력·결과·상태 3열

왼쪽은 4탭 탐색, 중앙은 현재 작업, 오른쪽은 출처·상태·미리보기만 담당합니다.

폭이 좁아지면 상태 rail을 중앙 아래로 내리고, 입력과 결과의 읽는 순서를 유지합니다.

creator·운영 화면은 일반 앱 shell과 시각적으로 구분하고 noindex·secondary 진입을 유지합니다.

상태·오류

기다림과 실패도 설계

URL 확인 중에는 “기존 준비를 먼저 찾는 중”과 취소를 보여주고 AI 생성처럼 표현하지 않습니다.

복사·파일 생성 실패 시 입력과 개인 설정을 보존하고 같은 버튼에서 다시 시도하게 합니다.

localStorage가 비워지면 서버 저장처럼 오해하지 않게 이 기기 저장임을 설정에서 설명합니다.

접근성

색만으로 구분하지 않기

hit·검토 필요·아직 없음은 아이콘, 제목, 설명을 함께 사용합니다.

포함·제외는 실제 checkbox label로 만들고 44px 터치 영역과 키보드 초점을 제공합니다.

동적 결과, 복사 성공, 설정 적용은 화면 읽기 도구가 알 수 있는 상태 메시지로 전달합니다.

카피

내부 모델 대신 결과

canonical, sourceTrace, Step, Item, handoff는 일반 화면에서 숨깁니다.

“내보내기”보다 “캘린더 파일 받기”, “Obsidian용 Markdown 복사”처럼 결과를 씁니다.

민감 영역은 조언을 만들지 않고 공식 출처 확인·중단·문의 결정을 분리합니다.

측정

기능보다 루프를 계측

입력 제출 → hit 재사용 → 개인화 → 저장/파일 → 첫 완료 → 재방문을 하나의 funnel로 봅니다.

miss는 요청 저장률, 재조회율, resolved 후 시작률을 보고 공급 우선순위에 연결합니다.

AI 비용은 호출 수가 아니라 “재사용으로 피한 호출”과 사용자가 선택한 재생성 비율로 관리합니다.

첫 검증 이벤트

intake_submitted → lookup_resolved → personal_copy_saved 또는 artifact_exported → first_step_checked → returned_to_execute.

아직 성공이라고 부르지 않을 것

화면이 완성되거나 자동 테스트가 통과해도 사용자 가치가 검증된 것은 아닙니다. URL 5건, 메모 5건 정도의 관찰 세션에서 첫 행동·출력 사용·재방문을 따로 확인해야 합니다.

10. vertical 확장 표면

여행, 식단, 운동, 학습, 행정, 가전 관리는 별도 앱처럼 기능을 늘리기보다 같은 루프 안에서 입력/산출물/기록 표면만 다르게 보여주는 방식이 맞습니다.

여행

준비 Map

준비물, 출국 절차, 일정표를 child Flow로 분리하고, 날짜 있는 항목만 Calendar로 보냅니다.

식단

장보기와 기록

메뉴 글이나 메모를 장보기 체크리스트와 식사 기록 TSV로 나눕니다. 영양 조언은 생성하지 않습니다.

운동

영상 루틴

영상 URL을 일정, 세트 체크, 회고 메모로 나눕니다. 자세나 건강 조언은 원문 추적 밖에서 만들지 않습니다.

행정·세무

증빙 중심

공식 출처, 기한, 제출물, 완료 기준을 분리합니다. 해석이나 판단은 사용자가 원문에서 확인하게 둡니다.

11. 눈검토 포인트

처음 10초

Home에서 “URL이나 메모를 넣으면 일정/체크/문서가 나온다”가 즉시 보이는가?

상태 구분

hit, miss, needs_review, 후보 저장, resolved-hit이 기능명보다 행동 차이로 이해되는가?

수정 부담

시작 전 수정이 전체 편집기처럼 무겁지 않고, 시작일/저장 이름/Step 포함/내보내기만 충분히 보이는가?

실행 공간

My Flow는 inventory가 아니라 오늘 실행할 Top 3부터 보이는가?

일정 공간

Calendar는 날짜 있는 Step만 agenda-first로 보여주고, 날짜 없는 체크는 My Flow에 남기는가?

외부 도구

Obsidian, 메모장, todo, calendar 사용자에게 Markdown/체크리스트/ICS/TSV가 자연스러운가?

후보 재방문

실행 불가 상태를 저장하되 Flow처럼 오해시키지 않고, resolved 후 정상 시작으로 자연스럽게 복귀하는가?

개인 사본 소유권

원본, 공용 Flow, 내 설정, 완료 상태, 내보낸 파일이 서로 다른 층이라는 점이 조용히 이해되는가?

업데이트 무결성

원본이 바뀌어도 저장 이름·시작일·포함/제외·완료·메모가 보존된다는 확신이 드는가?

공유 진입 경계

/f는 저장 전 가벼운 공유 shell이고, 저장 이후에만 4탭 실행 앱으로 들어간다는 전환이 자연스러운가?

편집 깊이

작은 실행 수정과 구조를 바꾸는 fork가 분리되어, 일반 사용자가 제작자 편집기에 끌려 들어가지 않는가?

운영 분리

sourceTrace, canonical, QA-pass 같은 운영 언어와 creator/studio가 일반 사용자 첫 화면에서 보이지 않는가?

구현 순서 제안

P0 · 첫 사용

Home 통합 입력 → /flows hit/miss 결과 → 시작 전 수정까지 한 번에 연결합니다.

P0 · 반복 실행

My Flow Today depth를 줄이고 Calendar에 Flow 색·라벨·같은 날 그룹을 붙인 뒤 export sheet를 정리합니다.

P1 · 재사용

메모 초안 확인, 복수 hit 비교, 후보 resolved 재방문, 원본 업데이트 비교를 같은 상태 시스템으로 묶습니다.

P2 · 확산

fork, 공유 전 검수, creator adoption과 vertical별 고급 옵션을 검증된 사용 패턴 위에 올립니다.

화면은 그렸지만 P0 구현에서 제외

  • AI 자동 생성은 비용·출처 gate가 정리된 뒤 명시적 fallback으로만 엽니다.
  • 계정/서버 저장, Google Calendar/Notion/Obsidian API 직접 연동은 제외했습니다.
  • W18~W20의 fork·공유·creator는 방향 검토용이며 전체 편집기와 버전 관리 구현을 뜻하지 않습니다.
  • W22 수동 등록 QA는 내부 운영 화면이며 일반 사용자 서비스 IA에 넣지 않습니다.
  • 실제 사용자 검증을 주장하지 않습니다. 현재 산출물은 디자인 검토용입니다.

가장 먼저 눈으로 볼 6장면

1. W01 → W02

내 URL을 넣는 이유와 hit의 결과 가치가 10초 안에 이어지는지 봅니다.

2. W10 → W11

miss를 실패가 아니라 재방문 가능한 공급 요청으로 이해하는지 봅니다.

3. W05 → W14

시작 전 수정과 실행 중 재조정이 같은 모델로 느껴지는지 봅니다.

4. W06 → W07

My Flow가 오늘의 행동, Calendar가 날짜의 행동으로 명확히 나뉘는지 봅니다.

5. W08 → W16

Step 실행과 외부 도구 이동이 경쟁하지 않고 필요할 때만 열리는지 봅니다.

6. W18 → W22

개인 수정, 공개 공유, 운영 등록의 책임 경계가 섞이지 않는지 봅니다.
