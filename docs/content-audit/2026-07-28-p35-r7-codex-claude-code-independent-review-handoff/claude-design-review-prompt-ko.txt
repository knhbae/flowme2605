2. 제품 방향
======================================================================

FlowMe는 무거운 planner가 아니라 portable execution layer다.

외부 URL 또는 개인 메모
→ 실제 결과 미리보기
→ 필요한 값만 최소 조정
→ FlowMe에 저장하거나 익숙한 도구로 가져가기
→ 실행·완료·다시 열기
→ 수정·기록·재사용

현재 제안된 전역 진입:
- Flow 찾기
- 캘린더
- 내 Flow

콘텐츠별 자연스러운 결과:
- Calendar
- Checklist
- Routine
- Sheet
- Memo

다섯 결과를 고정 탭으로 모두 노출하지 않는다. primary artifact 1개와 필요한
secondary artifact 최대 2개만 제안한다.

======================================================================
3. 반드시 평가할 문제
======================================================================

1. public preview와 저장 후 개인 workspace가 같은 Flow처럼 보이는가.
2. 날짜 묶음 화면을 public row와 비슷한 anatomy로 만들고 checkbox를 오른쪽에
   두는 편이 더 자연스러운가.
3. 저장 직후 Today 중간 화면이 필요한가, 아니면 저장한 전체 Flow와 첫 실행
   묶음을 바로 보여줘야 하는가.
4. Calendar형 Flow의 다음 할 일은 같은 날짜의 미완료 항목을 묶어야 하는가.
5. 저장 전 제목·상세·날짜 조정의 깊이가 충분한가.
6. 저장 전 실제 결과에서 FlowMe 저장과 외부 가져가기를 예측할 수 있는가.
7. 완료 후 항목이 사라질 때만 즉시 되돌리기를 보여주는 것이 나은가.
8. Calendar·Checklist·Routine·Sheet·Memo의 첫 실행 단위가 설명 없이 이해되는가.
9. 기록 영역이 완료 history·메모·회고를 혼합하지 않는가.
10. 60개 Flow에서도 My Flow가 스캔 가능하고 focused workspace가 명확한가.

======================================================================
4. 검토 방식
======================================================================

390x844, 1024x768, 1440x900을 구분한다.

다섯 콘텐츠 형태마다 다음 세 상태를 비교한다.

Session 1:
public 실제 결과와 저장 전 조정

Session 2:
외부 가져가기 전 범위·개수·형식 preflight

Session 3:
저장한 개인 Flow의 첫 실행 단위와 전체 계획

다음 reference pattern을 화면 복제가 아니라 adopt / adapt / reject로 비교한다.

- Todoist / Things: Today와 project, contextual item detail
- Google Calendar: month/day hierarchy와 event detail
- Notion: database row와 page detail
- Wanderlog: 날짜별 itinerary grouping
- Strava / Nike Training: series, current session, history 분리

긴 설명을 추가해 구조 문제를 가리지 않는다.
가짜 사용자 수, 평점, 리뷰를 제안하지 않는다.

======================================================================
5. 결과 형식
======================================================================

1. severity 순 findings
2. 전체 verdict
   - retain
   - bounded_revision
   - structural_reopen
   - block_publish
3. 위 10개 질문별 판정
   - supported
   - partly_supported
   - rejected
   - needs_observation
4. 다섯 형태 x 세 session scorecard
5. 390px current / proposed wireframe
6. 1024px current / proposed wireframe
7. 1440px 60-Flow library 개선안
8. public row와 saved row의 공통 component anatomy
9. keep / change / remove / defer
10. 권장 다음 개발 순서와 첫 bounded slice
11. 실제 사용자에게만 확인할 질문

finding에는 route 또는 screenshot, viewport, 기대/실제, 사용자 영향, 제안을
포함한다.

자동화, screenshot, heuristic simulation은 실제 사용자 검증이 아니다.
현재 observed-user count는 0이다.
