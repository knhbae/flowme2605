FlowMe URL-first P0 2026-07-05 CEO + 개발 핸드오프

Canary 12 전략을 이제 구현 가능한 slice와 QA scorecard로 잠근다

결론은 단순하다. 현재 `/flows` URL-first 구현은 P0 골격과 3개 hit 검증까지는 로컬에서 확인되어 있다. 다음 단계는 새 전략을 더 쓰는 일이 아니라, Canary 12를 기준으로 P0-now 4개 hit, P1-review 6개 lock, P2-hold 2개 hold를 코드와 테스트가 같은 언어로 말하게 만드는 일이다.

이번 목표의 결정

구현은 한 번에 크게 열지 않는다. Canary registry → P0-now 4 hit → Export Pack v1 → ledger/export/save QA 순서의 4개 implementation slice로 자른다. Home redesign, OAuth/API, AI-first 생성, full editor, fake usage는 제외한다.

1. 현재 구현이 이미 증명한 것

새로 과장하지 않고, 기존 QA 문서와 코드에서 확인 가능한 사실만 CEO 보고용으로 압축했다.

evidence-based

URL lookup 골격

/flows 상단 URL 입력, hit / needs_review / miss, AI disabled, start panel, custom start가 존재한다.

저장과 Markdown

hit 상태에서 날짜와 export mode를 선택하고 My Flow local persistence 및 Markdown 다운로드까지 QA 기록이 있다.

숨은 lab route

/flow-lab/url-first-p0는 preview용 실험 route로 남아 있고 public nav에는 노출하지 않는 방향이다.

3. P0 구현 흐름도

개발자가 따라갈 실제 loop다. 중요한 것은 hit 성공뿐 아니라 locked 상태가 절대 export/save로 새지 않는 것이다.

loop contract
URL 입력 /flows의 URL field. memo나 AI prompt가 첫 화면의 주인공이 되지 않는다.
Canary registry 판정 canonical URL, source type, canary status, risk, default artifact를 결정한다.
상태별 UI hit는 start/export, review는 preview+lock, hold/miss는 대체 CTA만 노출한다.
Export Pack v1 `.ics`, Markdown, checklist 중 허용된 output만 실제 동작으로 제공한다.
Ledger 저장 화면, export file, My Flow 저장 기록에 같은 source/trust 필드가 남는다.

4. Implementation slices

각 slice는 독립 QA가 가능해야 한다. Slice A가 없으면 이후 구현은 case-by-case 예외 처리로 커진다.

handoff

Slice A. Canary registry 고정 먼저

  • lib/flow/url-first-lookup.ts 또는 신규 url-first-canaries.ts에 12개 canary 정책을 모은다.
  • 각 canary에 P0-now, P1-review, P2-hold, source type, risk, default artifact, lock reason을 둔다.
  • unit test는 12개 전부가 기대 status와 export/save permission을 반환하는지 본다.

Slice B. P0-now 4개 hit 완성 core

  • 이사, 차량구매, 예방접종, 에어컨필터 4개를 실제 hit로 고정한다.
  • 각 hit가 자연스럽게 Calendar / checklist / Markdown / My Flow로 이어지는 기본값을 가진다.
  • 민감 canary는 hit여도 caution과 ledger가 export/save에 반드시 포함되어야 한다.

Slice C. Export Pack v1 실동작 gap

  • 현재 Markdown은 QA 기록이 있으나 lookup 결과의 `.ics`, checklist 실동작은 별도 구현이 필요하다.
  • my-flow-step-export.ts, export.ts의 기존 builder를 재사용해 새 export 엔진을 만들지 않는다.
  • P1/P2/needs_review/miss에서는 export 버튼이 disabled이고 reason이 명확해야 한다.

Slice D. Ledger와 lock QA 완료 조건

  • source URL, canonical URL, source title/type/status, checked date, version, risk, caution, export date를 한 contract로 정한다.
  • 화면 badge, export footer/description, My Flow persistence가 같은 값을 공유해야 한다.
  • P1-review 6개와 P2-hold 2개는 save/export가 막히는 E2E를 반드시 갖는다.

7. 이번 slice 제외 범위

제외 범위가 선명해야 P0가 작아진다. 아래 항목은 결정적으로 유혹적이지만 이번 구현 완료 조건이 아니다.

out of scope

Home redesign

URL-first는 `/flows` product loop에서 검증한다. Home 개편은 다음 문제다.

Direct API/OAuth

Google Calendar, Notion, Todoist direct 연결은 P1/P2다. P0는 portable export다.

AI-first generation

현재 방향은 lookup-first다. miss에서도 AI 생성이 곧바로 앞에 나오면 안 된다.

Full editor

custom start는 허용하되 source-backed 원본 편집기까지 열지 않는다.

Live crawler

P0는 검증된 source-backed map과 canary registry로 충분하다.

Fake usage

usage count, 인기 척도, 검증되지 않은 성공 지표는 넣지 않는다.

8. 결정해야 할 항목

이 네 가지가 승인되면 다음 목표는 실제 구현 sprint로 전환할 수 있다.

decision
  • P0-now 4개 확정: 이사, 차량구매, 예방접종, 에어컨필터를 첫 구현 acceptance로 승인할지 결정한다.
  • Export Pack v1 실동작 기준: lookup hit 결과에서 `.ics`, Markdown, checklist를 모두 실제 output으로 제공할지 승인한다.
  • Ledger 최소 필드: 10개 필드를 화면/export/save 공통 contract로 잠글지 결정한다.
  • P1/P2 잠금 원칙: review/hold canary는 preview와 reason만 제공하고 save/export를 막는 기준을 승인한다.

근거 문서와 구현 링크

이 보고서는 아래 파일을 근거로 만든 핸드오프다. 새 구현 완료를 주장하려면 여기에 QA 파일이나 실제 명령 결과가 추가되어야 한다.
