Experience Map Platform Study

FlowMe는 작은 Flow 변환기에서 경험맵 플랫폼으로 넘어가야 한다

지금까지는 원컨텐츠 하나가 작은 실행 Flow가 될 수 있는지 확인했다. 다음 질문은 제작자가 본인의 경험을 큰 지도처럼 구조화하고, 그 안에 작은 Flow들을 연결해 사용자에게 제공할 수 있는지다.

creator map child Flow save full or partial calendar/checklist/sheet/memo

결론 먼저

1

작은 Flow 단위는 1차 충분

날짜형, 체크리스트형, 표형, 루틴형, 버킷형은 대강 성립한다. 더 파면 개별 polish다.

2

플랫폼 검증은 아직

제작자가 큰 경험 구조를 만들고 하위 Flow를 연결하는 레이어는 아직 검증하지 않았다.

3

다음 PoC는 경험맵

자격증 취득처럼 단계, 기간, 과목, 루틴, 체크리스트가 섞인 큰 경험맵 1개를 만든다.

핵심 판단: FlowMe가 Notion 템플릿 마켓, Coursera 코스, roadmap.sh 로드맵, Asana 프로젝트 템플릿 중 하나를 그대로 복사하면 안 된다. FlowMe의 단위는 실행 가능한 child Flow가 붙은 경험맵이어야 한다.

참고 플랫폼 구조 스터디

플랫폼 유형 대표 서비스 구조 FlowMe에 유용한 점 그대로 따라 하면 안 되는 점
로드맵/경로 roadmap.sh 역할/스킬 기반 로드맵, 가이드, 프로젝트, 학습 여정 큰 목표를 노드와 경로로 보여주는 방식이 경험맵에 가깝다. 실행 artifact가 약하면 “읽는 지도”로 끝난다. FlowMe는 각 노드가 캘린더/체크리스트/표로 실행되어야 한다.
코스/자격 프로그램 Coursera, Coursera Specializations Guided Project, Course, Specialization, Professional Certificate처럼 단위가 계층화된다. 큰 목표 아래 여러 코스/프로젝트를 묶는 구조는 자격증/커리어 경험맵에 참고할 만하다. FlowMe는 강의 플랫폼이 아니다. 영상 수강/퀴즈/성적 관리보다 사용자의 기존 도구로 옮겨 실행하는 것이 우선이다.
창작자 교육 비즈니스 Teachable, Kajabi, Maven 코스, 코칭, 디지털 다운로드, 멤버십, 커뮤니티, 코호트 프로그램 제작자가 자신의 전문성을 상품화하고, 여러 제품 유형을 묶어 제공하는 구조를 참고할 수 있다. 초기 FlowMe가 결제/멤버십/코칭 플랫폼으로 보이면 Stage 0이 무거워진다.
템플릿 마켓 Notion Marketplace, Notion creator profile, Figma Community 제작자 프로필, 템플릿/파일/플러그인 발행, 갤러리 탐색, 복제/설치 제작자 프로필과 발행된 실행 자산 목록은 FlowMe creator page에 유용하다. FlowMe는 템플릿을 복제하는 데서 끝나면 약하다. 복제 후 사용자의 날짜/상황에 맞게 실행되어야 한다.
프로젝트 템플릿 Asana Templates, Asana Task Templates, Trello Templates 프로젝트, 섹션, 작업, 마일스톤, 카드, 체크리스트를 복제해 반복 업무를 표준화한다. 큰 경험맵 안에 마일스톤과 하위 실행 카드가 들어가는 구조에 참고할 수 있다. FlowMe가 프로젝트 관리 툴처럼 보이면 입력/관리 부담이 커진다. 사용자는 전체 업무 관리보다 실행 artifact를 원한다.
문서/지식 계층 GitBook Collections, GitBook Spaces Collection, Space, Page로 지식을 계층화하고 권한/공개 범위를 관리한다. 제작자 경험맵의 단계/섹션/자료 구조를 정리할 때 유용하다. 문서 계층만 있으면 실행성이 약하다. FlowMe는 각 페이지가 실행 Flow로 연결되어야 한다.
지도/루트 탐색 AllTrails, AllTrails Lists 트레일 가이드, 지도, 리스트, 저장, 내 루트 생성/편집 경험맵을 “길 찾기”처럼 이해시키는 데 좋다. 전체 루트와 개별 구간을 동시에 보여준다. GPS/지도 같은 시각적 은유를 과하게 쓰면 실행 항목보다 탐색 UI가 커질 수 있다.

이 구조에서 작은 Flow는 여전히 중요하다. 다만 작은 Flow가 흩어져 있는 것이 아니라, 제작자가 만든 큰 경험 구조 안에서 의미를 가져야 플랫폼처럼 보인다.

제안안 4개

추천 1순위map-first

안 A. 경험맵 우선 플랫폼

제작자가 먼저 큰 경험맵을 만들고, 단계마다 하위 Flow를 붙인다. 사용자는 전체 맵을 저장하거나 특정 단계/Flow만 저장한다.

  • 예: 정보처리기사 합격까지, 초등 입학 준비 전체, 첫 해외여행 준비
  • 사용자 화면: 전체 지도, 현재 단계, 이번 주 할 일, 하위 Flow 저장
  • 제작자 화면: 단계 추가, 하위 Flow 연결, 원문 자료 연결, 사용자 미리보기

FlowMe 적합도 높음

creator shelf

안 B. 제작자 컬렉션/선반

제작자 프로필 아래에 독립 Flow들을 카테고리별로 모은다. Notion/Figma Community처럼 탐색과 복제가 쉽다.

  • 예: “A 강사의 자격증 Flow 모음”, “B 부모의 초등 준비 Flow 모음”
  • 장점: 빠르게 만들 수 있고 현재 작은 Flow 자산을 재사용 가능
  • 한계: 플랫폼/경험맵 느낌은 약하다. 단순 템플릿 갤러리로 보일 수 있다.
program-first

안 C. 프로그램/코호트형 Flow

4주, 8주, D-30처럼 기간이 정해진 프로그램을 만든다. Maven/Coursera식 프로그램 구조를 가볍게 가져온다.

  • 예: 4주 홈트, 30일 글쓰기, 시험 D-30 준비
  • 장점: 기간/반복/진행률이 명확하다.
  • 한계: 강의 플랫폼이나 챌린지 앱처럼 보일 수 있다. 모든 경험에 맞지는 않는다.
나중AI compiler

안 D. 원문 묶음에서 경험맵 자동 생성

제작자가 여러 URL, 영상, 문서를 넣으면 FlowMe가 경험맵 초안을 만든다. 강력하지만 지금 바로 하기엔 위험하다.

  • 장점: FlowMe의 자동화 가치가 가장 강하게 보인다.
  • 위험: 여러 출처가 섞이면서 source fidelity가 깨지기 쉽다.
  • 전제: 안 A의 수동/반자동 경험맵 구조가 먼저 검증되어야 한다.

추천 방향

바로 다음 PoC는 안 A: 경험맵 우선 플랫폼이 맞다. 이유는 작고 독립적인 Flow를 더 만드는 것보다, 제작자 플랫폼으로 보이는지 판단하는 데 더 직접적이기 때문이다.

제작자 화면에서 확인할 것

  • 큰 경험 목표를 만들 수 있는가?
  • 단계를 추가하고 순서를 조정할 수 있는가?
  • 단계 안에 하위 Flow를 붙일 수 있는가?
  • 각 Flow가 원문 1개와 자연 artifact를 유지하는가?
  • 발행 전 사용자 화면을 예측할 수 있는가?

사용자 화면에서 확인할 것

  • 전체 지도를 5초 안에 이해하는가?
  • 전체 저장과 일부 저장의 차이를 아는가?
  • 오늘/이번 주 할 일이 보이는가?
  • 하위 Flow를 열면 캘린더/체크리스트/표가 실행 가능한가?
  • 경험맵이 단순 링크 모음처럼 보이지 않는가?

이번 단계의 산출물 제안

  1. 경험맵 사용자 화면 HTML: 전체 지도, 단계, child Flow, 전체 저장/부분 저장, 오늘/이번 주 실행.
  2. 제작자 화면 HTML: 맵 생성, 단계 추가, 하위 Flow 연결, 원문 연결, 사용자 미리보기.
  3. 기획 리포트: 작은 Flow와 경험맵의 차이, 필요한 데이터 구조, Stage 0 범위, 하지 말아야 할 것.

이 PoC에서는 로그인, 결제, 마켓플레이스, 커뮤니티, 자동 URL 수집을 만들지 않는다. 목적은 “큰 경험맵 안에 작은 Flow가 붙을 때 FlowMe가 플랫폼처럼 보이는가”를 보는 것이다.
