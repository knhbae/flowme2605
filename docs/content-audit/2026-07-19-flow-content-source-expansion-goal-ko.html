“그럴듯한 3단계 Flow”를 만들어내는 것보다 올바르게 멈추는 능력이 backend 품질이다.

ICS나 checklist는 최소 데이터 단위가 아니라 같은 Item의 목적지별 projection이다

이미 정한 변환 gate

하나의 원문 → 하나의 사용자 일 → 하나의 자연 결과물 → 최소 실행 UI. 원문이 뒷받침하지 않으면 구조를 크게 만들지 않는다.

이미 정한 사용자 가치

원문을 다시 읽고 수동으로 Calendar·Todo·Memo·Sheet에 옮기는 비용을 줄이되, 사용자의 기존 도구를 대체하지 않는다.

이번에 추가할 연결

targetCondition, 플랫폼 역할, 제공자 유형, 반응 지표, 접근·권리·지역·위험, 변환 상태를 후보마다 붙인다.

근거: Flow 콘텐츠 계약 v1, canonical data model, source-to-Flow conversion gate, 플랫폼·버티컬 전략, P0 24 예시 원장.

넓힐 것

학습·커리어, 집·생활, 식사, 건강 행동, 취미·만들기, 중장년 지원과 반복·자료 큐·단계 성장.

분리할 것

원문 호스트 / 제공자 발굴 / 배포 / 실행 목적지 / benchmark, 그리고 개별 반응 / 제공자 규모.

그대로 둘 것

원문 충실도, Item 최소 단위, 자연 결과물, 권리·지역·위험 gate, 실제 사용자 검증 경계.

최근 육아 wedge는 여전히 가설이다. 이번 확장에서는 육아를 버리는 것이 아니라 여행·학습·생활·커리어·취미 등에서 같은 행동 조건이 반복되는지 비교한다.

플랫폼 범위플랫폼 이름보다 이번 후보에서 맡는 역할을 먼저 본다

모든 플랫폼을 URL fetch 대상으로 보면 backend 범위가 잘못 커진다

1. source_host

실제 원문 행이 공개되어 있는 곳.

오늘의집 · Maily · K-MOOC · GitHub

fetch/extract 후 Flow 또는 hold를 판정한다.

2. provider_discovery

권리자·제공자를 찾는 곳.

숨고 · 여행에미치다 · Gumroad

자동 수집보다 제휴·creator file 흐름을 설계한다.

3. distribution

사용자가 콘텐츠를 발견하는 곳.

YouTube · Pinterest · Careerly

가능하면 연결된 원 출처로 이동한다.

4. execution_destination

Flow를 가져가 실제로 쓰는 곳.

Calendar · Todoist · Notion · Sheets

ICS·Markdown·CSV 같은 projection을 만든다.

5. benchmark / hold

수요와 UX는 강하지만 직접 가져오면 안 되는 곳.

roadmap.sh · Medium · Pinterest data

정확한 hold가 제품 품질이다.

YouTube는 두 얼굴

공개 metadata·통계 API는 후보 발굴에 쓰고, 영상·자막·제작자 경험의 변환은 권리와 제공 방식이 필요하다.

Notion도 두 얼굴

템플릿 평점은 수요 신호지만 실제 DB 행은 사용자 OAuth·페이지 공유 또는 제작자 파일이 있어야 읽는다.

인기 목록의 역할

Pinterest·Medium·Substack ranking은 원문을 고르는 discovery layer이지 파생 콘텐츠 생성 허가가 아니다.

한국 신규 후보반응·구조·공식성·제공자 역할을 섞지 않고 비교

우선 deep set 후보는 “인기 글 + 공식 실행 원문 + 제공자 lead”를 함께 담는다

36 후보의 역할

포트폴리오 공백과 플랫폼·접근 상태를 넓게 비교한다. 이 단계에서 상세 Flow를 모두 만들지 않는다.

12 원문의 역할

실제 원문 snapshot과 SourceRow를 기준으로 “쓸 만한 Flow가 나오는가”를 사람이 직접 판단한다.
