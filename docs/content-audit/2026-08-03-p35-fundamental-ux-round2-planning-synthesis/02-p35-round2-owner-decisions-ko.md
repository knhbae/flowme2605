## 무엇을 근본적으로 바꾸려는가

지금은 공개 화면과 `내 Flow` 양쪽에 수정·저장·내보내기가 반복되어, 사용자가 “지금 바꾸는 것이 원본인지 내 사본인지”, “어디에서 실제로 보내는지”를 알기 어렵다.

다음 구조로 단순화하려 한다.

1. 공개 화면에서는 내용을 이해하고, 결과를 미리 보고, 저장 전 조정한다.
2. 저장하면 방금 저장한 계획 상세로 바로 간다.
3. `내 Flow`에서는 저장한 계획을 수정하고 실행하며 실제 결과를 다시 만든다.
4. 결과 형식은 항상 다섯 개를 보여주지 않고, 이 계획에서 실제로 만들 수 있는 것만 먼저 보여준다.
5. 도움 문장은 줄이되, 중복·삭제·외부 전송처럼 중요한 영향은 숨기지 않는다.

## Codex와 Claude가 같은 의견인 부분

- 문제의 중심은 버튼 하나가 아니라 **상태와 행동의 주인이 불명확한 것**이다.
- `내 Flow`는 저장한 계획을 찾고 다시 쓰는 장소여야 한다.
- 공개와 저장본 편집은 같은 구조를 쓰되, 공개의 `변경 반영`과 저장본의 `저장`은 구분해야 한다.
- 모든 콘텐츠에 고정 다섯 형식을 보여주면 안 된다.
- 도움 문장을 줄이되 중요한 경고를 아이콘 안에만 숨기면 안 된다.
- 저장 후에는 방금 저장한 계획과 다음 행동이 바로 이어져야 한다.
- 현재 자료는 내부 시뮬레이션·정적 검토이며 실제 사용자 관찰은 0명이다.

## 서로 다른 의견과 권장안

| 쟁점 | Codex 쪽 강조 | Claude 쪽 강조 | 권장안 |

## 승인된 Owner 결정 — B/B/B

### Q1. 저장 없는 빠른 내보내기를 일부 남길까?

**권장: 제한적으로 남긴다.**

- 남기는 경우: 사용자가 아무것도 수정하지 않았고, 계정 연결이나 전송 이력이 필요 없는 로컬 파일/복사 결과만 허용한다.
- 화면에는 `FlowMe에 저장되지 않음`과 `지금 저장`을 항상 함께 보여준다.
- 범위 선택, 재생성, 중복 경고, 전송 기록은 저장한 계획에서만 제공한다.
- 이 조건을 충족하지 못하면 먼저 저장하게 한다.

선택:

- [ ] A. 모든 내보내기는 먼저 저장해야 한다.
- [x] B. 위 조건의 제한적 빠른 내보내기를 남긴다. **(승인)**

결정 메모: `2026-08-04 Q1-B 승인. clean·eligible·local file/copy일 때만 one-shot으로 허용하며 계정 연결·이력·재시도·원격 전송은 제외한다.`

### Q2. 일반 `내 Flow` 진입을 저장 계획 중심으로 바꿀까?

**권장: 바꾼다.**

- 첫 화면 골격은 항상 `오늘 요약(있을 때만) → 최근 저장 → 저장한 계획` 순서다.
- 저장 직후에는 방금 저장한 계획 상세로 바로 간다.
- 계획이 0개면 `계획 찾기`, 1개면 바로 실행할 항목, 20개면 검색과 최소 상태 필터를 보여준다.
- 문제가 생기면 기존 P35 방식으로 되돌릴 수 있는 전환 장치를 둔다.

이 선택은 현재 P35의 일반 `/my` 첫 화면 결정을 명시적으로 바꾸는 것이다.

선택:

- [ ] A. 현재 Today 중심 일반 진입을 유지한다.
- [x] B. 안정적인 저장 계획 중심으로 바꾼다. **(승인)**

결정 메모: `2026-08-04 Q2-B 승인. 일반 /my는 저장 계획 library shell을 유지하고 Today는 있을 때만 compact 파생 요약으로 둔다. 저장 직후에는 선택 계획 상세로 직접 이동한다.`

### Q3. 핵심 화면의 `Flow`를 `계획`으로 단계 전환할까?

**권장: 단계적으로 바꾼다.**

- 1차: `Flow 찾기→계획 찾기`, `내 Flow→내 계획`, `Flow 조정→계획 수정`.
- FLOW 브랜드, URL, 내부 데이터 이름은 그대로 둔다.
- 다음 단계는 실제 사용자 관찰에서 `계획`이 내용을 더 잘 설명하는지 확인한 뒤 결정한다.

선택:

- [ ] A. 현재 `Flow` 표현을 유지하고 보조 설명만 더한다.
- [x] B. 핵심 화면부터 `계획`으로 단계 전환한다. **(승인)**

결정 메모: `2026-08-04 Q3-B 승인. 사용자-facing navigation·CTA·editor title부터 계획을 적용하고 FLOW 브랜드·URL·내부 type/storage 이름은 유지한다.`

## 답을 받으면 자동으로 정해지는 것

아래 항목은 추가 owner 질문으로 남기지 않는다.

- 공개와 저장본은 같은 editor family를 쓰고, 공개는 `변경 반영`, 저장본은 `저장`을 사용한다.
- `완료`는 Item의 실제 실행 완료에만 사용한다.
- 결과는 `주 결과 1개 + 바로 가능한 보조 결과 최대 2개 + 조건부/불가 이유` 순서로 보여준다.
- Flow Map 3칸 grid는 없애되 선택 수 같은 필수 값은 한 줄로 남긴다.
- 저장 후 별도 receipt 화면 대신 선택 계획 상세에 저장 배너를 둔다.
- 중요한 안전·중복·비가역 영향은 항상 화면에 직접 보인다.

## 구현 후 Owner가 직접 볼 것

기능 목록을 확인하기보다 아래 여덟 과업을 직접 해 본다.

1. 공개 계획을 열었을 때 무엇을 먼저 할 수 있는지 한눈에 말할 수 있는가?
2. 날짜 없는 계획에서 빈 캘린더가 먼저 나오지 않는가?
3. 계획을 수정하고 닫으려 할 때 변경을 버리는지 분명한가?
4. 저장 직후 방금 저장한 계획과 항목 수, 되돌리기를 바로 찾을 수 있는가?
5. `내 Flow`에 계획이 0개·1개·5개·20개일 때 첫 행동이 하나로 읽히는가?
6. Item의 `완료`와 계획 편집의 `저장`을 혼동하지 않는가?
7. 내 도구로 옮기기 전에 범위·형식·항목 수·중복 위험을 알 수 있는가?
8. 오류·뒤로가기·중복 클릭 후에도 수정 내용과 저장본이 안전한가?

이 확인은 owner acceptance다. 실제 사용자 이해도는 별도의 관찰 세션에서 판단하고 사용자 수를 실제 값으로 기록한다.
