시뮬레이션

대표 사용자 흐름

상황 사용자 행동 v10 데이터 관점 판단
이사 D-30 Flow를 저장한 사용자 오늘 탭에서 `이삿짐센터·입주청소 예약`을 누르고 업체명/견적을 메모한다. Step은 `FlowItem`, 업체명/견적은 memo. 별도 vendor form이 필요하지 않다.
중1 수학 목차를 저장한 학부모/학생 지도 탭에서 `정수와 유리수`를 열고 `양수와 음수`를 완료 표시한다. FlowItem으로 표현 가능하지만, UX 의미는 `progress row`다. item type gap을 남긴다.
영유아 검진·접종 일정을 저장한 보호자 날짜가 다가오면 검진 기간과 원문 링크를 확인하고 병원 질문만 메모한다. 공식 일정은 source/detail, 질문은 memo. 의료 판단 UI를 만들 필요는 없다.
여권 재발급을 준비하는 사용자 사진 파일 기준을 확인하고 정부24 신청 날짜를 캘린더에서 본다. Process Flow지만 일부 Step은 dated reminder가 될 수 있다. 기존 `scheduled_task` 파생으로 충분하다.

Rubric

FLOW 품질 관점 평가

항목 점수 근거
User Need Fit 4 v9에서 실제 사용 상황이 있는 소스만 남겼다. 다만 Stage 0 실제 사용자 행동은 아직 없다.
Execution Clarity 4 Step title, 날짜, completion, memo가 분리되어 있다.
Content Fidelity 4 원문 구조가 있는 fixture만 사용했다. 제외된 카테고리는 다시 source model이 필요하다.
Portability 3 개념은 명확하지만 실제 `FlowBundle` adapter와 ICS/text export 테스트는 아직 없다.
Cognitive Load 4 사용자 화면은 v8/v9 수준을 유지한다. 데이터 설명은 별도 내부 문서로 분리했다.
Source/Safety 4 영유아/전세는 source link를 보존하고 판단/보증 문구를 피했다.

문제 분류

Blocking/High는 없지만 구현 전 gap은 있다

등급 문제 처리
Blocking 없음 v9 구조가 현재 제품 모델과 완전히 충돌하지는 않는다. 기존 `FlowItem` 계약으로 먼저 adapter를 만든다.
High 후보 진도형/학습형 Flow가 `check_task`로만 보이면 의미가 약해질 수 있다. `progress_step` 필요성을 별도 결정으로 남기고, 중1 수학 adapter에서 확인한다.
Medium Flow Map persistence가 아직 최종 schema로 고정되지 않았다. 지금은 그룹 관계로 두고, creator/public map 구현 때 확정한다.
Medium ICS description에 Item과 memo hint가 충분히 들어가는지 실제 export 테스트가 필요하다. 다음 코드 slice에서 export snapshot을 추가한다.

다음 단계

이제 코드로 들어간다면 이 순서가 맞다

  1. v9 fixture 중 2개만 먼저 `FlowBundle`으로 옮긴다: 이사 D-30, 중1 수학 목차.
  2. 이사는 timeline/calendar export가 잘 되는지 본다.
  3. 중1 수학은 progress row가 기존 item type으로 충분한지 본다.
  4. 충분하면 실제 `/my?demo=...` fixture에 넣고, 부족하면 `progress_step`을 설계한다.
  5. 이후 영유아 검진/접종을 넣어 source/risk 경계가 My Flow에서 유지되는지 본다.
