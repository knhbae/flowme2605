# P35 모바일 Production 기획 세션 브리프

## 이 세션에서 만들 결과

최근 모바일 Production에서 확인된 문제를 바로 수정하는 대신, 다음 구현에서 공통으로 지킬 UX 구조와 UI 변형 기준을 결정합니다.

핵심 질문은 네 가지입니다.

1. Flow별 화면 차이가 데이터 차이에 따른 정상적인 변형인지, 콘텐츠별 예외가 쌓인 결과인지
2. `Flow 찾기 → 확인·조정 → 저장 → 실행 → 가져가기` 과정에서 겹치거나 끊기는 단계가 무엇인지
3. 모든 Flow가 공유할 화면 규칙과 콘텐츠 유형에 따라 달라질 부분의 경계가 무엇인지
4. MVP에서 지금 없애거나 합칠 것과 이후로 미룰 것을 어떻게 나눌지

결과물은 완성된 리디자인 시안이 아니라, 기획자와 구현 에이전트가 같은 기준으로 후속 작업을 시작할 수 있는 결정 문서여야 합니다.

## 검토 범위

포함:

- 모바일 Production
- Flow 찾기 목록과 공개 Flow 미리보기
- Flow 전체 조정과 Item 개별 수정
- 내 Flow로 저장, 저장 완료, Flow 가져가기
- My Flow의 `할 일 / Flow`, Step·Item 상세, 메모와 일정
- 원문 링크, 출처와 주의 정보
- 공통 데이터·렌더링 구조와 콘텐츠별 변형 정책

제외:

- Text-to-Flow
- 데스크톱 최적화
- 신규 콘텐츠 제작
- 외부 사용자 관찰
- 제품 코드 수정과 배포
- 계정, 클라우드 동기화, 협업, OAuth, AI 생성 기능
- 브랜드, 색상, 타이포그래피 전면 개편

이번 검토자는 제품 소유자, Codex, Claude Design입니다. 자동화나 화면 검토를 사용자 관찰로 부르지 않습니다.

## 문제를 다루는 규칙

각 쟁점은 아래 세 층으로 나눕니다.

- 관찰: 화면이나 코드에서 직접 확인한 사실
- 가설: 그 현상이 생긴 원인에 대한 추정
- 결정 질문: 다음 기획에서 명시적으로 선택할 사항

화면 차이만 보고 하드코딩이라고 단정하지 않고, 코드 구조는 구조 사실 문서로만 판정합니다.

## 세션에서 다룰 문제 묶음

### A. 공통 UI와 콘텐츠별 변형

관찰:

- 같은 공개 경로 안에서도 결과 모양과 조정 가능한 값이 Flow마다 다릅니다.
- 공개 Flow와 My Flow에서 같은 내용을 보여주는 방식과 조작 방식이 크게 달라집니다.
- 별도 공개 경로인 `/flow-maps` 화면도 남아 있습니다.

가설:

- 공통 데이터 렌더러는 있으나 경로별 화면 틀과 콘텐츠별 표시 예외가 함께 남았을 수 있습니다.
- 필요한 콘텐츠 차이와 구현 과정에서 생긴 예외가 명확히 구분되지 않았을 수 있습니다.

결정 질문:

- 현재 구조는 `공통 렌더러 유지`, `공통 렌더러와 예외 정책 정리`, `구조 재설계` 중 어디에 해당합니까?
- 모든 Flow가 공유할 화면 틀과 전환 규칙은 무엇입니까?
- 콘텐츠 차이는 어떤 데이터 필드와 명시적 variant로만 허용합니까?

### B. Flow 조정과 Item 수정

관찰:

- Flow 조정은 현재 화면 아래에 이어지고, Item 수정은 바텀시트로 열립니다.
- Flow 유형에 따라 조정 항목이 달라집니다.
- 화면에 보이는 Step·그룹 이름은 현재 공개 편집 화면에서 수정할 수 없습니다.

가설:

- Flow 단위 편집과 Item 단위 편집의 역할 및 진입 규칙이 충분히 정리되지 않았을 수 있습니다.
- 사용자가 편집하는 대상보다 구현 단위에 따라 표면이 나뉘었을 수 있습니다.

결정 질문:

- Flow 조정과 Item 수정을 하나의 편집 경험으로 묶을지, 역할을 분리할지
- 별도 페이지, 바텀시트, 모달, 인라인 중 어떤 기준으로 편집 표면을 선택할지
- 이름, Step·그룹 이름, Item, 날짜, 반복 중 MVP에서 수정할 범위는 어디까지인지
- 수정 결과를 캘린더·체크리스트·Flow 형태로 언제 미리 보여줄지

### C. 저장·시작·가져가기

관찰:

- `Flow 가져가기`가 저장 전과 저장 완료 뒤에 모두 나타납니다.
- 저장 CTA의 문구가 결과 유형에 따라 `캘린더 24개로 시작`, `체크리스트 10개로 시작`처럼 달라집니다.
- 저장, 실행 시작, 외부 도구로 내보내기가 한 흐름 안에서 서로 다른 이름으로 보입니다.

가설:

- 제품 내부 저장과 외부 내보내기의 상태 구분이 UI에서 충분히 드러나지 않을 수 있습니다.
- 상태 전환보다 기능을 빠짐없이 노출하는 데 초점이 맞춰졌을 수 있습니다.

결정 질문:

- 정식 상태 흐름을 `미리보기 → 조정 → 내 Flow 저장 → 실행 → 외부 도구로 내보내기`로 둘지
- 각 상태에서 주 행동을 하나로 줄일 수 있는지
- `시작`, `저장`, `가져가기`, `이 사본 사용`의 뜻과 노출 위치를 어떻게 나눌지
- 가져가기 전에 실제 캘린더·체크리스트 결과와 범위를 어떻게 보여줄지

### D. 정보량과 출처 정책

관찰:

- `내 조건`, `저장 결과`, `전체`, `전체 내용과 원문`, `출처와 주의`가 경로와 Flow에 따라 다르게 나타납니다.
- 일부 정보는 현재 사용자의 다음 행동과 직접 연결되지 않습니다.

가설:

- 내부 분류나 검증용 정보가 사용자 화면에 함께 노출됐을 수 있습니다.
- 출처와 주의 정보의 위험도별 노출 원칙이 없거나 경로별로 다를 수 있습니다.

결정 질문:

- 다음 행동에 필요한 최소 정보는 무엇인지
- 기본 화면에서 없애고 필요할 때만 펼칠 정보는 무엇인지
- 원문 링크는 공통으로 유지하되 주의 문구는 어떤 조건에서만 보여줄지

### E. My Flow 실행 구조

관찰:

- `할 일 / Flow` 두 보기가 있고 기본은 `할 일`입니다.
- 행의 `열기`와 `메모`, 상세의 `실행 메모`와 `메모·일정`이 함께 존재합니다.
- 같은 원문에서 저장된 사본을 정리하는 `이 사본 사용` 블록이 My Flow 상단에 나타날 수 있습니다.
- 한 Flow 작업 공간에 이어서 할 일, 전체 계획, 단계, 일정 변경, 전체 가져가기가 함께 있습니다.

가설:

- 오늘 실행할 일과 전체 Flow 관리라는 서로 다른 작업이 탭으로 분리됐지만, 그 차이가 설명 없이 드러나지 않을 수 있습니다.
- 실행, 기록, 일정, 내보내기, 사본 관리가 한 화면에 모였을 수 있습니다.

결정 질문:

- My Flow의 대표 작업은 `지금 할 일 확인`과 `Flow 전체 관리` 중 무엇인지
- 두 작업을 탭으로 유지할지, 하나의 진입점과 단계적 공개로 바꿀지
- Item을 여는 한 경로 안에 메모와 일정을 통합할 수 있는지
- 중복 사본 정리는 일상 실행 화면이 아니라 데이터 관리·복구 영역으로 옮길지

## 반드시 내려야 할 결정

1. 현재 UI 구조에 대한 아키텍처 판정과 확신 수준
2. 모든 Flow가 공유할 화면 틀·상태·전환 규칙
3. 콘텐츠 유형별로 허용할 변형 목록
4. Flow 조정과 Item 수정의 역할 및 표면 원칙
5. 저장과 가져가기의 상태·용어·위치
6. 유지, 통합, 삭제, 필요할 때만 표시할 정보
7. My Flow의 대표 사용자 작업과 화면 구조
8. P0, P1, 보류 범위 및 각 수용 기준

## 완료 조건

- 사용자 피드백이 관찰·가설·결정 질문으로 분리되어 있습니다.
- Claude Design이 로컬 저장소 없이도 현재 화면과 코드 구조 사실을 이해할 수 있습니다.
- 공통 UI 여부를 판단할 근거가 변경되지 않는 GitHub 코드 링크로 제공됩니다.
- 날짜형, 체크리스트형, 루틴형, 기존 `/flow-maps` 화면이 비교됩니다.
- 독립 검토와 사용자 피드백 대조가 분리되어 있습니다.
- 최소 2개의 실제로 다른 모바일 구조 대안과 하나의 권고안이 나옵니다.
- 권고안이 구현 가능한 P0·P1 작업과 수용 기준으로 이어집니다.
- 전면 재작성 여부는 화면 인상만이 아니라 코드 영향 범위로 판정합니다.
- 구현과 배포는 별도 승인 전까지 시작하지 않습니다.

## 세션 결과 작성 형식

각 결정은 아래 형식으로 남깁니다.

```text
결정 항목:
확인된 관찰:
원인 가설:
선택안:
권고안:
권고 이유:
감수할 점:
적용 범위:
P0 / P1 / 보류:
수용 기준:
추가로 필요한 근거:
```

마지막에는 아래 표를 포함합니다.

```text
현재 요소 | 유지 | 통합 | 삭제 | 필요할 때만 표시 | 근거 | 우선순위
```
