# Claude Design 1차 독립 작업 프롬프트

아래 본문을 Claude Design에 그대로 전달합니다. 이 단계에서는 `06-owner-feedback-normalized-ko.md`를 보내지 않습니다.

---

당신은 모바일 생산성 서비스의 시니어 제품·인터랙션 디자이너입니다.

GitHub에 공개된 다음 자료를 먼저 읽고 작업해 주세요.

1. `01-planning-session-brief-ko.md` — 목표와 범위
2. `02-production-evidence-index-ko.md` — Production 모바일 화면과 상태
3. `03-architecture-facts-ko.md` — 로컬 접근 없이 볼 수 있는 코드 구조 사실
4. `04-screen-state-and-variant-matrix-ko.md` — Flow 유형과 상태 비교

로컬 저장소에는 접근할 수 없습니다. 제품 소유자의 평가나 개선 의견은 아직 제공하지 않았습니다. 먼저 화면과 구조 사실만으로 독립적인 진단과 제안을 만들어 주세요.

## 제품의 기본 과정

```text
Flow 찾기
→ 내용과 예상 결과 확인
→ 필요한 부분 조정
→ 내 Flow로 저장
→ 실행하고 완료 상태 관리
→ 캘린더·체크리스트·시트·메모 등으로 가져가기
```

현재는 Production 기준 MVP/PoC이며 모바일을 우선 검토합니다. Text-to-Flow, 계정, 클라우드 동기화, 협업, OAuth, AI 생성, 외부 사용자 관찰은 이번 범위에서 제외합니다.

## 작업 원칙

1. 스크린샷의 차이만 보고 코드가 하드코딩됐다고 추측하지 마세요. 구조 판정은 `03-architecture-facts-ko.md`만 사용하고, 부족하면 `판단 불가`라고 적으세요.
2. 기능과 설명을 더하기 전에 삭제, 통합, 필요할 때만 표시하는 방법을 먼저 검토하세요.
3. 한 화면에서 사용자가 내릴 결정 하나에 주 행동 하나를 기본으로 두세요.
4. 콘텐츠에 따라 달라져야 하는 값과 모든 Flow에서 같아야 하는 상호작용 규칙을 구분하세요.
5. Flow 찾기와 My Flow가 반드시 똑같아야 한다고 가정하지 마세요. 저장 전·후 상태 때문에 필요한 차이와 이유 없는 차이를 각각 밝히세요.
6. 인라인 확장, 별도 화면, 모달, 바텀시트를 실제 모바일 이동과 복귀 방식까지 비교하세요.
7. 출처 링크, 중요한 주의, 오류 복구, 되돌리기는 단순화를 이유로 무조건 삭제하지 마세요. 필요한 위치와 노출 수준을 정하세요.
8. 자동화나 전문가 검토를 사용자 검증이라고 표현하지 마세요.
9. 전체 재작성은 화면 인상만으로 권고하지 말고, 구조 사실과 영향 범위를 연결하세요.

## 반드시 답할 질문

- 현재 UI는 공통 데이터와 renderer를 중심으로 확장 가능한 구조입니까, 예외가 누적된 혼합 구조입니까, 콘텐츠별 구현입니까?
- 사용자는 `미리보기`, `조정 중`, `저장 완료`, `실행 중`, `외부로 가져가기` 상태를 구분할 수 있습니까?
- Flow 전체 조정과 Item 개별 수정의 역할 및 화면 방식은 일관됩니까?
- Step·그룹 이름을 포함해 MVP에서 수정할 속성은 무엇이어야 합니까?
- 가져가기는 어느 상태에서, 어디에 두고, 어떤 결과를 미리 보여준 뒤 실행해야 합니까?
- Flow 찾기와 My Flow 사이에 유지할 시각·상호작용 계약은 무엇입니까?
- `할 일 / Flow`는 서로 다른 사용자 과업을 해결합니까, 내부 데이터 관점을 노출합니까?
- 겹치는 카드, 설명, 메모, 버튼, 상태 표시는 무엇입니까?
- Flow 유형별 필드가 달라도 동일하게 유지할 화면 틀과 전환 규칙은 무엇입니까?

## 제출물

### 1. 독립 진단

각 발견을 `Blocking / High / Medium / Low`로 표시하고 E01~E13 증거 ID를 연결하세요. 아래를 분리하세요.

- 화면에서 직접 확인한 관찰
- 그 관찰에 대한 해석
- 코드 구조 사실
- 아직 확인할 수 없는 것

### 2. 구조 판정

`공통 데이터 매핑 중심 / 혼합 구조 / 콘텐츠별 구현 중심 / 판단 불가` 중 하나를 선택하고 근거와 확신 수준을 적으세요.

### 3. 사용자 상태 모델

저장 전부터 실행·가져가기까지 상태를 하나의 흐름으로 그려 주세요. 각 상태마다 아래를 적으세요.

- 사용자의 질문
- 주 행동
- 보조 행동
- 다음 상태
- 되돌아가는 방법

### 4. 불변 요소와 가변 요소

Flow 찾기, 미리보기, 조정, 저장, My Flow, 가져가기에서 모든 Flow가 공유할 요소와 콘텐츠 유형에 따라 달라질 요소를 표로 만드세요.

### 5. 삭제·통합 제안

현재 요소를 아래 네 묶음으로 분류하세요.

- 삭제
- 다른 요소와 통합
- 필요할 때만 표시
- 반드시 유지

각 항목에 이유와 위험을 적으세요.

### 6. 실제로 다른 모바일 구조 대안 2~3개

이름만 다른 대안이 아니라 화면 이동과 상태 모델이 달라야 합니다. 각 대안에 아래를 포함하세요.

- 화면 목록과 이동 구조
- Flow 조정과 Item 수정 방식
- 저장과 가져가기의 위치
- 결과 미리보기 방식
- Flow 찾기와 My Flow의 관계
- 공통 UI/data contract
- 저해상도 모바일 wireframe
- 장점, 단점, 구현 위험

### 7. 권고안

MVP에 가장 적합한 대안 하나를 선택하고 다음을 구체적으로 제안하세요.

- 모바일 사용 흐름
- 화면별 정보 우선순위
- 주 버튼과 보조 버튼 문구
- 삭제·통합할 요소
- 콘텐츠별 차이를 허용할 범위
- 기존 공통 코어에서 유지할 부분과 정리할 부분

버튼 문구는 자연스러운 한국어로 작성하고 `저장`, `시작`, `가져가기`의 뜻이 겹치지 않게 하세요.

### 8. 구현 우선순위

`P0 / P1 / 보류`로 나누고 각 항목에 수용 기준을 적으세요. 이번 답변에서는 코드를 작성하지 마세요.

### 9. 추가로 필요한 근거

현재 자료만으로 판단할 수 없었던 사항과 필요한 화면·상태·코드 사실을 적으세요.
