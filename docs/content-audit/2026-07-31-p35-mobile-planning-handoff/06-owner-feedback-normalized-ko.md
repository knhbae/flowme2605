# 제품 소유자 모바일 피드백 정리본

## 성격과 한계

- Production을 모바일에서 직접 사용한 제품 소유자의 피드백입니다.
- 외부 사용자 관찰 결과가 아닙니다.
- 아래의 `관찰`은 제품 소유자가 화면에서 느끼고 확인한 현상입니다.
- `원인 가설`과 `해결 가설`은 검토가 필요한 의견이며 확정 결론이 아닙니다.
- Claude Design에는 1차 독립 검토가 끝난 뒤에만 제공합니다.

## 전체 구조

### O-01. 공통 데이터 기반 UI인지 불분명함

- 관찰: Flow마다 화면과 조정 방식이 달라 콘텐츠별로 UI를 따로 만든 것처럼 느껴집니다.
- 원인 가설: 공통 UI에 데이터를 매핑하는 구조가 아니거나, 공통 구조가 있더라도 콘텐츠별 예외가 많이 쌓였을 수 있습니다.
- 위험: 사실이라면 콘텐츠가 늘어날수록 일관성과 유지보수성이 나빠집니다.
- 결정 질문: 현재 구조는 공통 코어 유지와 제한된 정리로 충분한지, 더 큰 구조 개편이 필요한지 코드 근거로 판정해야 합니다.

### O-02. 정보 구조가 서로 겹치고 빠짐없이 나뉘지 않음

- 관찰: 화면과 단계가 MECE하게 느껴지지 않고, 불필요한 단계와 정보가 여전히 많습니다.
- 원인 가설: 사용자 과업보다 기능·내부 데이터 단위로 화면을 나눴을 수 있습니다.
- 결정 질문: 각 화면이 어떤 사용자 질문 하나에 답하는지, 없애거나 합칠 단계가 무엇인지 다시 정리해야 합니다.

## Flow 찾기와 공개 Flow

### F-01. Flow별 하단 행동 영역이 다름

- 관찰: 특정 Flow를 고른 뒤 하단의 `조정 / 그대로 시작` 또는 이에 해당하는 버튼·카드 구성이 Flow마다 다릅니다.
- 요구 방향: 공통 행동 영역과 콘텐츠별로 달라질 값을 구분하고, 위치와 상호작용 규칙은 통일해야 합니다.

### F-02. Step·그룹 이름을 수정할 수 없음

- 관찰: `큰 일정`, `D-30 큰 준비`처럼 Item 위에 붙는 이름을 화면에서 수정할 수 없습니다.
- 결정 질문: 이 값이 실제 Step·그룹 제목인지, 설명용 subtitle인지 데이터 의미를 확인하고 MVP 수정 범위를 정해야 합니다.

### F-03. Flow 가져가기 진입 방식이 어렵고 현재 화면과 섞임

- 관찰: `Flow 가져가기`가 현재 화면 아래로 이어져 어디까지가 원래 화면이고 어디부터 새 작업인지 헷갈립니다.
- 해결 가설: 별도 화면, 모달 또는 바텀시트처럼 원래 영역과 명확히 분리할 수 있습니다.
- 추가 요구: 캘린더·체크리스트 등 실제 결과를 가져가기 전에 미리 볼 수 있어야 합니다.
- 결정 질문: 작업 길이와 복귀 경로를 기준으로 가장 적절한 편집·내보내기 표면을 정해야 합니다.

### F-04. Flow 전체 조정과 Item 수정 UI가 크게 다름

- 관찰: Item의 `수정`으로 여는 화면과 `Flow 조정`으로 여는 화면의 방식이 다릅니다.
- 관찰: Flow 조정 항목도 콘텐츠마다 달라 예측하기 어렵습니다.
- 결정 질문: 대상이 다른 만큼 필요한 차이인지, 하나의 편집 규칙으로 묶어야 하는지 판단해야 합니다.

### F-05. 저장·시작 전후에 Flow 가져가기가 반복됨

- 관찰: `Flow 시작` 또는 저장 전 화면에 `Flow 가져가기`가 있고, 저장 완료 뒤에도 다시 나타납니다.
- 관찰: 가져가기는 핵심 기능 중 하나인데 현재 접힌 보조 영역처럼 보여 눈에 잘 띄지 않습니다.
- 결정 질문: 저장 전 가져가기와 저장 후 가져가기가 서로 다른 작업인지, 어느 한 상태에만 둘지, 이름을 다르게 해야 하는지 정해야 합니다.

### F-06. Flow 찾기와 My Flow의 표현이 이어지지 않음

- 관찰: 같은 Flow가 Flow 찾기와 My Flow에서 같은 구조로 인식되지 않습니다.
- 관찰: 공개 화면이 미리보기라는 점도 충분히 드러나지 않습니다.
- 결정 질문: 두 화면이 같은 내용을 공유한다는 신호와 저장 전·후라서 달라야 할 부분을 각각 정해야 합니다.

### F-07. 상단 요약 카드가 과함

- 관찰: `내 조건 / 저장 결과 / 전체` 같은 카드가 일부 화면 상단에 나타나지만 현재 결정에 꼭 필요한지 불분명합니다.
- 요구 방향: 다음 행동에 기여하지 않는 정보는 삭제하거나 필요할 때만 보여줍니다.

### F-08. 원문·출처·주의 정보가 일관되지 않음

- 관찰: 일부 Flow에는 `전체 내용과 원문`, 다른 Flow에는 `출처와 주의`가 나타나고, 아예 없는 경우도 있어 보입니다.
- 사용자 제안: 기본 화면에는 직접 원문 링크만 남기고 나머지는 줄입니다.
- 검토 조건: 중요한 안전·법률·민감 정보의 주의 문구까지 일괄 삭제하지 말고, 위험도와 해당 행동에 맞는 위치를 따로 판단해야 합니다.

## My Flow

### M-01. `이 사본 사용`이 일상 실행 화면에 어울리지 않음

- 관찰: My Flow 상단에 `이 사본 사용` 관련 내용이 나타날 수 있는데, 일상 실행에 필요한 정보로 느껴지지 않습니다.
- 구조 사실: 같은 원문에서 여러 사본이 생겼을 때 계속 쓸 사본을 고르는 데이터 보호 기능입니다.
- 결정 질문: 기능을 유지하되 데이터 관리·복구로 옮길지, 예외가 생긴 순간에만 별도로 안내할지 정해야 합니다.

### M-02. Step·Item 상세가 전체 스타일과 이질적이고 복잡함

- 관찰: My Flow와 다른 탭의 Step·Item 상세가 전체 화면과 시각·상호작용 면에서 동떨어져 보입니다.
- 결정 질문: 공개 Item 수정, My Flow Item 상세, 메모·일정을 하나의 detail/edit 패턴으로 정리할 수 있는지 검토해야 합니다.

### M-03. `할 일 / Flow` 구분의 이유가 불명확함

- 관찰: 두 탭이 어떤 다른 작업을 위한 것인지 설명 없이 이해하기 어렵습니다.
- 결정 질문: 실제로 `여러 Flow의 지금 할 일`과 `한 Flow 전체 관리`라는 두 사용자 과업이 있는지, 그렇다면 탭 외의 더 분명한 구조가 필요한지 판단해야 합니다.

### M-04. 행의 열기와 메모가 겹침

- 관찰: 각 Item 행에 `열기`와 `메모`가 따로 있고, 열어서 보는 상세 안에도 메모가 있습니다.
- 사용자 제안: 행의 메모 버튼을 없애고, `열기` 뒤 상세에서만 메모를 작성합니다.
- 결정 질문: 빠른 메모가 실제 핵심 작업인지, 행 명령을 줄이는 편이 더 나은지 비교해야 합니다.

### M-05. `실행 메모`와 `메모·일정`의 구분이 이상함

- 관찰: 상세에 `실행 메모`와 `메모·일정`이 따로 존재해 사용자가 같은 메모로 인식할 수 있습니다.
- 사용자 제안: `실행 메모`를 없애고 하나의 메모로 합칩니다.
- 구조 사실: 코드에서는 서로 다른 데이터 모델입니다.
- 결정 질문: 사용자가 구분할 가치가 있는지 확인하고, 없다면 데이터 보존 방법을 포함한 통합안을 제안해야 합니다.

### M-06. 한 Flow 작업 화면이 너무 복잡함

- 관찰: 이어서 할 일, 행 메모, 완료, 진행률, 전체 계획, 여러 할 일 조정, 날짜 변경, 전체 가져가기가 한 화면에 함께 있습니다.
- 결정 질문: 기본 화면에 남길 핵심 실행 정보와 상세·관리로 옮길 기능을 나눠야 합니다.

## 제품 소유자가 기대하는 2차 결과

- 각 피드백에 대한 `확인됨 / 일부 확인 / 현재 근거로 확인 불가 / 다른 해결 권고`
- 사용자 피드백에 없었던 추가 발견
- 전면 재작성이 필요한지, 공통 코어를 살린 제한된 구조 개선으로 가능한지
- 유지, 통합, 삭제, 필요할 때만 표시할 UI 목록
- 모바일 핵심 화면과 전환 규칙
- P0·P1 및 수용 기준
