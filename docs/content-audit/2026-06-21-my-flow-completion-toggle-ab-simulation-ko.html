My Flow UX 시뮬레이션

상세 화면의 완료는 없앨 것인가, 작게 남길 것인가

이 문서는 사용자용 화면이 아니라 검토 리포트입니다. 목적은 저장한 Flow를 열어 메모를 확인하고 실행한 뒤, 완료 신호를 어디에서 처리하는 것이 가장 덜 복잡한지 판단하는 것입니다.

A/B PoC 열기 완료 토글 관찰 기준 저장 개수별 관찰 통합 시뮬레이션

현재 판정

기본안은 “작은 상세 완료 토글 유지”가 맞다

남기는 이유사용자가 상세를 연 순간은 메모와 원문 단서를 보고 실제로 실행하는 순간이다. 이 자리에서 바로 완료를 표시할 수 있어야 한다.
줄이는 이유큰 CTA나 반복 텍스트 버튼은 프로젝트 관리 앱처럼 보인다. 완료는 보조 체크 토글이어야 한다.
관찰 후 바꿀 조건사용자가 상세 완료를 거의 쓰지 않거나 목록 체크와 혼동하면, 상세에서는 메모만 남기고 완료는 목록 체크로 이동한다.

정리하면 기능을 없애는 문제가 아니라, 완료를 “실행 상태 신호”로 남기되 화면의 주인공으로 만들지 않는 문제입니다.

비교안

A/B 기준

안 화면 형태 장점 리스크
A. 상세 완료 있음 상세 drawer 하단에 작은 `완료` 체크 토글을 둔다. 목록 row에도 빠른 체크는 있다. 상세에서 메모 확인, 실행, 완료까지 한 흐름으로 끝난다. 캘린더/투두 앱의 체크 감각과 가깝다. 목록 체크와 상세 체크가 같은 동작이라는 것을 명확히 보여줘야 한다. 큰 버튼이 되면 과하다.
B. 상세 완료 없음 상세 drawer는 메모와 원문 단서만 보여주고 완료는 목록에서만 처리한다. 상세 화면은 더 조용하다. 사용자는 읽고 메모하는 일에 집중한다. 상세에서 실행을 마친 뒤 다시 목록으로 돌아가야 한다. “방금 한 일을 어디서 끝내지?”가 생길 수 있다.

UX 디자이너 관점

Apple/Galaxy/Toss식으로 보면

Apple식 판단상세 화면의 주 작업은 읽기와 메모다. 완료는 보조 컨트롤이어야 하며, primary 버튼처럼 보이면 안 된다.
Galaxy식 판단목록과 상세 양쪽에서 같은 상태가 즉시 반영되어야 한다. 체크한 뒤 숫자와 상태가 바뀌는 피드백이 중요하다.
Toss식 판단사용자가 다음에 할 행동이 하나로 보여야 한다. 설명 대신 `완료`, `닫기`, `메모`처럼 결과가 예측되는 단어만 남기는 게 맞다.

개선 방향

지금 적용해야 할 UX 원칙

  • 완료는 삭제하지 말고 작은 체크 토글로 낮춘다.
  • row마다 `완료` 텍스트 버튼을 반복하지 않는다. 목록에서는 체크 아이콘처럼 보이게 한다.
  • 상세 화면에서는 `완료`와 `닫기`만 남기고, `나중에 보기`, `이 항목 완료`, `현재 설명 복사` 같은 결과가 불명확한 버튼은 기본값에서 뺀다.
  • Flow 1개 저장 상태에서는 전체 관리 UI보다 `저장됨`, 체크, 메모, fallback text가 먼저 보여야 한다.
  • Flow 8개 이상에서는 버튼을 늘리지 말고 `Flow 찾기`, 검색, 접힌 목록을 써야 한다.

실제 사용자에게 볼 것

질문 유지 신호 숨김 신호
상세를 열고 메모를 남긴 뒤 사용자가 어디서 완료를 누르는가? 상세의 작은 완료를 자연스럽게 누른다. 항상 닫고 목록 체크를 찾거나, 완료를 전혀 누르지 않는다.
목록 체크와 상세 체크를 중복으로 느끼는가? 같은 상태로 이해하고 문제없이 사용한다. 서로 다른 의미로 오해한다.
완료 토글이 메모 작성을 방해하는가? 메모를 먼저 쓰고 필요할 때 완료한다. 완료가 primary action처럼 보여 메모를 지나친다.
