기준 모델

Step은 저장되는 최소 단위, Item은 상세 또는 텍스트 fallback

계층 제품에서의 의미 사용자 화면에서의 원칙
Flow Map 여러 Flow를 묶는 상위 구조 전체 위치를 볼 이유가 있을 때만 보여줍니다. My Flow 첫 화면을 지도 대시보드로 만들지 않습니다.
Flow 하나의 실행 artifact 캘린더, 진도표, 체크리스트, 메모 중 자연스러운 형태로 보입니다.
Step 캘린더/투두/시트에 저장되는 최소 row 클릭하면 바로 같은 맥락에서 상세가 열리고, 완료/메모/출처를 확인할 수 있어야 합니다.
Item Step 안의 체크/메모/설명/링크 FlowMe에서는 체크리스트로 보일 수 있고, 외부 앱에서는 텍스트 설명으로 내려갑니다.

현재 충분한 부분

다음 구현 기준으로 쓸 수 있는 것

공개 저장 경로Flow Map 공개 페이지에서 저장하면 실제 /my로 이동하는 경로가 있습니다.
부모 map snapshot저장 시 child Flow뿐 아니라 map version, child slug, risk, source checked date를 기록합니다.
Step detail원문 링크, Item 체크, memo hint, text fallback이 Step 아래로 내려갑니다.
공식 기간 처리영유아 검진 기간처럼 날짜 범위가 있는 source row도 하나의 Step으로 유지합니다.
모바일 post-save저장 뒤 calendar 또는 Flow view로 이동했을 때 사용자가 확인할 위치로 스크롤됩니다.
선택 날짜 detail일정에서 날짜를 누르면 Step이 저장된 Flow Map 또는 Flow 단위로 묶이고, 단일 Flow 지도에서는 중복 chip을 숨깁니다.
혼합 캘린더 필터일정과 루틴이 섞인 달에만 `전체/일정/루틴` 같은 작은 표시 필터를 보여주고, 단순 캘린더에는 숨깁니다.
지도 업데이트 notice저장한 source-backed 지도 snapshot이 현재 지도와 다르면 Flow 탭에 확인 안내를 띄우고, 기존 Step은 자동 변경하지 않습니다.
화면 분리사용자 화면, 제작자 준비 화면, 내부 리뷰 문서를 같은 화면에 섞지 않는 방향이 정리됐습니다.

Phase 2 업데이트

저장 record를 두 층으로 분리했다

저장 키 역할 현재 판단
flow:map:saved:{mapId} 현재 My Flow가 부모 지도 문맥을 붙일 때 쓰는 호환 snapshot 유지. 기존 화면을 깨지 않기 위한 bridge입니다.
flow:map:persistence:{mapId} schema version, 저장 출처, readiness, update assessment, child Flow binding을 담는 제품화 record 추가. 최종 DB schema는 아니지만 다음 persistence/update/creator 작업의 기준입니다.

의미: 사용자 화면은 그대로 단순하게 두고, 내부 저장 계약만 다음 제품화 단계에 맞게 선명해졌습니다. readiness 분리와 제작자 source-row review는 bridge 수준으로 들어갔고, 다음 축은 계정 저장, update review, 고밀도 캘린더 규칙입니다.

Phase 3 업데이트

My Flow에서 ready와 review/legacy를 분리했다

구분 어디에 보이나 원칙
실행 가능 Flow 탭의 바로 이어서 볼 Flow source-backed 저장 지도, 실제 원문 Flow는 일반 실행 카드로 둡니다.
검토 필요 Flow 탭의 확인 후 실행할 Flow needs_review, preview, legacy 컨텐츠는 낮은 톤의 별도 영역으로 둡니다.
Today / Calendar 그대로 실행 중심 날짜/오늘 화면은 review dashboard로 만들지 않고, 사용자가 저장한 실행 row를 계속 보여줍니다.

의미: 사용자는 accepted source-backed Flow와 예전 기준 컨텐츠를 한눈에 구분할 수 있습니다. 동시에 예전 컨텐츠도 삭제하지 않고 필요하면 열어볼 수 있습니다.

Phase 4 업데이트

제작자 화면에 원문 row 검토를 추가했다

검토 항목 제작자가 보는 것 제품 경계
Step 전환 원문 row가 어떤 Step 제목, Flow, 섹션, destination으로 옮겨졌는지 확인합니다. 사용자 화면의 실행 카드와 섞지 않습니다.
Item fallback FlowMe 내부 체크리스트 또는 외부 앱 텍스트로 내려갈 실제 Item 문장을 봅니다. 원문에 없는 일반론으로 채우지 않습니다.
출처/위험 공식 정보, 참고 원문, 제작자 경험, 건강 민감 여부를 row 근처에서 확인합니다. 공식/경험/주의를 사용자 실행 화면에서 뒤섞지 않습니다.
발행 준비 상태 준비됨, 원문 링크 필요, 하위 Item 확인 상태를 봅니다. 아직 편집기나 버전 리뷰 UI는 아닙니다.

의미: 제작자는 공개 전에 원문 근거와 Step/Item 변환 결과를 볼 수 있고, 사용자는 여전히 가벼운 My Flow 실행 화면만 보게 됩니다.

Phase 5 업데이트

일정 선택 날짜를 Flow Map/Flow 단위로 묶었다

문제 수정 사용자 효과
캘린더 날짜를 눌렀을 때 여러 Step이 평평하게 보이면 어느 지도나 Flow에서 온 일정인지 알기 어렵습니다. my-flow-selected-date-group 단위로 선택 날짜 Step을 묶었습니다. 사용자는 “원룸 이사 D-30 일정 지도” 안의 “기준 D-30” Step처럼 소속과 실행 항목을 함께 봅니다.
단일 Flow 지도에서는 Step row 아래의 Flow 이름과 진행률 chip이 group title과 중복됩니다. 같은 group 안에 child Flow가 하나뿐이면 Flow/progress chip을 숨깁니다. 선택 날짜 detail이 캘린더 앱의 일정 목록처럼 간단해지고, 필요한 hierarchy만 남습니다.
여러 Flow가 같은 날짜에 섞이는 경우에는 child Flow 구분이 필요합니다. group 안에 여러 child Flow가 있을 때만 compact chip을 유지할 수 있게 했습니다. 고밀도 일정에서도 context를 잃지 않고, 단순한 날에는 화면이 과해지지 않습니다.

의미: My Flow 일정 화면은 “오늘/날짜별 Step 실행”을 중심에 두되, Flow Map의 부모 맥락은 필요한 순간에만 드러납니다.

Phase 6 업데이트

혼합 캘린더에만 표시 범위 필터를 추가했다

규칙 동작 남은 범위
일정과 루틴이 섞이면 필터를 보여줍니다. my-flow-calendar-scope-filter에서 전체, 일정, 루틴을 전환합니다. 고급 검색이나 카테고리별 대시보드는 아직 만들지 않습니다.
필터는 월 캘린더와 선택 날짜 detail을 함께 좁힙니다. 루틴 선택 시 일정 row가 사라지고, 일정 선택 시 루틴 아이콘이 사라집니다. 대량 저장 상태의 검색, 정렬, 숨김 규칙은 별도 후속입니다.
단순한 캘린더에는 필터를 숨깁니다. 이사 D-30처럼 일정만 있는 Flow는 캘린더 앱 수준의 단순 화면을 유지합니다. 실제 사용자 행동 데이터가 생기기 전에는 더 많은 제어를 기본 노출하지 않습니다.

의미: 저장 Flow가 늘어날 때 필요한 최소한의 숨쉬는 공간을 만들되, My Flow를 Jira나 프로젝트 보드처럼 키우지 않는 쪽으로 정리했습니다.

Phase 7 업데이트

저장한 지도 업데이트를 조용히 적용하지 않게 했다

상황 사용자 화면 제품 경계
저장한 source-backed 지도 version이나 source row shape가 현재 발행본과 다릅니다. Flow 탭에 my-flow-map-update-review 안내가 나타납니다. Today와 Calendar는 계속 실행 화면으로 둡니다.
공식/민감 일정은 자동 반영하면 기존 체크 상태와 충돌할 수 있습니다. “자동 반영 안 함”을 표시하고 공개 지도 링크와 “지금은 숨기기”를 제공합니다. 이번 V1은 적용 UI가 아니라 notice + dismiss입니다.
저장 snapshot이 최신 상태입니다. 추가 안내를 보여주지 않습니다. 필요한 경우에만 나타나는 낮은 톤의 safety surface로 유지합니다.

의미: 사용자 실행 화면을 무겁게 만들지 않으면서, 공식/민감 Flow Map이 바뀌었을 때 기존 개인 기록을 몰래 바꾸지 않는 경계를 세웠습니다.

아직 bridge인 부분

제품 완료로 오해하면 안 되는 것

현재 상태는 내부 PoC, route integration, 자동화 테스트 근거입니다. 실제 사용자 행동 데이터가 없으므로 검증 완료나 상품화 완료로 표현하면 안 됩니다.

  • lib/flow/source-backed-my-flow.ts는 최종 DB schema가 아니라 source-backed adapter/fixture registry입니다.
  • localStorage 저장은 bridge입니다. 계정 기반 저장, 동기화, update review는 아직 남았습니다.
  • 제작자 화면은 publish prep에 가깝고, 실제 authoring/editor workflow는 아닙니다.
  • 기존 preview, review, legacy content는 ready/review 영역으로 나뉘었지만, 운영 정책과 마이그레이션 규칙은 아직 남았습니다.
  • 선택 날짜 group, scope filter, update notice/dismiss는 1차 정리입니다. 일정이 더 많을 때의 검색, 정렬, 숨김과 update apply/row compare는 아직 별도 판단이 필요합니다.
  • 더 많은 카테고리를 만들기 전에 이 세 기준선이 실제 제품 표면에서 깔끔하게 유지되는지 봐야 합니다.

다음 코드 우선순위

지금 바로 더 볼 일

순서 작업 이유
1 계정 기반 저장과 update apply/compare 현재 localStorage bridge와 notice로는 여러 기기 동기화, 업데이트 적용, 이전/새 Step 비교, 확인 후 닫기까지 처리하지 못합니다.
2 대량 저장 캘린더 검색/숨김 규칙 선택 날짜 group과 scope filter는 1차로 충분하지만, 저장 Flow가 더 많아지면 검색, 숨김, 정렬, 월 이동 기준이 필요합니다.
3 제작자 source-row editing / version review review v1은 추가됐습니다. 다음은 제작자가 Step 제목, Item fallback, source link를 수정하고 버전 변경을 관리하는 편집/검토 흐름입니다.
4 공개 save-before polish 사용자가 무엇을 저장하는지는 더 선명해져야 하지만, My Flow 실행 결과가 먼저 안정되어야 합니다.
5 footprint/event logging 실제 검증은 open, 입력, 저장, Step open, check, memo, return 행동 데이터가 있어야 가능합니다.
