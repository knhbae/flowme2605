# FlowMe 텍스트 저작 문법·UX 개선 검토서

작성일: 2026-08-04  
판정: 현재 데모는 기능 시연은 가능하지만 문법·출력·중간 구조의 의미가 사용자에게 일관되게 전달되지 않는다. 디자인 다듬기 전에 문법 v2 후보와 결과 형태 계약을 먼저 고정해야 한다.

## 1. 내부 시뮬레이션 결론

### 현재 기준선

- 파서·인프라·문법 시뮬레이션 집중 테스트: 45/45 통과
- 기존 문법 시나리오: 27/27 통과
- 기존 브라우저 자동 확인: 11/11 통과
- 위 결과는 구현의 일관성을 본 내부 QA다. 문법 학습성, 결과 형태 이해, 사용자 검증을 증명하지 않는다.

### 새 `- 속성:` 표기를 현재 구현에 바로 넣었을 때

기존 27개 입력 중 속성 줄이 있는 18개를 `설명:`에서 `- 설명:`으로 기계 변환해 현재 파서에 넣으면 18개가 모두 실패한다.

| 대표 예시 | 현재 결과 | 새 표기를 현재 파서가 읽은 결과 |
|---|---:|---:|
| 이사 D-30 | 27 Item / Calendar 27 | 81 Item / Calendar·ICS 65 |
| 자동차검사 | 10 Item / Calendar 10 | 20 Item / Calendar·ICS 20 |
| Allblanc 7일 | 7 Item | 28 Item |
| 신차 구매 | 14 Item | 28 Item |
| 시간·시간대·소요 시간 | 1 Item | 5 Item |
| 미정 속성 | issue 1 | issue 0, 가짜 Item 생성 |
| 잘못된 날짜 | issue 1 | issue 0, 가짜 Item 생성 |

이유는 현재 파서가 일반 목록을 속성보다 먼저 판정하기 때문이다. `- 설명:`, `- 날짜:`, `- 자료:`가 모두 새 Item으로 만들어지고, 날짜·URL은 그 가짜 Item의 일정과 자료로 다시 추출된다.

따라서 UI 예제만 바꾸면 안 된다. parser, writer, supported Markdown parser, round-trip, grammar version, 도움말, 27개 fixture와 테스트를 하나의 변경으로 다뤄야 한다.

## 2. 권장 문법 v2 후보

```markdown
# 행사 준비
- 기준일: 2026-08-10

## 준비
- [ ] 장소 확인
  - 설명: 행사 장소에 예약 가능 여부를 확인합니다.
  - 상대 날짜: D-3
  - 시간: 09:00
  - 소요 시간: 30분
  - 장소: 행사장
  - 완료 기준: 예약 가능 여부를 기록합니다.
  - 반복: 매주 월요일
  - 조건: 비가 오면 실내 장소를 확인합니다.
  - 자료: [장소 안내](https://example.com/place)

이 줄은 구조 표식이 없으므로 원문 텍스트로 남습니다.
```

### 표식의 역할

| 표식 | 의미 | 규칙 |
|---|---|---|
| `#` | Flow 제목 | 문서당 1개 |
| `- 기준일:` | Flow 단위 기준 날짜 | 절대 날짜 `YYYY-MM-DD`; 상대 날짜 계산에 사용 |
| `##` | Step | 포함 관계의 큰 구획 |
| `- [ ]` | 실행 Item | 작성 순서가 기본 순서 |
| `  - 속성: 값` | 바로 위 Item의 속성 | 공백 2칸 이상 + 체크박스 없음 + 공식 속성명 |
| 표식 없는 문장 | 원문 텍스트 | Item으로 자동 생성하지 않음 |

### 파서 우선순위

1. 제목·Step·표·CSV/TSV/Markdown table
2. Flow 단위 공식 필드 `- 기준일:`
3. 들여쓴 공식 속성 `  - 속성: 값`
4. 들여쓴 미정 `  - 알 수 없는 키: 값`을 issue로 보존
5. 일반 Item 목록
6. v1의 대시 없는 속성을 읽기 전용 호환으로 수용
7. 나머지 일반 문장은 원문 텍스트로 보존

### 소유권과 모호성

- 들여쓴 속성은 직전 Item이 있을 때만 그 Item에 귀속한다.
- `  - [ ] 하위 작업`은 v2에서 임의 평탄화하지 않는다. 지원할 때까지 `unsupported_nested_item` issue로 보존한다.
- `  - 책: 읽기`처럼 공식 속성이 아닌 colon bullet은 새 Item이나 속성으로 추정하지 않고 `unknown_property` issue로 남긴다.
- 기존 `  설명:` 입력은 읽을 수 있지만 writer는 항상 `  - 설명:`으로 정규화한다.
- 속성 bullet 수는 canonical Item 수를 절대 늘리지 않는다.

## 3. 사용자 피드백 10개에 대한 결정안

| # | 관찰 | 원인 | 권장 변경 | 완료 기준 |
|---:|---|---|---|---|
| 1 | `- 설명:`처럼 구조 표식 필요 | 현재 속성만 Markdown 목록이 아님 | v2의 모든 Item 속성을 들여쓴 bullet로 통일 | 속성 1~N개를 추가해도 Item 수 불변 |
| 2 | 날짜·D-Day 순서가 입력과 결과에서 다름 | Calendar 행도 원문 순서를 그대로 사용 | Calendar는 계산 날짜 오름차순, Todo·표·텍스트는 작성 순서. 차이가 날 때 `입력도 이 순서로 맞추기` 표시 | 클릭 시 같은 Step 안 Item 블록만 재정렬, 원문·모든 결과 동시 반영, 되돌리기 제공 |
| 3 | Sheet의 정체성이 없음 | 일반 목록도 Sheet 가능, 열이 지나치게 일반적 | 이름을 `표/엑셀`로 하고, 원본 표 또는 2개 이상의 반복 필드·열이 있을 때만 활성화 | 목록만 있는 예시는 비활성; 표 예시는 실제 열 머리글과 URL 열 표시 |
| 4 | 상대 날짜 기준일이 갑자기 나타남 | 기준일이 입력문과 분리된 UI 상태처럼 보임 | `- 기준일: YYYY-MM-DD`를 원문에 명시. UI 입력도 이 줄을 추가·수정 | 기준일 없으면 Calendar 비활성; UI로 설정하면 원문에 즉시 반영 |
| 5 | 결과 형태 버튼 위치가 이동 | 가능한 추천만 필터링해 렌더링 | 고정 슬롯·고정 순서로 렌더링하고 조건 미충족은 disabled | 입력이 바뀌어도 버튼 위치·폭 불변, 비활성 이유는 `?` 또는 tooltip |
| 6 | `정리 메모`의 의미가 불명 | 원문과 정리된 산출물의 경계가 흐림 | `텍스트` 결과 안에 `원문 그대로`와 `정리된 TXT/Markdown`을 분리 | 두 복사 결과가 무엇을 보존/변환하는지 한 줄로 식별 |
| 7 | 링크·상세가 미리보기에 안 보임 | 결과 행이 제목·날짜 중심 | 설명, 완료 기준, 날짜·시간·장소, 링크를 결과별 자연스러운 위치에 시각화 | Calendar 상세, 체크 하위정보, 표 URL 열, 텍스트 Markdown 링크로 확인 가능 |
| 8 | 탭·표·CSV·Markdown의 등장 이유 불명 | 입력 구조와 파일 형식을 같은 층위에 노출 | 첫 화면에서 숨기고 `표 붙여넣기` 또는 내보내기 형식 안에서만 설명 | 일반 문법 도움말에는 기술 형식명이 없음 |
| 9 | 사용자가 순서 번호를 써야 하는지 불명 | 표 미리보기의 자동 번호와 입력 형식이 혼재 | 번호 입력 불필요. Item 작성 순서로 자동 번호 표시 | `1.`, `2)`는 가져오기 호환만 지원하고 writer는 `- [ ]`로 정규화 |
| 10 | `나눈 항목`의 목적이 불명 | 내부 파싱 용어가 사용자 과업을 설명하지 못함 | `항목 구조`로 이름 변경하고 기본은 읽기 전용 요약. 분리·병합은 `구조 수정`을 눌렀을 때만 표시 | 첫 화면에 이동·합치기·나누기 설명이 반복되지 않음 |

## 4. 추가로 찾은 개선점

### A. 표식 없는 일반 문장의 자동 Item화

현재 구현은 설명 문장이나 쉼표로 나뉜 메모를 행동처럼 추정할 수 있다. 새 원칙과 충돌한다.

- 기본 저작 모드: 명시적 `- [ ]`만 Item으로 만든다.
- 복붙 가져오기 모드: 후보 분할을 제안할 수 있지만 사용자가 확인하기 전에는 canonical Item이 아니다.
- URL만 붙인 입력, 모호한 날짜, 설명 문장은 원문+issue로 남긴다.

### B. Calendar 표시 순서와 원문 순서가 같은 축으로 취급됨

현재 Calendar row와 ICS 순서는 입력 Item 순서이며, `dateRange`만 날짜 정렬이다.

- Calendar 화면·ICS 미리보기: 계산된 날짜 오름차순, 같은 날짜는 작성 순서
- canonical·체크/할 일·표·텍스트: 작성 순서
- `입력도 이 순서로 맞추기`: 사용자가 명시적으로 눌렀을 때만 원문을 재작성
- D-Day 기준일 없음: Calendar는 만들지 않되 D-30 → D-Day → D+3의 상대 순서는 안내할 수 있음
- 날짜 없음: 정렬 시 마지막, 서로 간 작성 순서 유지

### C. `할 일`과 `체크`가 같은 축인지 불분명

현재 Text Authoring 산출물 계약에는 calendar/todo/sheet/memo 네 종류가 있고, `internal_check`는 FlowMe 안의 실행 목적이다. 이를 다섯 개 동급 결과 버튼으로 보이면 중복이 된다.

Phase 1 권장 결과 형태는 다음 네 개다.

1. 캘린더
2. 체크/할 일
3. 표/엑셀
4. 텍스트

추후 분리한다면 `체크`는 FlowMe 안에서 실행, `할 일`은 외부 할 일 앱 내보내기로 서로 다른 층위에 배치해야 한다.

### D. 예제와 QA 정보가 제품 UI를 점유함

- 27개 예제 전체는 데모·QA에서만 유지한다.
- 실제 저작 화면은 `예시 불러오기` 하나와 최근/대표 예제 3~5개만 둔다.
- `27/27 통과`, source row, projection 같은 내부 표현은 사용자 화면에 노출하지 않는다.

### E. 고급 제어가 첫 화면에 너무 많음

소유권, 원문 메타, 분리·병합·역할, 반복 경고, preflight, export 세부 형식은 필요할 때 펼친다. 첫 화면은 다음 작업만 남긴다.

1. 텍스트 입력
2. 항목 구조 확인
3. 결과 형태 선택
4. 저장/복사/내보내기

### F. 짧은 모바일에서 도구가 본문을 밀어냄

실제 390x600 화면에서 순서 도구를 열면 Item 영역이 사실상 한 줄만 남았고, 닫아도 약 3개만 보였다. 결과 저장 버튼 문구와 상단 빠른 예시 링크도 일부 잘렸다.

- 구조 편집 도구는 모바일에서 inline 확장 대신 별도 drawer 또는 sheet로 연다.
- 빠른 예시 링크 여러 개를 없애고 하나의 예시 선택기로 합친다.
- 하단 행동은 문구가 잘리지 않고 콘텐츠를 가리지 않을 때만 고정한다.
- 390x600에서는 입력·구조·결과 탭 각각의 마지막 요소, 결과 형태 네 슬롯, 복사/저장 행동까지 도달해야 한다.

## 5. 목표 화면 구조

### 데스크톱

```text
[예시 불러오기]                                       [? 문법]
┌ 입력 ─────────────────┬ 항목 구조 ────────────────┬ 결과 ─────────────┐
│ 원문 textarea         │ Step / Item 읽기 요약     │ 고정 결과 버튼 4개 │
│ 즉시 반영             │ [구조 수정] 때만 편집     │ 선택 결과 미리보기 │
│ 필요할 때 정렬 제안   │ issue만 눈에 띄게         │ 링크·상세 포함      │
└───────────────────────┴───────────────────────────┴───────────────────┘
```

### 모바일

```text
[입력] [구조] [결과]  <- 고정 탭, 위치 불변
현재 탭 내용만 표시
하단 주요 행동은 내용을 가리지 않음
각 탭은 390x600에서도 끝까지 스크롤 가능
```

## 6. 구현 순서

1. 문법 v2 계약·버전과 호환 정책을 테스트로 먼저 고정
2. parser의 속성 우선순위와 plain-text 보존 수정
3. writer·supported parser·round-trip 동시 수정
4. 27개 fixture를 v2로 변환하고 새 경계 시나리오 추가
5. 정렬 projection과 원문 재정렬 operation 분리
6. 결과 형태 고정 슬롯과 비활성 이유 구현
7. Sheet eligibility·열·링크/상세 preview 개선
8. 구조 Pane과 도움말을 단순화
9. standalone HTML 재생성
10. 데스크톱·모바일·짧은 화면 내부 QA 및 근거 저장

## 7. 출시 금지 조건

- 속성 bullet이 Item 수를 늘림
- 새 writer 결과를 다시 읽을 때 필드·링크·날짜가 사라짐
- 기준일 없이 실제 날짜를 추정함
- Calendar 정렬이 원문을 자동으로 바꿈
- 결과 형태 버튼 위치가 입력에 따라 이동함
- 일반 목록만으로 표/엑셀이 활성화됨
- 390x600 또는 360x640에서 끝까지 스크롤할 수 없음
- 내부 자동 QA를 사용자 검증으로 표기함

## 8. 검증 상태 표현

- `자동 시뮬레이션 통과`: 정해진 입력과 기대 결과가 코드에서 일치함
- `브라우저 내부 QA 통과`: 지정 화면 크기에서 클릭·스크롤·표시를 자동 확인함
- `사용자 검증`: 실제 사용자가 과업을 수행하고 관찰한 경우에만 사용함

이번 패키지는 앞의 두 가지를 준비하기 위한 것이며 사용자 검증 범위는 제외한다.
