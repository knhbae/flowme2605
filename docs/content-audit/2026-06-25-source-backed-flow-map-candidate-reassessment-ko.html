이번 결론

홈 대표

moving-d30만 명확한 대표 기준선이다. middle-school-math-1은 Flow Map 구조 후보로 홈에 남기되, 후보 성격을 제품 내부에서만 관리한다.

홈 제외

baby-health-schedule은 사용자가 저장할 이유는 있지만 현재 Step 정보가 얕다. 나머지 5개 확장 후보는 Park/Reject로 내리고 대표로 보이지 않게 한다.

기존 Flow

기존 단일 Flow는 source-fit 감사 90개 중 15개만 대표 가능으로 남긴다. 홈/대표 화면에는 별도 기준선 Flow만 보여주고, preview·review 후보는 섞지 않는다.

사용자 화면

설명글을 줄이고 원문 → 저장 산출물 → 첫 실행만 보여준다. 평가 점수, PRD, 후보 판정, 개발자 문구는 사용자 화면에 넣지 않는다.

서비스 노출 정책

사용자 홈

저장 이유와 산출물이 분명한 2개만 노출한다. 현재는 이사 D-30, 중1 수학 목차 진도.

직접 라우트

Revise/Park 후보는 링크로 테스트 가능하지만 대표 사례처럼 묶지 않는다.

내부 리포트

후보 판정, 점수, 리스크, Creator gate 설계는 이 레이어에서만 관리한다.

대표 노출 조건 one primary source -> one clear user job -> one natural artifact -> minimal execution UI -> save/revisit reason

사용자 화면 정리 원칙

남길 것

원문 제목, 저장되는 산출물, 필요한 입력, 첫 실행 Step, Step 안 Item, 원문 링크, 짧은 메모.

뺄 것

후보 판정, 점수, PRD, source-fit, 개발자/리뷰 문구, "왜 이 PoC가 좋은지" 설명.

미룰 것

세부 편집, 반복 규칙 고급 설정, Creator 승인 워크플로, 대량 candidate browsing.

홈 카드도 이 원칙에 맞춰 homepageEligible인 후보만 렌더링하고, 사용자 문구에서는 "대표 후보" 같은 검토 표현을 제거했다.

Creator publish gate 다음 설계안

Creator 화면의 핵심은 "내 원문 row가 어떤 Step/Item으로 바뀌었는지"를 확인하는 것이다. 제작자에게는 검토 게이트가 보여야 하지만, 공개 사용자 화면에는 실행 산출물만 보여야 한다.

Creator publish gate v1 1. Source URL 입력 2. 원문 row 추출: 제목 / 설명 / 원문 위치 / 위험도 3. Step preview: Step 제목 / destination / 날짜·반복·진도 여부 4. Item preview: FlowMe 체크리스트 + 외부 앱 text fallback 5. 차단 조건: source 없음 / Item 없음 / 민감 판단 포함 / 입력 과다 6. 공개 preview: 사용자에게 보이는 저장 화면만 확인 7. My Flow preview: 저장 후 실행 화면만 확인 8. 발행: 대표 노출이 아니라 direct route 또는 review 상태부터 시작
제작자에게 보일 것

원문 근거, 변환 row, publish blocker, 수정 가능한 Step 제목·destination·fallback text.

사용자에게 보일 것

무엇이 저장되는지, 오늘 또는 다음에 무엇을 하면 되는지, 원문을 어디서 다시 보는지.

운영자가 볼 것

후보 상태, 홈 노출 여부, route 유지 여부, 대표 후보 승격 조건.

다음 작업

1순위

baby-health-schedule 재작성 여부 결정. 공식 표를 기반으로 실제 정보성 있는 Step/Item을 다시 만들 수 없으면 대표 후보에서 계속 제외한다.

2순위

홈/공개 화면의 설명글을 더 줄이고, 저장 후 My Flow에서 Step detail이 바로 이해되는지 모바일 리허설을 반복한다.

3순위

Creator publish gate를 실제 화면으로 만들기 전에, source row → Step/Item 변환 표를 먼저 고정한다.

금지

새 카테고리 수를 늘리기 위해 약한 원문을 UI로 포장하지 않는다. 텍스트 모델이 통과하기 전 UI를 만들지 않는다.
