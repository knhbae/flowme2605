# P22-06 완료 Flow 재사용·버전 갱신 정책

작성일: 2026-07-11

상태: **정책 확정, Slice A 저장 계약 구현 완료**

범위: 완료된 Flow의 재사용, 새 실행 분리, 원본 버전 갱신과 개인 수정본 충돌 처리

## 1. 결론

완료한 Flow를 다시 사용할 때는 기존 진행 상태를 초기화해서 덮어쓰지 않는다. **지난 실행을 읽기 전용 기록으로 보존하고 새 실행을 별도 인스턴스로 만든다.** 사용자는 아래 세 경우 중 하나를 고른다.

1. `그대로 다시 쓰기`: 현재 항목 구성과 내 수정 내용을 새 실행에 복사한다.
2. `날짜만 새로 잡기`: 현재 구성과 내 수정 내용을 유지하면서 새 기준일로 상대 일정을 다시 계산한다.
3. `새 내용 검토`: 원본의 새 버전과 내 사본 차이를 확인한 뒤 새 실행에 반영할 내용을 선택한다.

자동 병합, 복잡한 버전 트리, 공개 리뷰, Studio의 핵심 탭 승격은 이번 정책 밖이다.

## 2. 사용자 문제

현재 제품은 중복 저장을 막고 완료 상태를 보여주지만, 완료 뒤 다시 사용할 때 다음 질문에 답하지 못한다.

- 지난번 완료 기록을 남긴 채 새로 시작할 수 있는가?
- 이사일이나 학습 시작일만 바꾸면 전체 일정은 어떻게 움직이는가?
- 내가 바꾼 제목·날짜·메모와 원본의 새 버전이 겹치면 무엇이 우선하는가?
- 새 원본을 쓰지 않고 내 현재 사본을 계속 사용할 수 있는가?
- 완료 후 남긴 회고와 원본 내용 알리기는 새 실행에도 복사되는가?

이 질문을 정하지 않은 채 `다시 시작`을 구현하면 과거 완료 상태, 개인 수정본, 원본 버전 중 하나를 조용히 잃을 수 있다.

## 3. 현재 코드가 증명하는 제약

### 3.1 실행 상태는 Flow slug 하나에 묶여 있다

`lib/flow/storage.ts`의 저장·완료 상태는 실행 인스턴스가 아니라 Flow slug를 키로 사용한다.

- 저장 기록: `flow:saved:<slug>`
- 완료 체크: `flow_builder_mvp_checks_<slug>`
- 기준일: `flow:<slug>:anchorDate`
- 항목 상태: `flow_builder_mvp_item_state_<slug>`
- 완료 회고·원본 내용 알리기: `flow:my-flow:completion-feedback:<slug>`

`saveFlowRecord()`는 같은 slug의 `savedAt`, 기준일, 결과물 형식을 덮어쓴다. `clearFlowLocalProgress()`는 완료 체크, 기준일, 항목 상태, 완료 회고까지 함께 지운다. 현재 구조에는 `runId`, 과거 실행 목록, 완료 실행 snapshot이 없다.

따라서 기존 key를 초기화하는 방식의 재사용은 **완료 기록 보존** 요구를 충족하지 못한다.

### 3.2 원본 버전과 개인 수정본은 이미 분리돼 있다

`lib/flow/source-backed-my-flow.ts`의 saved snapshot은 다음을 보존한다.

- 원본 Map `version`
- Flow 목록과 항목 수
- 출처 확인일과 위험도
- 기준일
- 선택한 항목과 제외한 항목
- 항목 제목 alias, 고정 날짜 override, 사용자 메모

`assessSourceBackedFlowMapUpdate()`는 저장 버전과 현재 버전, Flow 구성, 항목 수, 출처 확인일을 비교한다. 공식·민감 일정은 변경 내용을 사용자가 확인하도록 이미 분류한다. 다만 이 평가는 **업데이트가 있다는 사실**만 판정하며, 완료 실행과 새 실행을 분리하거나 개인 수정 충돌을 해결하지는 않는다.

### 3.3 완료 회고는 새 실행의 기본값이 아니다

P22-01/P22-02에서 분리한 `내 실행 회고`와 `원본 내용 알리기`는 완료한 경험에서 생긴 기록이다. 새 실행으로 복사하면 과거 경험과 새 경험이 섞인다. 둘 다 과거 실행에 남기고 새 실행은 빈 상태로 시작해야 한다.

## 4. 제품 모델

### 4.1 네 가지 객체를 분리한다

| 객체 | 의미 | 변경 가능 여부 |
| --- | --- | --- |
| 원본 Flow 버전 | 제작자·공식 출처에서 발행한 기준 내용 | 사용자가 직접 덮어쓰지 않음 |
| 개인 사본 | 포함 항목, 제목 alias, 날짜 override, 사용자 메모 | 사용자가 수정 가능 |
| 실행 인스턴스 | 특정 기준일로 실제 수행하는 한 번의 실행 | 진행 중에 완료·메모 변경 가능 |
| 완료 실행 기록 | 종료된 실행의 기준일, 개인 사본 snapshot, 완료 상태, 회고 | 읽기 전용 |

사용자 화면에는 `인스턴스`, `snapshot`, `overlay`, `source-backed` 같은 용어를 쓰지 않는다. 화면에서는 `지난 실행`, `새로 시작`, `내가 바꾼 내용`, `새 내용`으로 표현한다.

### 4.2 다음 구현에서 필요한 최소 내부 식별자

아래는 구현 방향을 고정하기 위한 제안이며 이번 slice에서 스키마를 추가하지 않는다.

```ts
type FlowRunRecord = {
  runId: string;
  flowSlug: string;
  mapId?: string;
  sourceVersion?: string;
  status: 'active' | 'completed' | 'archived';
  startedAt: string;
  completedAt?: string;
  anchor?: string;
  previousRunId?: string;
  reuseMode?: 'same_copy' | 'new_anchor' | 'reviewed_version';
  personalCopySnapshot?: SourceBackedFlowMapPersonalCopy;
};
```

완료 체크, 항목 상태, 회고, 원본 내용 알리기도 장기적으로 `slug`가 아니라 `runId`에 연결해야 한다. 완료 당시 원본 버전과 개인 사본 snapshot을 함께 남겨야 지난 실행을 나중에 열어도 내용이 바뀌지 않는다.

## 5. 세 가지 재사용 정책

### 5.1 그대로 다시 쓰기

사용자 의미: `지난번에 쓰던 구성으로 새로 시작합니다.`

새 실행에 복사하는 것:

- 포함·제외한 항목
- 제목 alias
- 사용자 메모
- 결과물 형식 선택
- 원본 버전 참조

복사하지 않는 것:

- 완료 체크와 하위 확인 항목 상태
- 완료 시각과 지난 진행률
- 내 실행 회고
- 원본 내용 알리기 초안
- 지난 실행 중 발생한 일회성 상태

날짜 정책:

- 날짜가 없는 체크 Flow는 바로 새 실행을 만들 수 있다.
- 이사·시험처럼 기준일이 필요한 Flow는 같은 과거 날짜로 조용히 시작하지 않는다. `날짜만 새로 잡기` 단계로 이어져 새 이사일·시험일·시작일을 확인해야 한다.

### 5.2 날짜만 새로 잡기

사용자 의미: `내용은 유지하고 새 기준일에 맞춰 일정을 다시 잡습니다.`

규칙:

- Flow 기준일을 새로 저장한다.
- 상대 일정은 새 기준일에서 다시 계산한다.
- 포함·제외 항목, 제목 alias, 사용자 메모는 유지한다.
- 완료 체크와 진행 상태는 빈 상태로 시작한다.
- 과거 실행의 캘린더·완료 기록은 변경하지 않는다.

개별 날짜 override가 있으면 자동으로 결정하지 않는다. 새 실행을 만들기 전에 개수를 알려주고 아래 중 하나를 명시적으로 고르게 한다.

1. `새 기준일에 맞추기`: 개별 고정 날짜를 지우고 원본 상대 일정으로 다시 계산한다.
2. `기존 날짜 유지`: 사용자가 직접 정한 절대 날짜를 그대로 복사한다.

Flow마다 다른 기본값을 몰래 적용하지 않는다. 특히 이미 지난 날짜가 포함되면 경고만 보여주고 사용자 선택을 요구한다.

### 5.3 새 내용 검토

사용자 의미: `원본에 바뀐 내용이 있어 내 사본과 비교합니다.`

진입 조건:

- 저장된 `sourceVersion`과 현재 발행 버전이 다름
- Flow 구성, 항목 수, 출처 확인일 중 하나가 바뀜
- 공식·민감 일정의 출처 내용이 갱신됨

기본 원칙:

- 새 버전을 자동 적용하지 않는다.
- 기존 완료 실행은 항상 이전 버전으로 남긴다.
- 새 실행을 만들 때만 새 버전을 선택할 수 있다.
- 개인 수정이 없는 안전한 변경도 사용자에게 `새 내용 있음`을 알리고 선택을 받는다. 코드의 `canApplyAutomatically`는 기술적 안전성 판정일 뿐, 백그라운드 자동 적용 허가가 아니다.

## 6. 원본 변경과 개인 수정 충돌 규칙

| 원본 변화 | 개인 수정 상태 | 새 실행 기본 처리 | 사용자 선택 |
| --- | --- | --- | --- |
| 항목 변화 없음 | 개인 수정 있음 | 개인 수정 유지 | 선택 불필요 |
| 같은 안정 ID의 제목·설명 변경 | alias·메모 없음 | 새 내용 사용 가능 | `새 내용 사용` / `현재 내용 유지` |
| 같은 안정 ID의 제목·설명 변경 | alias 또는 메모 있음 | 자동 병합 금지 | 원본 새 내용과 내 수정 비교 후 선택 |
| 새 항목 추가 | 해당 없음 | 자동 활성화하지 않고 검토 목록에 둠 | `새 실행에 추가` / `이번에는 제외` |
| 원본 항목 삭제 | 개인 수정 없음 | 새 실행에서 제외 제안 | `제외` / `내 항목으로 유지` |
| 원본 항목 삭제 | alias·날짜·메모 있음 | 개인 전용 항목으로 보존 제안 | `내 항목으로 유지` / `제외` |
| 기준 일정 변경 | 개별 날짜 override 없음 | 새 기준에 맞춰 계산 | 변경 요약 확인 |
| 기준 일정 변경 | 개별 날짜 override 있음 | 자동 결정 금지 | `새 기준에 맞추기` / `내 날짜 유지` |
| 공식·민감 Flow 변경 | 수정 유무와 무관 | 항상 검토 필요 | 변경 내용 확인 후 적용 또는 현재 사본 유지 |

항목 연결에는 제목 문자열이 아니라 안정 item ID가 필요하다. ID가 바뀌어 같은 항목인지 확신할 수 없으면 자동 매칭하지 않고 `연결 확인 필요`로 분류한다.

## 7. 완료 기록 보존 정책

완료 실행에는 최소한 다음을 고정한다.

- Flow와 Map 식별자
- 사용한 원본 버전
- 실행 시작일과 완료일
- 기준일
- 실행 당시 개인 사본 snapshot
- 완료·건너뜀·하위 확인 상태
- 사용자 메모
- 완료 회고
- 원본 내용 알리기 초안과 전송 상태

새 실행을 만들어도 과거 실행의 Calendar projection과 export 재생성 기준이 바뀌지 않아야 한다. 원본이 사라져도 완료 기록은 마지막 snapshot으로 읽을 수 있어야 한다.

현재 localStorage의 slug key만으로는 이를 보장할 수 없다. 실행 인스턴스 도입 전에는 사용자 화면에 `다시 쓰기`를 추가하지 않는다.

## 8. 사용자 흐름과 화면 위계

### 완료된 My Flow

1. 완료 상태와 지난 회고를 먼저 보여준다.
2. `다시 쓰기`는 완료 기록 아래의 2차 행동으로 둔다.
3. 누르면 세 선택을 한 sheet에서 보여준다.
4. 선택을 마친 뒤 새 실행을 만들고 My Flow의 오늘/다음 영역으로 이동한다.

권장 문구:

- `그대로 다시 쓰기` — `내가 고친 내용은 유지하고 완료 상태만 새로 시작해요.`
- `날짜만 새로 잡기` — `새 이사일·시험일·시작일에 맞춰 일정을 다시 잡아요.`
- `새 내용 검토` — `원본에 바뀐 내용을 확인하고 내 사본에 반영할지 고릅니다.`

### Studio

Studio는 4탭 IA 밖의 보조 표면을 유지한다.

- 새 버전이 있을 때 비교 대기 항목을 모아볼 수 있다.
- My Flow의 `새 내용 검토`에서 필요할 때만 연결한다.
- `다시 쓰기`의 필수 경로로 만들지 않는다.
- 발행, 공개 리뷰, 팔로워, 자동 병합을 추가하지 않는다.

## 9. 상태 전이

```text
진행 중
  -> 완료
  -> 지난 실행(읽기 전용)

지난 실행
  -> 그대로 다시 쓰기
  -> 날짜만 새로 잡기
  -> 새 내용 검토

세 선택 모두
  -> 새 실행 생성
  -> My Flow 오늘/다음 실행으로 이동

원본 버전 변경만으로
  -> 진행 중 실행이나 지난 실행을 자동 변경하지 않음
```

## 10. 구현 순서

### Slice A. 실행 인스턴스와 과거 기록 보존

- `runId` 기반 active/completed record 도입
- 기존 slug 기반 상태를 첫 active run으로 읽는 migration adapter
- 완료 시 읽기 전용 snapshot 생성
- 새 실행 생성 시 완료 상태와 회고가 복사되지 않는 단위 테스트

### Slice B. 날짜만 새로 잡기

- Flow 기준일 재계산
- 개별 고정 날짜 `새 기준에 맞추기 / 기존 날짜 유지` 선택
- Calendar·export가 새 실행만 읽는 projection 테스트

### Slice C. 새 버전 검토

- 안정 ID 기반 changed/added/removed 분류
- 개인 수정 충돌 표시
- 공식·민감 Flow 항상 검토
- 선택 결과로 새 실행 생성

### Slice D. 화면 연결

- 완료된 My Flow의 2차 `다시 쓰기`
- 모바일 390px과 wide 1024px sheet 검증
- Studio는 비교 대기 보조 선반만 유지

Slice A가 끝나기 전 Slice D를 먼저 구현하지 않는다.

## 11. Acceptance criteria

### 완료 기록 보존

- 새 실행을 만들어도 지난 완료 체크, 완료일, 회고, 원본 내용 알리기가 변하지 않는다.
- 지난 실행과 새 실행이 서로 다른 `runId`를 가진다.
- 새 실행의 완료 상태는 0에서 시작한다.

### 날짜 재사용

- 날짜형 Flow는 새 기준일 확인 없이 과거 날짜로 다시 시작하지 않는다.
- 상대 일정은 새 기준일로 재계산된다.
- 개별 날짜 override가 있으면 유지·재계산을 사용자가 고른다.

### 버전 갱신

- 기존 완료 실행은 저장 당시 원본 버전을 유지한다.
- 개인 수정과 원본 변경이 겹치면 자동 병합하지 않는다.
- 추가·삭제·변경 항목을 구분해 명시적으로 선택할 수 있다.
- 공식·민감 Flow는 항상 변경 검토를 거친다.

### IA와 copy

- Studio는 5번째 탭이 아니다.
- `run`, `snapshot`, `overlay`, `source-backed`, `Step`, `Item`, `version tree`를 사용자 화면에 노출하지 않는다.
- 다시 쓰기 행동이 완료 회고나 오늘 실행보다 강한 1차 CTA가 되지 않는다.

## 16. 2026-07-11 Slice A 구현 결과

`lib/flow/storage.ts`에 기존 화면 projection을 바꾸지 않는 opt-in run registry를 추가했다.

- `flow:run-registry:<slug>` versioned registry
- legacy slug 상태를 첫 active run으로 승격하는 `ensureLegacyActiveFlowRun()`
- 완료 당시 상태를 snapshot으로 고정하는 `completeActiveFlowRun()`
- 완료 기록을 남기고 새 current state만 비우는 `startFlowRunFromCompleted()`
- 완료 뒤 작성한 회고·원본 내용 알리기 초안을 최근 완료 run에 동기화
- source version, personal copy, anchor, 결과물 형식 보존
- 완료 체크, 항목 상태, 하위 확인, 비교표, workbench, reaction log, 완료 feedback 보존
- `new_anchor` mode에서 새 기준일이 없으면 시작을 거부
- 명시적 저장 기록 삭제 시 run registry도 함께 삭제

현재 My Flow·Calendar·export 호출부는 run API를 아직 사용하지 않는다. 따라서 기존 사용자 상태가 자동 migration되거나 화면에 `다시 쓰기`가 나타나지는 않는다. 이 경계는 데이터 모델을 먼저 검증하고 사용자 흐름을 나중에 여는 의도된 순서다.

검증 evidence는 [P22-06A Flow run storage evidence](./2026-07-11-claude-design-p22-06a-flow-run-storage-evidence/README.md)에 기록했다.
