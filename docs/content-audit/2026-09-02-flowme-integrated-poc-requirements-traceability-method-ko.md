# FlowMe 통합 PoC 요구사항 추적 방법

- 작성일: 2026-09-02
- 대상: 개인공간 v4.1, 개발 1, 개발 2의 세 결과물
- 목적: 과거 화면·대화·결정을 현재 통합 PoC의 화면·코드·테스트 증거와 한 행씩 대조
- 적용 범위: 현재 격리 PoC와 로컬 검증물
- 비적용 범위: 운영 schema 승인, 배포, 실제 기기·관찰 사용자 검증 대체

## 1. 세 결과물과 보조 근거

세 결과물은 같은 비중으로 추적한다.

| 코드 | 결과물 | 1차 근거 | 통합에서 맡는 역할 |
| --- | --- | --- | --- |
| `V41` | 개인공간 v4.1 UX/UI | v4.1 spec, 조작형 HTML, QA와 화면 캡처 | 폴더·기간·QuickItem·이동·완료 화면 문법 |
| `D1` | 개발 1 | `D1 baseline session`, My/Public Plan 편집·lifecycle 정본과 현재 main | 네 saved-plan origin, 공통 상세·편집·뒤로가기·보관·복구 owner |
| `D2` | 개발 2 | `D2 baseline session`, Text Authoring 정본과 후속 작성 틀 결정 | 일반 텍스트 작성, 구조 확인·수정, 결과·저장 영수증 |

통합 blueprint는 네 번째 결과물이 아니다. 세 결과물 사이의 연결 순서, 데이터
소유권, PoC 격리 조건을 판정하는 교차 기준으로만 쓴다.

## 2. 요구사항 원자화

한 부모 행에는 사용자가 화면이나 저장 결과에서 구분할 수 있는 기능 또는 계약 하나만
둔다. 원문이 여러 acceptance 조건을 하나의 계약으로 묶은 경우에는 부모 행을 유지하되,
각 관찰 조건을 `.1`, `.2` 형식의 하위 판정으로 다시 나눈다. 다음 기본 분류를 사용한다.

- `화면`: 화면 구성, 정보 위계, 문구, 빈 상태
- `기능`: 생성·열기·이동·완료·저장·보관 같은 사용자 작업
- `상태`: 준비·저장 중·성공·같은 위치·실패·복구
- `전환`: 입력에서 구조, 구조에서 결과, 목록에서 상세처럼 화면 간 이동
- `데이터`: identity, 소유권, 저장 범위, 원본·개인 값 분리
- `반응형`: 390×844, 375×812, 844×390, 1024×768, 1440×900의 구성
- `접근성`: 키보드, 초점, 48px 대상, 비드래그 경로, 상태 알림
- `오류·복구`: 취소·Escape·pointer cancel·실패·Undo·reload·손상 payload
- `검증`: 자동 테스트, 브라우저, 실제 기기, 관찰 사용자, 게시 상태

`탐색`, `폴더`, `이동`, `완료`, `복구`는 기본 분류를 대체하는 enum이 아니라 화면·기능
영역을 빠르게 찾기 위한 보조 태그다.

한 문장이 여러 독립 조건을 포함하면 행을 나눈다. 반대로 같은 조건이 세 결과물에
반복돼도 원출처 행은 합치지 않는다. `연결 묶음`으로 서로 연관시키되, 어느
결과물에서 나온 요구인지 지우지 않는다.

## 3. 출처와 결정 상태

모든 행에 정확한 세션 ID나 파일 경로·절을 기록한다. 출처의 성격은 다음처럼
보존한다.

| 결정 상태 | 뜻 | 구현 판단 |
| --- | --- | --- |
| `확정` | 사용자 결정, released contract, 명시적 acceptance | PoC 경계 안이면 구현·검증 대상 |
| `PoC 임시` | 이번 실험에서만 쓰는 교체 가능한 기본값 | 운영 정책이나 schema로 승격 금지 |
| `제안` | 비교안·prototype 가설·사용자 검증 전 방향 | 구현됐어도 영구 결정으로 표현 금지 |
| `보류` | 다시 열 조건이 정해진 후속 범위 | 현재 미구현을 결함으로 과장하지 않음 |
| `제외` | 이번 PoC에서 명시적으로 하지 않는 일 | 구현하지 않고 경계를 검사 |
| `충돌` | 두 정본이 서로 다른 owner·화면·범위를 요구 | 사용자 또는 owner 결정 전 쓰기 금지 |
| `대체됨` | 후속 결정이 이전 안을 바꿈 | 현재 결함이 아니라 변경 장부에 남김 |
| `관찰` | 구현 결정이 아니라 증거 상태 | 자동 QA와 실제 사용자 증거를 분리 |

원출처의 표현은 그대로 보존한다. 보고서 필터에서는 `현행확정`과
`확정-소유권제한`을 `확정`, `PoC확정`을 `PoC 임시`, `후보구현`을 `제안`,
`결정필요`를 `충돌`처럼 위 분류로 정규화하고, 펼친 행에는 원래 표현도 함께 표시한다.

최신 사용자의 명시적 지시, 승인된 통합 blueprint, released contract, prototype
interaction contract, 검토 제안 순으로 적용한다. 상위 근거가 하위 근거를 바꾸면
원래 요구를 삭제하지 않고 `의도적 변경`으로 남긴다.

## 4. 현재 적용 판정

| 판정 | 적용 규칙 |
| --- | --- |
| `충족` | 요구의 모든 관찰 조건이 구현되고, 해당 위험에 맞는 실행 증거가 있음 |
| `부분` | 핵심 경로 일부는 있으나 하위 조건·화면·owner·증거가 빠짐 |
| `미충족` | 포함 범위의 요구가 현재 화면과 코드에 없음 |
| `의도적 변경` | 통합 결정 때문에 원안과 다르게 구현했으며 이유·대체 흐름이 명시됨 |
| `제외` | PoC 경계에서 명시적으로 하지 않기로 한 항목이며 금지 경계가 유지됨 |
| `결정 필요` | 제품 정책, 운영 writer, identity·migration처럼 새 권한·결정이 필요함 |

`코드가 존재한다`와 `사용자가 조작할 수 있다`를 분리한다. UI 요구는 화면에서
도달 가능해야 충족이고, 저장 요구는 성공·실패·reload를 포함한 증거가 있어야
충족이다. 독립 HTML fixture는 live 운영 origin을 읽는 React PoC의 증거를 대신하지
않는다.

## 5. 증거 등급

| 등급 | 증거 | 확인 범위 |
| --- | --- | --- |
| `E0` | 없음 | 미구현 또는 미검증 |
| `E1` | 문서·코드·정적 화면 | 계약·구현 위치만 확인 |
| `E2` | 순수 모델·컴포넌트 테스트 | 상태·identity·transition |
| `E3` | 브라우저 자동화·캡처 | route·조작·반응형·오류 로그 |
| `E4` | E1~E3와 회귀·build를 함께 확인 | 최종 verification manifest에 실행 시각·개수·결과가 있는 현재 worktree 근거 |
| `E5-D` | 실제 Android Chrome·iOS Safari | 실제 OS 제스처·safe area |
| `E5-U` | 관찰 사용자 과업 | 발견 가능성·이해·회복·효용 |

E3·E4를 실제 기기나 관찰 사용자 검증으로 표현하지 않는다.

## 6. 매트릭스 필드

각 요구에는 아래 값을 둔다.

```text
ID / 결과물 / 연결 묶음 / 분류 / 여정 단계 / 우선순위
원출처 / 결정 상태 / 당시 기대 화면·행동
현재 구현 위치 / 자동 테스트·브라우저 증거
판정 / 차이 원인 / 이번 수정 / 다음 조치 / 하위 관찰 조건
```

보고서는 결과물, 화면·여정, 분류, 판정, 정규화된 결정 상태, 우선순위로 필터링한다.
연결 묶음은 검색어로 찾는다. 데이터 owner는 별도 흐름으로 보여 준다. 모바일은 표를
카드로 바꾸고, 각 행에서 원출처·현재 증거·이번 수정·하위 판정을 함께 펼쳐 볼 수 있게 한다.

## 7. 구현과 의사결정 경계

확정 근거가 있고 PoC 전용 저장·화면 안에서 닫히는 P0/P1 누락은 이번 작업에서
고친다. 다음 항목은 보고서에서 `결정 필요`로 남기고 임의로 구현하지 않는다.

- 기존 운영 완료·메모·날짜·보관·export writer 호출
- 운영 schema·key migration과 dual read·rollback
- 공개 후보·immutable version·correction suggestion owner
- Text Authoring 구조 수정 값을 어느 저장 lane에 둘지 정하는 일
- teal v4.1 shell과 운영 main token의 영구 통합
- 실제 기기·관찰 사용자 결과를 추정하는 일

## 8. 완료 조건

- 세 결과물 모두 독립 필터와 요구 개수를 가진다.
- 모든 요구 행에 원출처·결정 상태·현재 증거·판정·다음 조치가 있다.
- 화면별 흐름과 데이터 owner 흐름을 따로 볼 수 있다.
- 이번에 고친 항목은 변경 전·후와 재검증 결과가 연결된다.
- 미충족, 의도적 변경, 제외, 결정 필요가 서로 섞이지 않는다.
- 자동 QA, 실제 기기, 관찰 사용자, commit·push·PR·Preview·Production을 분리한다.
