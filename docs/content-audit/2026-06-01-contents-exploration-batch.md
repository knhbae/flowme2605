## 학습 1 — 어떤 콘텐츠가 FLOW가 되기 좋은가
이번 배치를 만들며 다시 확인한 "좋은 FLOW 후보"의 신호:

1. **시점/주기가 분명하다.** 면접(D-3), 이사, 검진(D-7), 종소세(5월), 정기점검(6개월).
   → 캘린더/타임라인/루틴 구조로 자연스럽게 떨어진다.
2. **사용자가 이미 캘린더·시트·메모로 옮겨 실행한다.** 비상금 적립표, 구독 점검표,
   수면 관찰표는 "FLOW 안에서 보기"보다 "내 시트로 가져가기"가 진짜 행동이다(export-first).
3. **정보가 흩어져 있고 "빠뜨리면 손해"인 항목이 있다.** 전세 등기부 확인, 퇴사 시
   경력증명/이직확인서, 폰 교체 시 카톡 백업·OTP 재등록 — 한 번 빠뜨리면 비용이 크다.
4. **민감 영역은 공식 확인 질문과 경험 팁을 분리할 수 있어야 한다.** 건강·세무·계약은
   "Flow가 판단"하지 않고 "확인할 질문 + 공식 출처 + 경고"로 남길 수 있을 때만 후보가 된다.

반대로 **나쁜 후보**: 한 번 보고 끝나는 정보성 콘텐츠, 사용자 입력/산출물이 없는 글,
개인차가 너무 커서 체크리스트화하면 오히려 위험한 의료/법률 처방.

## 학습 2 — 어떻게 FLOW화하나 (저작 프롬프트 가설)
이번에 사용한 변환 패턴(다음 배치의 프롬프트 초안으로 승격 후보):

- **구조 먼저 정한다.** 시점 기반 → `timeline`(D-offset), 반복 → `routine`(@반복),
  순서 약함 → `checklist`. 단계(developmental) → `phase`.
- **첫 화면 = 첫 행동 + 자연 산출물.** 각 Flow의 primary_destination(calendar/sheet/memo)을
  먼저 정하고, 사용자가 손에 쥐고 나갈 산출물(캘린더/관찰표/제출 메모)을 1순위로 둔다.
- **항목은 "동사로 끝나는 한 줄 행동" + why/how/done/caution.** 파서가
  `why:/how:/done:/caution:/link:` 들여쓰기를 그대로 디테일 UI로 렌더링하므로,
  핵심 항목마다 "왜 빠뜨리면 안 되는지(why) / 어떻게(how) / 끝난 기준(done)"을 붙였다.
- **민감 영역은 경고(!)와 "확인 질문" 프레이밍.** 예: 건강검진은 결과 해석을 하지 않고
  "재검·진료 예약을 챙기는 준비용"으로, 수면은 "치료가 아니라 2주 관찰표"로 한정.

## 학습 3 — UX/UI
신규 UX는 만들지 않고 **기존 ArtifactWorkbench 시스템(ux12 계열)을 그대로 재사용**했다.
새 Flow는 기존 Flow와 동일한 데이터 형태(Flow/FlowSection/FlowItem/FlowItemDetail)라
별도 컴포넌트 없이 `/f/[slug]`에서 워크벤치·디테일·내보내기 UI가 그대로 렌더링된다.
검증: 프로덕션 서버에서 새 slug 4종이 HTTP 200, 제목·파싱 항목이 SSR HTML에 포함됨.

다음 UX 가설(아직 미구현, 다음 배치 후보):
- checklist형이 많아질수록 "오늘 할 N개"만 위로 끌어올리는 today-first 뷰가 필요할 수 있다.
- 관찰형(수면·식사·반려동물)은 routine의 회차 기록표 UX를 재사용하는 게 자연스럽다.

## 학습 4 — 사용자의 삶과 어떻게 연결되나
이번 배치는 "인생 이벤트의 그물"을 의도적으로 넓게 깔았다. 이사→자취 세팅→전세 계약,
이직→퇴사 인수인계→첫 출근, 출산→신생아 준비→어린이집 입소처럼 **하나의 생애 사건이
다음 Flow로 이어지는 연결**이 보인다. 이 연결이 실제로 사용자의 "다음 행동"을 만드는지는
관찰 세션에서 확인할 대상이며, 지금은 가설이다.
