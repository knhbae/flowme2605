FlowMe 사용자 피드백 및 제안 통합본
작성일: 2026-07-26

============================================================
1. 핵심 제품 방향
============================================================

FlowMe는 무거운 일정 관리 앱이나 모든 기능을 품은 planner가 아니다.

원문·URL·메모
→ 바로 쓸 수 있는 전체 Flow
→ 최소 개인화
→ 저장 및 실행
→ 완료·수정·복구
→ Calendar·Todo·Checklist·Sheet·Memo 등 외부 활용
→ 회고·수정·재사용

을 연결하는 portable execution layer여야 한다.

여러 콘텐츠 카테고리의 공통 구조는 통일하되, 이사·결혼·운동·여행·체크리스트·기록형 콘텐츠의 특성은 자연스러운 결과 형태에 반영해야 한다.

기능은 많이 추가됐지만 사용자가 계속 느끼는 핵심 문제는 다음과 같다.

- 설명이 너무 많고 화면이 길다.
- 카드와 명령이 많아 무엇부터 해야 할지 모르겠다.
- 콘텐츠마다 조작 방식과 화면 문법이 다르다.
- 저장 전에 무엇이 만들어질지 예측하기 어렵다.
- 저장 후 전체 Flow가 제대로 저장됐는지 확인하기 어렵다.
- My Flow가 가장 복잡하고 무엇을 보여주려는 화면인지 불명확하다.
- 필요한 기능이 있어도 발견하기 어렵거나 여러 화면에 흩어져 있다.
- 기능적 개선은 많았지만 상용 서비스 수준의 UX/UI 변화는 아직 부족하다.

필요하면 단순 수정에 머물지 말고 비교 prototype, 시뮬레이션, 테스트를 거쳐 화면 구조를 크게 다시 설계할 수 있어야 한다.

============================================================
2. 원하는 전체 사용자 여정
============================================================

1. 사용자가 URL, 메모, 기존 콘텐츠 또는 공개 Flow로 시작한다.
2. 저장 전에 실제로 만들어질 전체 Flow 결과를 먼저 본다.
3. 제목, 기준일, 항목 날짜, 내용, 순서, 포함 여부 등을 자연스럽게 조정한다.
4. Calendar, Todo, Checklist, Sheet, Memo 중 콘텐츠에 맞는 결과를 선택한다.
5. 저장 후 전체 Flow가 어떻게 저장됐는지 확인한다.
6. 오늘 할 일을 실행하고 완료한다.
7. 완료한 항목을 다시 미완료로 돌릴 수 있다.
8. 날짜 없는 항목에 날짜를 넣고, 바꾸고, 다시 날짜 없음으로 돌릴 수 있다.
9. 필요하면 시간, 예상 소요 시간, 반복 범위를 설정한다.
10. 개인 항목을 추가·삭제·복구·재정렬할 수 있다.
11. 전체 일정 또는 선택한 항목의 날짜를 함께 이동하고 되돌릴 수 있다.
12. My Flow와 Calendar가 같은 개인 수정본을 보여준다.
13. 전체·선택·현재 항목 범위로 외부 도구에 가져간다.
14. 실행 중에도 단계별 메모, 수정 의견, 보완 요청을 남길 수 있다.
15. Flow를 완료한 뒤 회고하고 새 실행으로 다시 사용한다.
16. 원본이 갱신돼도 개인 날짜·메모·완료·실행 기록은 보존한다.

저장 한 번으로 여정이 끝나면 안 된다. 발견, 개인화, 실행, 완료, 복구, 외부 활용, 회고, 재사용이 하나의 자연스러운 흐름으로 연결돼야 한다.

============================================================
3. 홈 탭
============================================================

- 홈과 Flow 찾기의 역할이 중복된다.
- 인기·최근 Flow 탐색은 Flow 찾기에 두는 편이 자연스럽다.
- 홈은 다른 사용자가 Flow를 어떻게 활용하는지, 어떤 상황에서 어떤 결과를 얻었는지 보여주는 역할을 검토할 수 있다.
- 긴 기능 설명보다 실제 결과, 출처, 사용 상황을 먼저 보여줘야 한다.
- “이사일 하나를 넣으면 D-30 일정...” 같은 긴 설명이 정말 필요한지 다시 검토해야 한다.
- 설명이 필요하더라도 첫 화면을 장악하지 않고 짧은 보조 정보로 내려야 한다.
- 홈과 Flow 찾기에서 같은 Flow 카드를 열면 동일한 canonical Flow 상세와 저장 결과로 이어져야 한다.
- 사용자 수, 리뷰 수, 검증 수는 실제 근거가 있을 때만 사용한다.
- 가짜 사용량, 평점, 리뷰를 실서비스 정보처럼 노출하지 않는다.

============================================================
4. Flow 찾기
============================================================

Flow 카드:

- 원문 출처는 실제 링크로 연결돼야 한다.
- 카드 안에 꼭 필요한 정보만 남겨야 한다.
- “이사일”, “D-30 일정”, “생활 일정”, “할 일 5개” 같은 정보가 선택 판단에 정말 필요한지 검토한다.
- 번호 뒤의 행동은 “Flow 열기”보다 “더보기” 또는 카드 전체 열기처럼 익숙한 방식이 적합한지 검토한다.
- 실제 이용자 수, 리뷰, 신뢰 정보가 있다면 선택 근거로 활용할 수 있다.
- 동일 콘텐츠가 홈, Flow 찾기, URL lookup에서 다른 제목·항목 수·저장 객체로 갈라지면 안 된다.

Flow 상세:

- 이사, 결혼, 운동마다 완전히 다른 조작 문법을 사용하지 않는다.
- 콘텐츠 특성은 살리되 헤더, 결과 미리보기, 조정, 저장, 가져가기의 기본 구조는 통일한다.
- 결혼처럼 여러 결과 형태가 있다면 긴 카드들을 모두 펼치지 않는다.
- 사용자가 하나의 형태를 먼저 선택하고 해당 흐름 안에서 미리보기, 조정, 저장을 진행하게 한다.
- “날짜 정하기”, “날짜 없이”, “예시만 보기”를 눌렀을 때 다음 행동과 저장 결과가 명확해야 한다.
- Calendar, Checklist, Sheet, Memo 등 결과 형태는 이름만 있는 탭이 아니라 실제 결과 예시로 보여준다.
- 지원되지 않거나 의미 없는 결과 형태는 숨긴다.
- 다섯 가지 결과를 모든 Flow에 강제로 제공하지 않는다.
- 콘텐츠별 primary 결과 하나와 가치 있는 secondary 결과 최대 두 개를 우선한다.

저장 전 조정:

- 현재의 포함·제외 중심 조정만으로는 부족하다.
- 제목, 기준일, 항목 날짜, 상세 내용, 메모, 순서 등을 자연스럽게 수정할 수 있어야 한다.
- 모든 고급 필드를 한 번에 펼치지 말고 progressive disclosure를 사용한다.
- 먼저 전체 Flow를 읽을 수 있게 하고, 필요한 시점에 조정 mode를 연다.
- 한 화면에서 여러 편집 작업이 경쟁하지 않게 한다.
- 저장 전에 어떤 결과와 몇 개 항목이 만들어지는지 보여준다.
- URL 원문을 확보하지 못했을 때 가짜 Flow나 live AI 생성처럼 보이는 결과를 만들지 않는다.
- 원래 URL과 사용자가 입력한 메모를 보존하면서 다음 행동을 안내한다.

============================================================
5. 운동·반복 Flow
============================================================

- 4주가 프로그램 종료인지 단순 미리보기 범위인지 구분해야 한다.
- 반복 기간, 종료일, 횟수를 사용자가 이해하고 조정할 수 있어야 한다.
- “월·수·금 · 오전 7:30 · 45분 · 8회”처럼 compact summary를 먼저 보여준다.
- 세부 요일, 시간, 소요 시간, 종료 조건은 필요할 때 펼친다.
- 운동만 “완료/강도 낮춤/휴식” 같은 별도 실행 문법을 사용하지 않게 한다.
- 다른 Flow와 같은 완료·다시 열기·건너뛰기 문법을 기본으로 사용한다.
- 반복 series와 개별 occurrence를 구분하되 사용자 화면은 단순하게 유지한다.
- 한 회차 완료가 전체 series 완료를 의미하지 않아야 한다.
- 영상과 URL은 완료할 확인 항목이 아니라 자료 영역으로 분리한다.
- Flow 찾기, My Flow, Calendar에서 같은 운동 Flow가 서로 다른 화면 문법을 사용하지 않아야 한다.
- Calendar grid에 긴 반복 설명이나 raw RRULE을 노출하지 않는다.

============================================================
6. Calendar
============================================================

- Flow가 많아졌을 때 가로로 긴 필터 버튼 행이 되지 않아야 한다.
- 최근·활성 Flow 그룹, 검색 가능한 전체 목록, 선택 요약을 검토한다.
- 특정 Flow만 선택해서 볼 수 있어야 한다.
- 날짜 없는 할 일을 Calendar에서도 발견하고 날짜를 배치할 수 있어야 한다.
- 날짜 없는 항목을 찾기 어렵지 않게 별도 tray 또는 sheet를 제공할 수 있다.
- 여러 항목을 선택해 같은 날짜로 이동하거나 함께 날짜를 바꾸고 되돌릴 수 있어야 한다.
- 기준일 전체 이동과 개인 고정 날짜 유지 정책을 명확히 해야 한다.
- 같은 날짜에 Flow가 여러 개면 grid는 compact summary로 보여준다.
- 선택일 agenda에서는 모든 Flow와 항목을 자세히 보여준다.
- 항목 상세를 페이지 아래에 길게 붙이기보다 bottom sheet, popover, inspector 같은 구조를 검토한다.
- 모바일과 wide에서 날짜 선택, 상세 확인, 완료가 같은 조작 문법을 사용해야 한다.
- 반복 Flow도 Flow 찾기와 My Flow에서 사용하는 occurrence 문법을 그대로 사용해야 한다.

============================================================
7. My Flow
============================================================

My Flow는 사용자 피드백에서 가장 반복적으로 지적된 영역이다.

- 여러 종류의 카드가 한 화면에 길게 쌓여 무엇을 보여주는 화면인지 불명확하다.
- 글이 많고 명령이 분산돼 있어 전체 흐름을 이해하기 어렵다.
- 단순한 시각 보정이 아니라 구조를 다시 설계할 수 있어야 한다.
- “Flow 목록 → 선택한 Flow의 focused workspace” 구조가 적합한지 검증한다.
- 선택한 Flow 안에서는 다음 행동, 전체 계획, 기록, 조정, 가져가기, 관리 순으로 보여준다.
- 오늘 화면은 실행 중심으로 사용한다.
- 전체 Flow 화면은 구조, 일정, 기록, 관리 중심으로 사용한다.
- 같은 occurrence를 여러 영역에 중복 표시하고 각각 완료하게 하면 안 된다.
- 제목, 날짜, 메모 수정은 2~3단계 안에 도달할 수 있어야 한다.
- 항목 추가, 삭제, 복구, 순서 변경이 한 문법으로 제공돼야 한다.
- 같은 날짜의 항목은 시각적으로 묶여야 한다.
- 20개 이상 Flow가 있어도 검색, 필터, 열기가 쉬워야 한다.
- Flow가 적을 때는 과도한 검색 UI를 강요하지 않는다.
- 완료 취소를 쉽게 발견할 수 있어야 한다.
- 저장 직후 오늘 항목 하나만 보여주지 말고 저장된 전체 Flow와 다음 행동을 확인하게 한다.
- export와 lifecycle 명령을 모든 행에 펼치지 말고 선택한 Flow 맥락 안에 둔다.
- 모바일과 wide에서 같은 행동 이름과 순서를 사용한다.

Flow lifecycle:

- 활성 Flow는 보관할 수 있어야 한다.
- 보관 직후 즉시 되돌릴 수 있어야 한다.
- 보관된 Flow는 새로고침 후에도 복구할 수 있어야 한다.
- 영구 삭제는 보관된 Flow에서만 제공한다.
- 영구 삭제 전에 삭제 범위와 복구 불가를 명확히 보여준다.
- source-backed Flow의 공개 원본은 개인 Flow 삭제로 제거되지 않는다.

============================================================
8. 저장 결과와 가져가기
============================================================

- 저장 직후 오늘 항목 하나가 아니라 저장된 전체 Flow 결과를 확인해야 한다.
- 저장 전 화면과 저장 후 receipt 화면을 구분한다.
- receipt에는 저장 이름, 항목 수, 날짜 범위, 출처, 다음 행동이 보여야 한다.
- 가져가기 전에 결과 범위와 개수를 확인할 수 있어야 한다.
- 예: 전체 24개, 선택 5개, 현재 항목 1개.
- 항목 하나씩만 내보내는 방식은 활용 가치가 낮다.
- 전체, 선택, 현재 범위를 모두 자연스럽게 지원해야 한다.
- Calendar, ICS, Checklist, Sheet, Memo가 같은 개인 수정본을 읽어야 한다.
- 목적지에서 빠지는 정보가 있다면 실행 전에 알려준다.
- 자료, 반복 조건, 개인 메모, 완료 상태가 어떤 destination에 포함되는지 일관돼야 한다.
- export 완료 후 실제 결과 개수와 다음 이동 위치를 보여준다.

============================================================
9. 완료·수정·메모·회고
============================================================

- 완료한 할 일을 다시 미완료로 돌릴 수 있어야 한다.
- 완료, 다시 열기, 건너뜀, 제외, 삭제는 서로 다른 의미여야 한다.
- 실행 중 단계별 메모와 수정 의견을 남길 수 있어야 한다.
- 회고를 Flow 종료 후에만 강제하지 않는다.
- 항목별 메모는 최종 회고와 연결될 수 있지만 같은 정보로 덮어쓰지 않는다.
- source 수정 요청과 개인 실행 회고를 구분한다.
- 한 번 완료한 Flow를 다시 사용할 때 이전 실행 기록과 회고를 보존한다.
- 새 기준일로 재사용할 때 개인 고정 날짜 유지 여부를 선택할 수 있어야 한다.

============================================================
10. 데이터와 상태 원칙
============================================================

다음 데이터 층을 분리한다.

1. source/content
2. published Flow
3. personal overlay
4. personal structural overlay
5. execution run
6. recurrence series/occurrence
7. export identity/receipt

필수 원칙:

- source-backed 원본을 개인 수정값으로 덮어쓰지 않는다.
- source-backed 항목 제외는 원본 삭제가 아니다.
- 개인 draft 항목 삭제는 복구 가능한 tombstone으로 처리한다.
- 완료 상태를 structural overlay에 저장하지 않는다.
- 개인 메모와 제외 sentinel을 같은 필드에 저장하지 않는다.
- 기준일 재계산으로 개인 고정 날짜와 메모를 덮어쓰지 않는다.
- 반복 회차 완료가 series 정의를 변경하지 않는다.
- 같은 source, user job, intentional variant는 진입 경로가 달라도 같은 canonical identity로 해석한다.
- source URL 하나만으로 canonical identity를 결정하지 않는다.
- 24개와 5개처럼 의도적으로 다른 편집본은 자동 병합하지 않는다.
- 기존 개인 사본, 완료 기록, 메모, occurrence, export identity를 migration 과정에서 삭제하지 않는다.

============================================================
11. 디자인 원칙
============================================================

- 긴 설명으로 UX 문제를 덮지 않는다.
- 첫 화면에는 실제 결과와 primary action 하나를 우선한다.
- 중첩 카드와 반복되는 목록을 줄인다.
- 한 화면의 경쟁하는 primary action은 하나 이하로 유지한다.
- 세부 설정은 progressive disclosure로 연다.
- 익숙한 icon, menu, sheet, dialog, segmented control을 사용한다.
- 완료, 수정, 삭제, 이동, export를 같은 행에서 경쟁시키지 않는다.
- Calendar, Notion, Todoist, Things, TickTick, 운동 계획 앱, 여행 앱 등의 패턴을 조사한다.
- 외부 제품을 그대로 복제하지 말고 FlowMe의 역할에 맞게 적용한다.
- 콘텐츠별 특성은 결과 형태에 반영하되 기본 command grammar는 통일한다.
- 내부 구조어, 개발 용어, raw recurrence 표현을 사용자에게 노출하지 않는다.
- 모바일 390px을 우선한다.
- 1024px과 1440px은 모바일 단순 확대가 아니라 rail, canvas, inspector 역할을 사용한다.
- horizontal overflow, fixed overlap, 이름 없는 focusable control을 허용하지 않는다.
- 시각적으로도 상용 서비스 수준까지 다듬는다.

============================================================
12. 검토와 개발 방식
============================================================

- 잘나가는 Calendar, Todo, Notion, 운동, 여행 서비스의 실제 사용자 흐름을 비교한다.
- 여러 페르소나가 한 번 저장하고 끝나는 것이 아니라 여러 세션에 걸쳐 사용하는 상황을 시뮬레이션한다.
- 발견, 저장, 수정, 실행, 완료, 복구, export, 회고, 재사용을 연속해서 검토한다.
- 자동화, Playwright, screenshot, agent simulation을 실제 사용자 관찰로 표현하지 않는다.
- current production interaction, current source, current screenshot을 prior artifact보다 우선한다.
- 오래된 페이지와 콘텐츠를 현재 구현의 정답으로 사용하지 않는다.
- 구현 전 current/proposed wireframe을 비교할 수 있다.
- 단순 수정으로 해결되지 않으면 bounded redesign 또는 대대적 구조 변경을 검토할 수 있다.
- 데이터 계약 변경은 별도 근거와 migration/rollback 계획이 있을 때만 진행한다.
- 기존 dirty worktree와 사용자 변경을 보존한다.
- commit, push, PR, merge, deploy 상태를 각각 분리해 보고한다.
- STATUS, ROADMAP, DECISIONS, backlog를 실제 상태에 맞게 갱신한다.

============================================================
13. 현재 반영 상태
============================================================

기반 또는 기능 수준에서 반영된 항목:

- 완료와 완료 취소
- 개인 항목 추가·삭제·복구·순서 변경
- 날짜 지정·변경·제거
- 시간, 예상 소요 시간, 반복 계약
- Calendar/ICS/checklist/sheet/memo projection
- whole/selected/current export scope
- archive, restore, 영구 삭제 lifecycle
- public 저장 전 preview와 저장 후 completion 경계
- source/personal/run/occurrence/export 데이터 분리
- canonical identity와 legacy 사본 보존

부분적으로 반영됐지만 체감 검토가 필요한 항목:

- progressive editor
- Calendar 날짜 없는 항목 배치
- batch date placement와 undo
- My Flow focused workspace
- 전체 Flow 저장 receipt
- 반복 occurrence UI
- export preflight와 compact receipt
- 단계별 메모와 최종 회고 연결

아직 사용자 관점에서 미완료로 보는 항목:

- 홈과 Flow 찾기의 역할 분리
- 홈과 Flow 찾기의 동일 Flow 상세 정합성
- 콘텐츠마다 다른 상세 화면 문법 통일
- 저장 전 조정 UX의 실질적 개선
- 다섯 가지 실제 Flow 결과 형태의 명확한 예시
- 결혼 Flow의 형식 선택과 다음 행동
- 운동 Flow의 반복 설정과 실행 UI 단순화
- Calendar Flow scope의 대규모 확장성
- Calendar 항목 상세 표시 방식
- My Flow 전체 정보 구조와 시각 위계
- 실제 사용량, 리뷰, 신뢰 정보 정책
- 실사용자 관찰 전 상용 서비스 수준의 UX/UI 완성도

보류 또는 비범위:

- 임의 URL의 실제 crawler
- 실제 AI 자동 생성
- account, DB, cloud sync
- Google Calendar, Todoist, Notion 등의 OAuth 직접 연동
- 모든 외부 planner 기능을 FlowMe 안에 재구현

현재 실제 관찰 사용자 수는 0명이다.
자동 테스트가 통과하더라도 실제 사용자 검증 완료로 표현하지 않는다.

============================================================
14. 앞으로 가장 중요한 우선순위
============================================================

1. 홈과 Flow 찾기의 역할과 cross-entry 상세 화면을 통일한다.
2. Flow 상세를 artifact-first 구조로 다시 정리한다.
3. 저장 전 조정을 제목·날짜·항목·순서까지 자연스럽게 확장한다.
4. 결혼·운동·이사 등 대표 콘텐츠의 차이는 살리되 조작 문법을 통일한다.
5. My Flow를 library와 focused workspace 중심으로 다시 검증하고 필요하면 재설계한다.
6. Calendar scope, 날짜 없는 항목, 선택일 상세 composition을 정리한다.
7. 전체·선택·현재 export의 결과 예측과 receipt를 단순화한다.
8. 모든 주요 여정을 여러 페르소나와 여러 세션으로 다시 시뮬레이션한다.
9. 상용 서비스 수준의 시각 완성도와 모바일 사용성을 독립 검토한다.
10. 자동 QA 이후에만 실제 사용자 관찰 준비도를 다시 판단한다.

최종 판단:

FlowMe의 실행 기반과 데이터 계약은 상당 부분 구축됐다.
하지만 사용자에게 보이는 제품 경험은 아직 기능의 존재만큼 단순하고 명확하지 않다.
다음 단계는 기능을 더 늘리는 것이 아니라 홈, Flow 찾기, 저장 전 조정, Calendar, My Flow를 하나의 일관된 사용자 문법으로 다시 조립하는 것이다.
특히 My Flow는 부분 수정에 제한하지 않고 비교 prototype과 사용자 여정 simulation을 거쳐 구조를 다시 열 수 있어야 한다.
