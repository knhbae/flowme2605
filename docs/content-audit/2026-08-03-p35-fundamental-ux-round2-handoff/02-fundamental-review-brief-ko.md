# 근본 UX 검토 브리프

## 검토 목표

이번 라운드의 목표는 화면을 예쁘게 다듬는 것이 아니라, P35 MVP에서 사용자가 다음 상태를 구분하고 다음 행동을 예측할 수 있는 구조를 확정하는 것입니다.

```text
Flow 찾기
→ 저장 전 결과 미리보기
→ 개인 초안 편집
→ 내 계획에 저장
→ 저장된 계획 상세
→ 실행 또는 내 도구로 옮기기
→ 완료·메모·재방문
```

위 흐름은 검토용 기본 가설이며 확정안이 아닙니다. Codex와 Claude Design은 대안과 반증 근거를 함께 제시해야 합니다.

## 결정 순서

### D1. 생명주기와 화면 소유권

먼저 공개 상세·저장·`내 Flow`·내보내기·실행·완료의 책임을 한 번씩만 배치합니다.

| 행동 | 검토용 기본 소유 화면 |
|---|---|
| 원문과 결과 읽기 | 공개 상세 |
| 지원 결과 형식 미리보기 | 공개 상세 |
| Flow 전체 편집 | 전용 전체 높이 편집 화면 또는 sheet |
| 편집 적용·취소 | 같은 편집 세션 |
| 개인 상태로 저장 | 저장 전 상세 |
| 저장 결과 확인 | 짧은 영수증 또는 저장된 상세로 직접 전환 |
| 최신 개인 상태 내보내기 | 선택된 `내 Flow` 상세 |
| Item 수정·메모·완료 | Item 상세 |
| 날짜 중심 실행 | Today/캘린더/Item 상세 |

내보내기 정책은 다음 세 안을 비교합니다.

- A안: 공개 화면은 미리보기만, 실제 내보내기는 저장 후 `내 Flow`에서만 한다.
- B안: 공개 화면에서도 빠른 내보내기를 허용하고, 저장 후에는 개인 수정본을 다시 내보낼 수 있다.
- C안: 개인화가 필요 없는 단순 Flow만 저장 없이 내보내고, 나머지는 저장을 요구한다.

사용자 선호는 A안에 가깝지만, FlowMe가 외부 캘린더·할 일·메모로 빠르게 옮겨주는 export-first 제품이라는 점과 함께 판단해야 합니다. 클릭 수가 아니라 `어느 버전을 옮기는지`, `저장 강제인지`, `중복 생성인지`, `실패 후 복구 가능한지`로 비교합니다.

### D2. `내 Flow` 정보 구조

검토용 데이터 관계는 다음과 같습니다.

```text
저장된 계획 하나
├─ 오늘/지금 할 일: 날짜와 상태로 자동 추린 실행 화면
├─ 저장한 계획: 전체 계획을 찾고 관리하는 화면
└─ 캘린더·할 일·체크리스트·메모·시트: 같은 계획의 목적지별 결과
```

`지금 할 일`과 `저장한 Flow`를 서로 다른 저장소처럼 만들면 안 됩니다. Today는 저장된 Item의 파생 화면이어야 합니다.

반드시 비교할 진입 상황:

- 저장한 계획이 0개인 첫 방문
- 방금 하나를 저장하고 들어온 상태
- 일반 재방문에서 오늘 할 일이 있는 상태
- 날짜 없는 계획만 있는 상태
- 저장한 계획 5개와 20개
- 완료·보관한 계획이 섞인 상태

### D3. 하나의 canonical 데이터와 결과 투영

캘린더·할 일·체크리스트·메모·시트는 서로 다른 콘텐츠가 아니라 같은 Item·Step·Flow를 다른 목적지에 맞게 보이는 결과여야 합니다.

현재 확인된 구현 범위는 다음과 같습니다.

- 내부 결과 미리보기: 캘린더, 체크리스트, 시트, 메모, Flow 실행 5종
- 명시적 내보내기: 캘린더, 체크리스트, 시트, 메모 4종
- Todo: 데이터 의미에는 있지만 독립 미리보기·내보내기 대상으로 연결되지 않음
- 공개 상세: 현재 `showShapeChoices={false}`로 한 종류만 노출

따라서 사용자 요청의 “5개 format”을 숫자 그대로 구현하기 전에 다음을 결정해야 합니다.

1. `할 일`과 `체크리스트`가 사용자에게 정말 다른 결과인가?
2. 날짜 없는 Flow에 캘린더를 어떻게 제시할 것인가?
3. 표로 만들 정보가 없는 Flow에 시트를 보여줄 것인가?
4. 지원 불가 형식을 숨길지, 조건을 알려줄지, 비활성으로 보여줄지?
5. 한 곳에서 수정한 제목·순서·날짜·메모가 모든 결과에 동일하게 반영되는가?

기본 가설은 `가장 자연스러운 결과 1개 + 실제 의미 있는 보조 결과`입니다. 모든 Flow에 빈 다섯 탭을 강제하지 않습니다.

### D4. 공통 편집 거래

공개 Flow 편집과 저장된 Flow 편집은 같은 필드·순서·버튼 위치·접근성 문법을 사용해야 합니다. 다만 거래 의미는 다릅니다.

- 공개 편집: 아직 저장되지 않은 개인 초안에 적용
- `내 Flow` 편집: 이미 저장된 개인 상태를 갱신

공통 편집기 계약에 포함할 것:

- Flow 이름과 필요한 subtitle/설명
- 기준일 또는 날짜 없음
- Item 포함/제외, 순서, 제목, 상세, 날짜
- 적용, 취소, 닫기, 뒤로가기
- 저장하지 않은 변경 경고
- 오류 발생 시 기존 상태 보존
- 편집 후 모든 결과 미리보기의 즉시 일치

모바일에서는 기존 내용 아래로 편집기를 이어 붙이는 방식과 전용 전체 높이 surface를 비교합니다. 긴 Flow에서 편집 맥락이 섞이는지, 닫은 뒤 원래 위치와 초점으로 돌아오는지 확인합니다.

### D5. 도움말과 주의사항

모든 문장을 `?` 또는 `!`에 넣는 규칙은 사용하지 않습니다.

| 정보 등급 | 기본 노출 |
|---|---|
| 제목·입력값·버튼을 그대로 반복 | 삭제 |
| 용어 정의, 드문 예외, 긴 사용법 | `도움말` popover/sheet |
| 선택 결과·적용 범위·내보내기 형식 | 결정 지점 가까이에 짧게 표시 |
| 되돌릴 수 있는 가벼운 주의 | 한 줄 또는 필요할 때 열기 |
| 안전·개인정보·중복 생성·되돌릴 수 없는 결과 | 핵심 한 줄을 항상 표시하고 상세만 확장 |

아이콘에는 `도움말`, `주의사항`이라는 접근성 이름, 44px 안팎의 터치 영역, 키보드 열기·닫기, 모바일 뒤로가기, 닫은 뒤 초점 복귀가 필요합니다.

### D6. 용어와 CTA

`완료`는 실제 Item 실행 완료에만 쓰는 것을 기본 가설로 둡니다. 저장 단계는 클릭 결과를 말해야 합니다.

| 현재 | 비교 후보 |
|---|---|
| Flow 찾기 | 계획 찾기 |
| 내 Flow | 내 계획 |
| Flow 시작 | 내 계획에 저장 / 저장하고 시작 |
| Flow 편집 | 계획 수정 |
| Flow Map | 계획 구성 또는 제거 |
| 내 도구로 옮기기 | 유지 후보, 목적지 선택과 실제 전송을 구분 |
| 실행할 일 | 삭제 후보 |
| 할 일 수정 | 수정 / 항목 수정 |
| 더보기 | 결과 보기 / 다른 형식 보기 |

브랜드와 내부 모델에는 `Flow`를 유지하면서 첫 노출과 행동 문구에서는 `계획`을 쓰는 안도 비교합니다.

### D7. 시각적 감산

마지막에 처리합니다.

- Item 상세의 파란 표면이 의미 없는 장식이면 중립 surface로 통일
- `실행할 일`처럼 내용이 이미 말하는 heading 삭제
- Flow Map 세 칸을 값별로 필요성 평가 후 삭제 또는 통합
- 날짜 입력값과 동일한 확인 문장 삭제
- 같은 의미의 기본·선택·경고·완료 상태에 하나의 시각 언어 적용

## MVP 범위 제안

이번 검토가 확정해야 할 것은 다음 계약입니다.

1. 공개 상세·저장·`내 Flow`·내보내기의 책임표
2. `내 Flow` 첫 화면과 저장 직후 진입 규칙
3. 지원 가능한 결과 형식과 표시 조건
4. 공개/저장 후 공통 editor 계약
5. 도움·주의 노출 규칙
6. 사용자 화면 용어와 CTA 원칙
7. U01~U10의 채택·부분 채택·기각 사유

고급 필터, 협업, 자동 동기화, AI 재계획, 복잡한 프로젝트 계층, 완전한 디자인 시스템 재구축은 이번 MVP 검토 범위가 아닙니다.

## 검토 통과 조건

- 저장 전 미리보기와 저장 후 개인 상태를 구분할 수 있음
- 편집·저장·내보내기·실행 완료가 각각 하나의 기본 위치와 뜻을 가짐
- 실제 지원 가능한 결과 형식만 제시함
- 같은 Item 수정이 모든 화면과 결과에 일치함
- 중요한 주의가 아이콘을 열어야만 보이지 않음
- 공개/`내 Flow` 편집의 거래와 복구가 예측 가능함
- 390px 모바일에서 주 행동과 내용이 겹치지 않음
