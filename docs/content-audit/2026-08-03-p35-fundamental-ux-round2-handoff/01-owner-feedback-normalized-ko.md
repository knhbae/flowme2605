# 사용자 피드백 재구성

## 한 줄 결론

이번 피드백은 작은 UI 수정 10개가 아니라 `내 Flow의 역할`, `저장·내보내기 생명주기`, `여러 결과 형식의 관계`, `편집과 완료의 소유권`을 다시 정하라는 신호입니다. 이 네 가지를 먼저 정하지 않으면 문구·색상·팝업을 고쳐도 화면별 예외가 다시 생깁니다.

## 근본 문제별 묶음

| 우선순위 | 근본 문제 | 관련 피드백 | 먼저 답할 질문 |
|---|---|---|---|
| P0 | 저장 전·후 생명주기와 행동 소유권 | 1, 7, 8, 9 | 공개 상세, 저장, `내 Flow`, 내보내기, 실행, 완료를 어느 순서와 화면이 소유하는가? |
| P0 | `내 Flow` 정보 구조 | 3, 7, 8, 10 | 첫 화면은 오늘 할 일, 저장한 계획, 방금 저장한 계획 중 무엇을 우선해야 하는가? |

## 피드백별 현재 사실과 검토 방향

| ID | 사용자 피드백 | 현재 확인된 사실 | 근본 검토 | 제안대로 바로 적용할 때의 위험 |
|---|---|---|---|---|
| U01 | F-05 내보내기는 `내 Flow`에서 해야 함 | 공개 상세와 `내 Flow` 양쪽에 내보내기가 있어 소유권이 중복됨 | 저장 전 미리보기와 저장 후 실제 전송을 분리할지, 저장 없는 빠른 내보내기를 유지할지 비교 | `내 Flow` 저장을 강제하면 export-first 약속이 무거운 내부 작업공간으로 바뀔 수 있음 |
| U02 | 도움은 `?`, 주의는 `!` 팝업 | 공통 분류 규칙 없이 설명과 주의가 인라인으로 흩어짐 | `삭제 / 필요할 때 열기 / 짧게 항상 표시 / 행동 옆에 표시` 네 등급을 먼저 정의 | 건강·안전·개인정보·중복 생성 위험까지 아이콘 안에 숨길 수 있음 |
| U03 | `내 Flow` 탭 전체 재설계와 타 앱 study 필요 | 기본 화면은 `지금 할 일 / 저장한 Flow` 두 보기이며 실행·관리·편집·내보내기를 모두 가짐 | 저장한 계획을 원본으로 두고 Today를 파생 화면으로 볼지 검증 | 타 앱의 프로젝트 계층·필터·대시보드까지 복사하면 MVP가 무거워짐 |
| U04 | Item 상세 색상 통일, `실행할 일` 삭제, `할 일 수정→수정` | 파란 표면, 해당 문구 모두 실제 활성 화면에 있음 | 정보 순서와 행동 의미를 먼저 정한 뒤 감산 | `수정`만 쓰면 Flow 수정인지 Item 수정인지 문맥에 따라 모호할 수 있음 |
| U05 | Flow Map 3칸 요약 삭제 또는 `?`로 이동 | 레거시 활성 Flow Map에 `내 조건 / 저장 결과 / 전체`가 남아 있음 | 세 칸을 한 덩어리로 보지 말고 결정에 필요한 값만 남길지 확인 | 선택 범위·저장 개수처럼 행동 결과에 필요한 값까지 숨길 수 있음 |
| U06 | 시작일 입력값 바로 아래 같은 날짜 표시 불필요 | 날짜 입력 후 동일 날짜 확인 문구가 바로 반복됨 | 반복 문구는 삭제하되 실제 적용 결과는 미리보기에서 한 번 확인 가능해야 함 | 적용 여부 피드백까지 모두 없애면 날짜가 반영됐는지 알 수 없음 |
| U07 | 상세 CTA 통일, 여러 형식 미리보기, 하단 `편집/완료`, 저장 후 `내 Flow` 이동 | 현재는 한 형식만 표시하고 Flow별 CTA가 다름. 저장 뒤에는 영수증에서 다시 `내 Flow에서 이어하기`를 눌러야 함 | 공통 생명주기 CTA와 자연스러운 결과 요약을 분리하고, 지원 가능한 형식만 보여줄지 검증 | `완료`는 편집 종료·저장·실행 완료를 혼동. 모든 Flow에 5형식을 강제하면 빈·가짜 결과가 생김 |
| U08 | 공개/`내 Flow` 편집 UI 통일, 아래 펼침 제거 | 공개 편집은 전용 패널, `내 Flow` 편집은 기존 계획 아래 인라인 | 같은 editor 계약을 사용하되 미저장 초안과 저장된 상태의 거래 차이는 명시 | 화면을 완전히 동일하게 만들면 적용·저장·되돌리기의 차이를 감출 수 있음 |
| U09 | `더보기`는 5형식 미리보기만, 편집은 하단에서 | `/flows`의 `더보기`는 상세로 이동하지만 상세 안에 행 수정·Flow 편집·저장 전 내보내기가 모두 있음 | 공개 상세를 결과 확인, 별도 편집을 수정, 저장 후를 관리·전송으로 나눌지 검토 | 고정 5탭은 다시 복잡도를 만들고 지원 불가 형식을 정상처럼 보일 수 있음 |
| U10 | `Flow`라는 단어가 이해되는지 의문 | 주요 경로 전체에서 `Flow`가 반복되지만 이해도 검증은 없음 | 내부 모델명은 유지하고 외부 라벨 `계획 / 실행 계획 / 저장한 계획`을 비교 | 전면 치환하면 브랜드·경로·내부 모델까지 불필요하게 흔들 수 있음 |

## 과거 판정과 다시 열린 항목

- 이전 P35 보고서에서 공개 내보내기는 당시 정책 아래 반영으로 판정됐습니다. 이번 피드백은 그 정책 자체를 다시 연 것입니다.
- 공개/`내 Flow` 편집 통일은 이전에 개선된 것으로 보였지만, 일반 Flow·Flow Map·저장 방식별 실제 경로를 다시 비교하니 동일하지 않았습니다.
- Flow Map 요약과 Item 상세는 이전에도 부분 완료였습니다. 이번 검토에서 잔여 구조를 명시적으로 다룹니다.
- 시작일 중복과 `Flow` 용어 이해도는 이번에 새로 들어온 항목입니다.

## 반드시 반증할 사용자 해결안

검토자는 사용자 의견에 동의하는 것으로 끝내지 말고 아래 항목 중 최소 두 개에 대해 유지안 또는 반대 근거를 제시해야 합니다.

1. 내보내기를 `내 Flow`에만 두면 저장 강제가 생기지 않는가?
2. 모든 도움·주의를 아이콘 뒤에 숨겨도 중요한 결과와 안전 정보가 보이는가?
3. 모든 Flow에 다섯 형식을 제시해도 빈 결과나 의미 손실이 없는가?
4. 하단 `완료`가 저장과 실제 실행 완료를 혼동하지 않는가?
5. Flow Map 세 칸 중 정말 모두 불필요한가?
6. 두 편집 화면은 UI뿐 아니라 적용·취소·복구 의미까지 같아야 하는가?
7. `Flow`를 모든 곳에서 바꾸는 것이 필요한가, 첫 노출과 행동 문구만 바꾸면 되는가?
