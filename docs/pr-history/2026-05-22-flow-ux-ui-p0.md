## Why

The public Flow detail pages did not answer the first-session questions quickly enough: whether the Flow matched the source content, what to do first, how long it takes, whether progress persists, and how to adapt the checklist to the user's situation.

The immediate goal was to improve Stage 0 execution behavior without adding login, database-backed state, or heavy integrations.

## What Changed

- Reworked the public Flow header to show duration, item count, and the relevant anchor-date action.
- Moved the anchor-date setup card near the top so mobile users see the first action earlier.
- Replaced confusing date-mode options with direct input, undecided, and example-preview choices.
- Added source content cards so users can connect the Flow back to its source.
- Replaced fake public usage/copy stats with an honest beta-operation label.
- Added localStorage persistence for anchor date, item notes, and skipped items.
- Added item-level memo and skip controls; skipped items are excluded from progress.
- Updated text, Excel, and ICS exports to reflect notes and skipped items.
- Removed generic boilerplate item detail copy from public display and export surfaces.
- Expanded the wedding D-180 seed Flow with specific why/how/completion content for all 12 items.
- Made the "next action" module conditional: hidden at 0%, visible during active progress, hidden at completion.
- Updated E2E coverage for first-screen questions, persistence, skip/memo behavior, source cards, and new next-action behavior.

## Not Done

- No database schema changes for source metadata or item detail fields.
- No server-side OG scraping for source thumbnails, titles, or publish dates.
- No login, account sync, or cross-device persistence.
- No full Flow editor redesign; "copy to editable draft" still uses the existing local draft flow.
- No export preview modal or thumbnail.
- No dependency visualization between items.
- No URL-encoded progress sharing.
- No reminder system beyond existing calendar export behavior.
- No production analytics/event tracking for open, anchor input, copy/export, check, or feedback.

## Decisions

- Kept this within Stage 0 constraints: client-side state only, no DB/login/heavy integrations.
- Used localStorage for progression and adaptation because login is intentionally out of scope.
- Used "베타 운영 중" instead of fabricated popularity numbers.
- Treated generic fallback completion criteria as internal filler and hid it from user-facing detail/export output.
- Put source context below the first-action setup on mobile so the primary action appears sooner while source trust still remains near the top.
- Kept `docs/HISTORY.md` unchanged because this is PR-level work, not a tagged release entry.

## Risks

- The public page component is still large, so future UX changes should consider splitting detail-page sections into smaller components.
- localStorage persistence is browser-local and can be lost if storage is cleared.
- Seed-content quality is improved for wedding D-180, but other flows may still need item-specific detail passes.
- Deployed before opening a PR; the PR should explicitly call this out and link this history file.
